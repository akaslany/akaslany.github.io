## 6 반증·과장·재현성 감사

- MCP 공격 벤치마크: 과제는 LiveMCPBench에서 악성 도구 호출과 적대적 응답 수용을 유도하는 것이다. 토큰 비용 비교 기준은 정상 도구 구성이고, 다른 모델로는 재최적화 없이 전이 시험을 했다. 저자 보고 지표는 GLM-4.6에서 네 시나리오 악성 도구 호출률의 매크로 평균 93.6%, 인지적 서비스 거부의 가중 토큰 비용 32.4배, 다른 세 공격 범주의 평균 성공률 74.4%다. 네 다른 모델로의 전이 결과는 각각 63.6%, 2.7배, 24.5%였다. 조건은 실행 추적을 이용한 블랙박스 2단계 최적화다. 운영 환경 침해의 증거가 아니며 다른 MCP 배치로의 일반화와 독립 재현은 확인되지 않았다. 오염 가능성에 관한 별도 공개 내용은 제공된 결과에 없다. [논문](https://arxiv.org/abs/2609.26761)
- 취약점 수정 평가: 과제는 Big-Vul의 C/C++ 취약 함수 203개에 대한 생성 패치 평가다. 비교 기준은 컴파일 성공률·전체 함수 CodeBLEU이며, 변경하지 않은 취약 함수도 기준 사례로 시험했다. 저자 보고에 따르면 컴파일 실패의 약 64%는 모델에 기인하지 않았고, 동일 패치에서 컴파일러 표준 플래그 하나를 바꾸자 컴파일 성공률이 1.8–2.7배 달라졌다. 변경하지 않은 취약 함수는 전체 함수 CodeBLEU에서 모든 모델보다 높은 점수를 받았다. 조건은 공개 코드 모델 3종·프롬프팅 방식 3종을 사용한 통제 실험 5개이며, 저장소상 보고된 컴파일 결과 환경은 Windows 11의 GCC 15.2.0이다. 제안된 편집 중심 diff_F1은 예비 선별 지표이지 수정 품질의 증명이 아니다. 저장소는 Big-Vul 함수 본문을 재배포하지 않아 재현 준비에 제약이 있으며 독립 재현은 확인되지 않았다. 오염 여부에 관한 별도 판단 근거는 제공되지 않았다. [논문](https://arxiv.org/abs/2609.26749)
- 시간 창 보류 — GGUF 지원: Hugging Face 게시물은 로컬 GGUF 추론 속도를 llama.cpp의 llama-bench와 비교한다. 지표는 128토큰 생성의 초당 토큰 수와 체크포인트 크기다. 조건은 M2 Max·32GB·macOS 26.6, PyTorch 2.12.1·kernels 0.17.0이며, llama-bench는 프롬프트 처리를 제외한 3회 평균인 반면 Transformers는 프리필을 포함한 예열 후 3회 중 최고값이다. 동등한 속도 비교가 아니다. 초기 지원은 Apple Silicon·Qwen3.5 중심이고 Transformers main 및 호환 커널이 필요하다. 독립 재현은 확인되지 않았고, 게시 시각도 없다. [공식 글](https://huggingface.co/blog/transformers-llama-cpp-quants)
- 시간 창 보류 — Evaluation Cards: 과제는 HealthBench, FrontierMath, Humanity’s Last Exam, SWE-Bench Pro, Terminal-Bench 2.0과 사이버 평가 2건의 결과·설정을 기록하는 것이다. 신규 단일 모델의 기준 성능이나 통합 지표를 발표한 것은 아니다. 점수는 추론 컴퓨트와 평가 프로토콜에 좌우된다. 공개 기록이 오염 우려를 해소하거나 독립 재실행을 입증하지는 않는다. 개별 설정·기록·오염 공개 여부의 추가 확인이 필요하며 게시 시각은 없다. [공식 글](https://huggingface.co/blog/evaleval-aisi)
- 시간 창 보류 — oMLX 유지관리자 합류: 성능 벤치마크 대상이 아니다. Hugging Face가 Jun Kim의 합류와 oMLX 유지 계획을 발표했지만 신규 코드 릴리스나 한국 관련 사건으로 해석하지 않았다. 게시 시각이 없고, 게시물 댓글에는 연결 저장소 접근이 어렵다는 제보가 있어 저장소·후속 릴리스 확인이 남았다. [공식 글](https://huggingface.co/blog/omlx)
