1. 개요 (Overview)

2026년 11월 20일, Anthropic 소속 수학자 레벤트 알푀게(Levent Alpöge)는 인공지능 모델 Claude와 협업하여 작성한 17만 5,187개 파일(약 1,700만 줄, 비공백 기준 약 1,550만 줄, 약 9억 8,040만 자) 규모의 Lean 4 기반 리만 가설(GRH 포함) 기계 검증 코드베이스를 공개하였다. 이 증명은 공개 직후인 11월 21일, Lean 및 Mathlib 공식 커뮤니티(leanprover-community)의 다중 독립 커널(Comparator, con-leche, con-ron 등) 검증을 거쳐 표준 RiemannHypothesis 명제와 정확히 일치하며 논리적 결함이 없는 참(True) 상태임이 공식 인증되었다.

그러나 해당 증명은 기계적 검증이 완료되었을 뿐, 인간 언어로 환산할 경우 25만 페이지를 상회하는 미증유의 AI 생성 기계 코드이다. 거대한 뼈대 속에 수많은 군더더기와 인공지능 특유의 우회 추론 단계가 얽혀 있어, 수학자들이 내부 논리를 직접 읽고 정수론적 아이디어를 소화하기 위해서는 체계적인 해독 및 구조적 축약 작업이 필수적으로 요구되는 상황이다.

기계 검증의 완결성과 인간의 소화 불능 사이의 극심한 간극을 메우기 위해, 공개 대시보드(riemann.verifytask.cn, Bohrium Playground 연동)를 중심으로 대규모 언어 모델(LLM)과 에이전트 하네스를 동원하여 증명 코드를 자동 최적화·압축하는 공개 챌린지가 진행 중이다. 동시에 워털루대, IHES, AMU 등 주요 학계 연구진은 컴퓨터 과학의 역공학(Reverse Engineering) 기법과 멀티-LLM 교차 파이프라인을 가동하여 1,700만 줄의 블랙박스 코드를 자연어 수학 논조로 해독하는 연구를 전개하고 있다.

2. 주요 논점 (Key Arguments & Technical Analysis)
2.1. Lean 4 증명 압축의 기술적 원리와 무결성 보장 메커니즘

  • [사실(Fact)]

    • Lean 4 커널은 모든 추론 단계를 기계적으로 엄격히 검사하므로, LLM이 리팩토링한 코드가 컴파일러를 통과하면 압축본의 논리적 무결성은 수학적으로 보장된다.
    • 공개 대시보드(riemann.verifytask.cn)는 공백·주석·import 구문을 제외한 토큰 수만 채점하는 anti-golf 방식을 채택하고 있으며, 모든 제출물은 Lean 4.34.1 및 4.33.1 컴파일러 환경과 Comparator를 통해 sorry 0개 및 표준 공리만 사용했는지 검증받는다.
    • 소스에 명시된 주요 압축 성과 데이터:
      • Core 1(영점 없는 영역): 코시 적분·오일러-매클로린 추정 코드를 Mathlib의 DSlope와 BorelCaratheodory로 대체하여 21개 파일에서 1개 파일로(-94.7%, 21.6k 토큰 → 1,153 토큰) 압축됨.
      • Core 3(절단 명시 공식): Mathlib의 GammaR_eq_zero_iff 등을 활용해 89개 파일에서 2개 파일로(-86.5%) 압축됨.
      • Core 4(Siegel-Walfisz): 114개 파일을 1개 파일로(-89.7%) 통합함.
      • Core 5(히로나카 특이점 해소): 500개 파일을 10개 모듈로 재구성하고 죽은 보조정리를 삭제하여(-39.5%) 압축함.
      • Core 7(기약 복소 다양체 연결성): 584개 파일을 1개 파일로(-98.7%) 대폭 축소함.

  • [소스의 주장(Source Claim)]

    • AI 또는 자동화 파이프라인이 초기에 작성한 Lean 증명은 불필요한 중간 단계, 중복 보조정리, 장황한 수동 증명 등 군더더기가 많다.
    • LLM에 기존 코드와 Lean 컴파일러가 출력하는 타입 오류 메시지를 반복적으로 피드백(Feedback Loop)함으로써, 장황한 수동 증명 구문을 tactic? 호출 한두 줄로 통합하거나 Mathlib의 기존 정리를 재사용하도록 리팩토링하여 단시간 내 용량을 대폭 줄일 수 있다.
    • 리팩토링 과정에서 가동되는 핵심 3대 압축 기법:
      1. Mathlib 기존 정리 재활용 및 수학적 우회: 원본 AI 증명이 수십~수백 개 파일에 걸쳐 직접 바닥부터 구현한 대수·해석적 보조정리를 Mathlib 표준 도구(예: DSlope, BorelCaratheodory, GammaR_eq_zero_iff)로 치환하여 모듈 규모를 축소함.
      2. Lean 4 자동화 전술(Tactic) 집중 투입: 장황하게 풀어쓴 대수 및 부등식 전개 단계를 grind, grw, simp_all, linarith 등 고성능 자동화 tactic 단일 호출로 통합함.
      3. 모듈 통합 및 죽은 보조정리(Dead Lemma) 가지치기: 증명 탐색 과정에서 파생된 불필요한 중간 인터페이스와 쓰이지 않는 보조정리를 탐지·정리하여 모듈을 통합함.

  • [작성자/해설자 해석(Interpretation)]

    • 형식 검증 관점에서 Lean 4 코드의 기계적 컴파일 통과 및 용량 축소와 리만 가설 증명의 논리적 유효성을 판단하는 것은 철저히 구별되어야 한다. 따라서 압축 성패 판단 시 아래 3가지 핵심 함정을 반드시 검증해야 한다.
      1. sorry 키워드 잔재 여부: 증명을 생략하고 임시 처리하는 구문이 포함되어 있으면 미완성 증명이다.
      2. 임의 공리(axiom) 추가 여부: 표준 공리 외 검증되지 않은 가정을 axiom으로 추가 선언하면 불완전하거나 비논리적인 명제도 짧게 통과할 수 있다.
      3. 명제 정의의 정확성: 코드 최종단에 증명된 대상이 실제 수학계의 리만 가설(제타 함수의 정의 및 조건)과 정확히 동치인지 인간 전문가의 검토가 수반되어야 한다.
2.2. 전체 압축 진척도(-0.5%)와 Phase 3(Core 14~25) 병목 현상
  • [사실(Fact)]
    • 독립적인 소규모 고전 정리 영역인 Core 1~13(Phase 1·2)에서는 -39.5%에서 -98.7%에 달하는 높은 압축률이 기록되었다.
    • 반면 증명 본체이자 핵심 지배(Dominator) 슬라이스인 Phase 3(Core 14~25)의 12개 슬라이스는 현재 모두 -0.0%의 진척도에 머물러 있어 검증을 통과한 압축본이 존재하지 않는다.
    • 전체 175,187개 파일 중 Core 1~25 합산 규모는 158,020개 파일(9억 383만 자, 전체의 92.19%)이며, 현재 전체 통합 압축 성과는 -0.5%(-287만 토큰 / -1,089만 자 절감) 수준에 그쳐 있다.

  • [소스의 주장(Source Claim)]

    • Core 1~13은 이미 교과서적으로 잘 알려진 정리들이므로 사전 학습된 수학 지식과 Mathlib API를 결합해 처음부터 새로 작성(Clean-Room Rewrite)하는 것이 매우 유리하다.
    • Phase 3(Core 14~25)는 아벨 다양체 이론(Abelian Variety Theory) 한 영역만 전체의 50.46%(99,187개 파일, 4억 9,470만 자)를 차지할 정도로 거대하고 복잡하게 얽혀 있어 압축 난이도가 극도로 높다.

  • [작성자/해설자 해석(Interpretation)]

    • LLM 에이전트들이 Phase 3(Core 14~25)에서 성과를 내지 못하고 -0.0%에 머무는 원인은 단순한 단순 난이도 상승이 아니라 아키텍처 차원의 5가지 물리적 요인 때문이다.
      1. 기억 기반 재작성 불가능성: 사전 학습 데이터에 존재하지 않는, 알푀게와 Claude가 41일간의 시행착오 끝에 새로 창안한 인류 최초의 증명 경로이므로 사전 학습 지식에서 더 짧은 표준 증명을 꺼내 쓸 수 없다.
      2. 물리적 컨텍스트 초과: 가장 작은 Core 14조차 1,153만 자(1,945개 파일), Core 16은 3억 8,740만 자(62,858개 파일)에 이르러 단일 슬라이스가 수천만~1억 토큰을 훌쩍 넘기므로 모델의 단일 추론 범위를 완전히 이탈한다.
      3. 동결된 상위 파일(Frozen Upstream)의 족쇄: 하위 슬라이스들이 수만 개의 상위 인터페이스 규격(Core 21: 51,214개, Core 20: 36,241개, Core 19: 27,520개, Core 17: 24,566개 등)에 강하게 결합되어 있어, 입출력 정의를 변경하지 않고 내부 구조를 재설계하기 어렵다.
      4. Mathlib 기반 인프라 공백: 지겔 모듈라이 토로이달 콤팩트화(Core 22), 산술 힐베르트-사무엘 정리(Core 23), 푸앵카레-를롱 높이 공식(Core 24), 전역 지겔-베유 공식(Core 25) 등 거대 현대 기하학 이론이 Mathlib에 부재하여 수만 개 파일의 이론 체계를 자체 유지해야 한다.
      5. 컴파일 피드백 지연(Latency): 파일 수정 시 수천 개 하류 파일의 타입체킹이 유발되고 본체 빌드에 64코어 서버가 필요한 초대형 프로젝트이므로, 에이전트의 피드백 탐색 루프 속도가 수백 분의 일로 떨어져 자동 압축이 작동하기 어렵다.
2.3. Phase 3(Core 14~25)의 4단계 수학적 계층 구조 및 세타 리프트 메커니즘
  • [사실(Fact)]
    • 알푀게 증명의 출발점은 모든 디리클레 L-함수 $L(\chi, s)$가 $\text{Re}(s) > 1/2$ 영역에서 영점을 갖지 않음을 증명하기 위해 폰 망골트 가중합 $G(x)$가 임의의 $\varepsilon > 0$에 대해 $G(x) \le x^{1/2+\varepsilon}$ 상계를 도출하는 구조이다.
    • 정수 $\mathbb{Z}$ 상에서는 다항식 미분을 통한 영점 중복도(multiplicity) 통제(유한체 위 스테파노프 방식)가 불가능하다. 이에 알푀게 증명은 정부호 유니터리 군(definite unitary groups) 사이를 잇는 길이 약 $\sqrt{X}$의 반복적 세타 리프트(theta lift) 사슬을 구성하여 미분과 동일한 중복도 효과를 보형(automorphic) 세계에서 구현한다.
    • Phase 3의 12개 슬라이스는 최종적으로 Core 14에서 일반화 리만 가설(EveryCharacter)을 도출하는 4단계 계층 구조(Dominator 트리)를 형성한다.
      1. 거대 기초 이론 기둥 (Macro-Pillars: Core 22~25)
        • Core 22: Faltings-Chai 토로이달 콤팩트화 이론을 통한 아벨 다양체 경계 기하 제어.
        • Core 23: 특이점 해소 및 주이데알화를 결합해 모리와키(Moriwaki) 크기·공체적 추정을 제공하는 산술 힐베르트-사무엘 정리.
        • Core 24: 산술 교차 미적분 및 순환 높이 탑을 구축하는 푸앵카레-를롱 기반 높이 공식.
        • Core 25: 국소 에르미트 밀도 정리를 전역 보형 커널 수준으로 확장하는 전역 표준 지겔-베유 공식.
      2. 아라켈로프 공체적 추정 허브 (Dominator 3: Core 15)
        • Core 15: 히로나카 특이점 해소, 주이데알화, 토로이달 콤팩트화, 차우 형식(Chow-form) 높이 비교를 결합해 상계 CovolumeBoundOfX를 출력하는 핵심 병목.
      3. 보형·갈루아 표현 및 기저변환 엔진 (Dominator 4, 2a, 2b: Core 16~18)
        • Core 16: 단일 최대 규모 슬라이스로, 세타 리프트에서 갈루아 표현 패키지(Row0b)를 구성하여 창 다리(vwin_of_row)로 전달.
        • Core 18: 정부호 유니터리 군 상에서의 무조건적 동압 기저변환(BaseChangeIsobaricN) 확립.
        • Core 17: 랭크-$n$ 보형성을 최종 조립 허브가 소비할 수 있는 VWin 상계로 변환하는 엔진.
      4. 세타 대응 가설 조립 및 최종 GRH 도출 (Dominator 1a~1c → 5: Core 19~21, Core 14)
        • Core 19 & 20: 실수 하우 쌍대성 기반 세타 평가 격자(EvLgG) 구축 및 제3 소수 세타 급수 푸리에 계수 정합(ConstantFunctionFits) 증명.

        • Core 14: 그린 높이 상계, 보형 창(VWin), Nonempty (HypsAlt)를 최종 결합해 모든 디리클레 지표 $\chi \pmod N$에 대해 $\text{Re}(s) > 1/2 \Rightarrow L(\chi, s) \ne 0$ (EveryCharacter)을 완성하는 최종 결합 허브.

2.4. 수학계의 4대 역공학(해독) 전략 및 AI-인간 협업 도구 스택

  • [사실(Fact)]

    • 1,700만 줄에 달하는 미증유의 기계 코드를 해독하기 위해 주요 연구 그룹이 공개 사흘 만에 역공학 작업을 가동하였다.
    • 수학자들의 4대 역공학 해독 전략:
      1. Top-Down 의존성 추적과 지배자(Dominator) 그래프 분해: 최상위 정리(theorem riemannHypothesis)에서 시작해 역추적하며 수만 개 파일이 모이는 병목 허브(Dominator)를 추려내 지도로 작성.
      2. 특수화·단순화 (GRH → 리만 제타 함수): 일반화 리만 가설 명제에서 지표 $\chi$를 자명한 지표로 고정해 단순화하고, 렘니스케이트(lemniscate) 타원곡선 사례를 손으로 직접 계산해 수학적 직관을 복원.
      3. 알려진 거대 이론의 블랙박스 격리 (Published Census): 이미 출판된 기존 학계 정리들을 '참인 가설 목록(Census)'으로 격리하여 새롭게 창안된 핵심 논리 구조와 분리.
      4. 압축을 통한 탈난독화 (Compression as Decompilation): 압축 과정을 통해 AI 특유의 죽은 보조정리와 중복 보일러플레이트를 제거함으로써 핵심 수학 논리 체계만 노출.

  • [소스의 주장(Source Claim)]

    • 학계는 인간이 코드를 직접 독해하는 방식 대신, 컴파일러 정적 분석과 프런티어 LLM 군단을 '역컴파일러(Decompiler)'로 투입하는 워크플로를 도입하였다.

  • [작성자/해설자 해석(Interpretation)]

    • 학계가 가동 중인 AI-인간 협업 도구 스택은 기계적 검증 무결성과 자연어 수학 해독 사이의 간극을 메우기 위한 고도의 소프트웨어 아키텍처 역공학 파이프라인이다.

5. 한계와 불확실성 (Limitations & Uncertainties)
  1. 웹사이트 직접 접근 불가에 따른 원본 데이터 확인의 한계
    • 초기 원본 데이터원 중 하나인 웹사이트(riemann.verifytask.cn)에 대한 직접 접근이 불가능하여 실시간 제출 수치나 코드를 직접 대조하지 못하고 제공된 요약 및 PDF 자료 데이터에만 의존하였음을 명시한다.
  2. 번역 충실도 격차(Translation Gap)와 AI 해설 환각 위험
    • Lean 4 코드 자체는 커널 검증을 거쳐 참이 보장되나, LLM이 집필한 67쪽 및 164쪽 LaTeX 해설서가 실제 코드 논리와 1:1로 완전 동치인지는 기계가 검증해 주지 않는다.
    • 거대한 형식 코드를 자연어로 번역하는 과정에서 LLM이 코드에 존재하지 않는 표준 수학 논리를 임의로 보충하는 '해설 환각' 위험성이 존재한다.
  3. 압축 챌린지 리더보드의 비공식성 및 트레이드오프
    • 대시보드 리더보드가 참가자 자가 태그 방식이며 인간 개입, 재시도 예산, 파워유저 편중이 존재하여 엄밀히 통제된 벤치마크로 보기 어렵다.
    • 단일 파일 인라이닝이나 grind 전술을 통한 과도한 압축은 중간 과정의 수학적 아이디어를 덮어버려 인간 수학자의 정수론적 해독을 저해할 수 있는 트레이드오프가 존재한다.
  4. 소스 내 정보 확인 불가 항목
    • 소속이 명시되지 않은 인물(테렌스 타오, 엘리엇 아리지, 사이먼 디데오)의 구체적인 소속 기관 및 직책은 소스 텍스트에 기재되어 있지 않으므로 "확인 불가"로 표기하였다.
