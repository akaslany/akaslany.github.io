I accidentally turned LLM memory into program analysis

웹 · 2026-08-30

요약

Lemmalog는 연역 상태로 검색 메모리를 보완하지만, 사실 추출이 병목이며 성능 근거는 저자 실행에 의존한다.

원문

LLM 메모리를 프로그램 분석으로 만들다 — Jordy Zomer의 Lemmalog 실험 검토

한 문장 결론: 구조화된 연역 상태(deductive state)는 검색(retrieval)에 대한 설득력 있는 보완이지만, 현재 벤치마크 근거는 저자 실행(author-run)이며 추출(extraction) 프런트엔드 품질이 병목이다.

이 보고서는 Jordy Zomer의 에세이 I accidentally turned LLM memory into program analysis(pwning.systems, 2026-08-28)를 변형적·비판적으로 분석한 한국어 기술 검토다. 원문 전체 번역이나 대체물이 아니며, 원문 그림을 재현하지 않는다. 모든 벤치마크 수치는 별도 표시가 없으면 저자가 보고한 실행(author-run) 값이다.

1. 원문의 핵심 주장

저자는 장시간 취약점 조사에서 LLM이 "이미 배제한 접근을 다시 제안하고, 거짓으로 판명된 가정을 계속 믿는" 실패를 반복적으로 겪었다고 말한다. "LLM에게 뭔가가 틀렸다고 말한다고 해서, 그것에 의존하던 모든 것을 모델이 믿지 않게 되는 것은 아니다."

그래서 메모리를 두 질문으로 분해한다.

  • 의미 검색(semantic retrieval): 과거의 어떤 정보가 이 질문에 관련 있는가? — 벡터 DB가 잘하는 문제.
  • 유지되는 연역 상태(maintained deductive state): 지금까지 배운 것 중 지금 참인 것은 무엇인가? — Lemmalog가 실험하는 문제.

어느 쪽도 다른 쪽을 대체하지 않는다. 벡터 DB는 "object_a가 object_b를 가리킨다"는 문장을 관련성 때문에 꺼내지만, 그 문장이 두 시간 뒤 반증되었는지, 그 문장에 의존하던 다섯 개의 결론이 무효화되어야 하는지는 알지 못한다.

2. 실패 모드: 반증된 전제는 의존 결론을 무효화해야 한다

controls(attacker, object_a).
points_to(object_a, object_b).
kernel_object(object_b).

controls_kernel_object(Attacker) :-
    controls(Attacker, ObjectA),
    points_to(ObjectA, ObjectB),
    kernel_object(ObjectB).

points_to(object_a, object_b)가 틀렸다고 밝혀지면, controls_kernel_object(attacker)는 어느 전제에서 나왔는지 추적되므로 자동으로 무효화된다. 이는 "모든 옛 정보를 프롬프트에 넣고 LLM이 같은 것을 알아차리기를 바라는" 방식보다 결정적이다. Datalog의 철회(retraction)는 단순 삭제가 아니다. c :- a.와 c :- b.처럼 결론에 지지 경로가 둘 이상이면, 하나가 사라져도 다른 지지가 살아 있으면 결론은 유지된다. 취약점 조사에서 "candidate_3은 악용 가능"이라는 결론이 하나의 원시(primitive) 실패에도 살아남을 수 있는 이유다. 출처 추적(why() 프로베넌스)은 "왜 이 결론을 믿는가"를 묻는 질문에도 답한다.

3. 유효 구간: 현재 진리와 역사적 진리

사실이 시간에 따라 바뀌면 삭제로는 부족하다. Lemmalog는 사실에 유효 구간(validity intervals)을 붙인다.

viable(primitive_a) [10:14, 12:37)
not_viable(primitive_a) [12:37, ...)

이렇게 하면 "지금 primitive_a가 유효한가?"와 "왜 예전에 그 공격 전략을 탐색했는가?"를 서로 모순되는 사실을 둔 채 LLM 판단에 맡기지 않고 답할 수 있다. 저자 말대로 "이것은 언어 모델 문제가 아니라 대부분 데이터베이스 문제"다. Datalog, 고정점(fixed point), 점증 유지, 프로베넌스, 유효 구간은 수십 년 된 데이터베이스·프로그램 분석 개념이며, Lemmalog의 기여는 이 기계를 에이전트 메모리에 적용한 설계·구현 제안이지, LLM이 추출한 사실이 참이라는 증명이 아니다.

4. 하이브리드 아키텍처

LLM은 확률적 프런트엔드로 자연어·코드·디버거 출력을 구조화 사실로 바꾸고, Lemmalog는 결정론적 백엔드로 사실→규칙→유도 사실을 유지한다. 최종 구조는 "벡터 메모리 OR 기호 메모리"가 아니라 결합이다.

  • 연역 상태: 사실 / 규칙 / 시간 / 출처 / 철회
  • 에피소드 메모리: 모호한 맥락 / 의미 검색 / 원문 텍스트

저자가 "우리의 파서는 확률적이지만, 그 뒤의 모든 것은 확률적일 필요가 없다"고 표현한 지점이 이 아키텍처의 핵심이다.

5. 벤치마크 감사: 프로토콜과 분모

5.1 LongMemEval (저자 실행 vs 공식 기준선)

LongMemEval은 계층화된 102문항 분할(범주당 17문항, 6개 범주: user facts, assistant facts, preferences, multi-session, temporal reasoning, knowledge updates)을 사용한다. MemEval 공식 프로토콜은 reader gpt-4.1, embedding text-embedding-3-small, judge gpt-4o(LongMemEval native binary accuracy)다. 원문에 따르면 추출은 Claude Sonnet 4.6(chunked, file-cached, 대화당 1회 지불)이다.

원문 보고(2026-08-28 스냅샷, 저자 실행 3회):

  • Lemmalog F1 0.463 ± 0.010, accuracy 0.575 ± 0.004
  • 대표 실행 범주: SS-User 0.790, SS-Asst 0.672, Preference 0.128, Multi-Session 0.211, Temporal 0.416, K-Update 0.579
  • 저자 자신의 full-context GPT-4.1 실행 F1 0.197 (MemEval 공식 Full Context 0.222)

공식 MemEval 기준선(README, 커밋 807ae6d7d8a5b76f6fe964d5a581d96c036e2ac4): PropMem 0.550, SimpleMem 0.480, OpenClaw 0.244, Full Context 0.222.

중요한 경계: Lemmalog는 MemEval 공식 게시 표에 없다. 원문은 공식 기준선 수치와 저자 별도 실행을 한 표에 결합한 것이며, 이것은 공식 리더보드 순위가 아니다. "PropMem보다 낮고 SimpleMem보다 약간 낮지만 full-context보다 2배 이상"이라는 원문의 해석은 정확한 비교지만, 표 자체가 공식 발행물이 아니다.

5.2 LoCoMo (저자 실행 vs 공식 기준선)

LoCoMo는 대화 10개, 1,986문항(factual recall, temporal reasoning, multi-hop, inference, adversarial false-premise)이다. 원문 보고(저자 실행 3회):

  • Lemmalog F1 0.533 ± 0.001
  • 최종 범주: Factual 0.399, Temporal 0.454, Multi-hop 0.545, Inferential 0.164, Adversarial 0.707

공식 MemEval 기준선: PropMem 0.605, OpenClaw 0.557, Full Context 0.542, Hindsight 0.489, Graphiti 0.416, Memory-R1 0.389, SimpleMem 0.358.

원문도 명시한다: PropMem이 두 비교 모두에서 전체적으로 여전히 이긴다("PropMem still beats Lemmalog overall on both standardized comparisons"). LoCoMo는 대화 메모리 벤치마크이지 취약점 조사 벤치마크가 아니다. Lemmalog의 약한 결과(Multi-Session 0.211, Inferential 0.164)는 유지되어야 한다.

5.3 스냅샷 경계와 지표 경계

저장소 README는 원문 이후 갱신되어 다른 수치를 보고한다(커밋 22c04ffaee73494eeb4633fa953e3b79bb276004, 2026-09-01): LongMemEval F1 0.487 ± 0.011, LoCoMo 0.573 ± 0.002, 토큰 ~2,300 vs ~104,000 = 45x. 원문의 0.463/0.533/38x와 README의 0.487/0.573/45x는 같은 시점의 측정이 아니므로 동일한 것으로 비교하지 않는다. README 내부에서도 accuracy가 0.566 ± 0.009(표)와 0.585 ± 0.005(요약)로 불일치한다. 토큰 F1과 judge/accuracy는 다른 지표이며, 범주당 17문항은 표본 불확실성이 크다. "세 번의 거의 동일한 실행"은 한 설정 아래의 실행 분산일 뿐, 외부 재현성·분포 이동·통계적 일반화를 증명하지 않는다. 공개 저장소에는 원시 실행별 결과 파일, 정확한 프롬프트, 모델 버전 고정, 비용 로그가 없어 독립 재현을 확인할 수 없다.

6. 토큰 회계: 38배는 응답 맥락이지 총비용이 아니다

원문 수치: LongMemEval full context 약 104,000 vs Lemmalog 약 2,700 토큰/질문(약 38배 적음), LoCoMo 약 18,900 vs 약 3,400(약 6배 적음). 원문 스스로 말한다: "전체 시스템이 단순히 38배 저렴하다고 말하는 것은 정직하지 않다." 추출은 대화당 1회 지불되고, embedding·judge 호출은 제외될 수 있으며, 손익분기점은 질문 수·갱신율·추출/재조정 비용에 달렸다. 지속 에이전트에서 full-context는 질문마다 전체 이력을 다시 읽으므로 차이가 커지고 결국 컨텍스트 윈도에 맞지 않게 된다는 개념적 주장은 타당하지만, 이것은 비용 절감의 증명이 아니라 확장 시나리오다.

7. 프런트엔드 실패 모드 (병목)

저자 자신의 진단이 가장 정확하다: "어려운 부분은 고정점을 계산하는 것이 아니라 자연어에서 좋은 IR을 만드는 것이다."

  • 추출 누락: multi-session 실패의 주원인. "추출기가 에어비앤비 예약 사실을 내지 않으면, 아무리 유도해도 그 질문에 답할 수 없다."
  • 엔터티 재조정: honda_civic / car / civic이 같은 사물로 연결되지 않으면 "엔진은 요청한 대로 정확히 일한다. 불행히도 우리는 서로 다른 세 개의 사물에 대해 추론하라고 요청한 것이다."
  • 시간 정규화: 날짜를 내부 기호 ID로 비교하면 "< 연산자가 날짜가 아니라 ID를 비교"하는 버그. 정수 변환 후 0.257 → 0.454.
  • 집계 누락: "가장 많이 탄 항공사" 질문에 flew(user, swiss, trip_1) 같은 개별 사실만 있고 집계 사실이 없다. 스테머가 4자 이하 단어를 접지 않아 owns/own 불일치로 모든 카운트 줄이 버려진 사건(0.371 거부 사태, 102문항 중 32문항 거부).
  • 조건부 지식의 평탄화: "조용한 식당을 선호하지만 친구와 여행할 때는 활기찬 곳"이 prefers(user, quiet_restaurants) 하나로 압축되면 정보의 절반이 Datalog에 도달하기 전에 사라진다. 조건부 지식은 조건부로 유지되어야 한다.
  • 프롬프트 변화: "근거가 있는 사실로만 답하라"는 지시가 "단일 사실에 답이 없으면 거부"로 해석되어 합성(카운팅) 자체를 금지한 사건.
  • 테스트 세트 반복: 버그 수정으로 오른 점수들(0.226 → 0.463, 0.483 → 0.533)은 유익한 공학 사례지만, 실패 사례를 보고 고친 설정이 테스트 세트 안내 튜닝 없이 깨끗하게 재실행되었는지는 공개 자료로 확인할 수 없다. 결정론적 추론은 인코딩된 사실·규칙의 귀결만 보장하지, 실제 세계 정확성을 보장하지 않는다.

8. 취약점 연구를 위한 실용 평가 계획

원문의 다음 실험("복잡한 취약점 조사를 에이전트에 주고, 분석 상태 유지가 죽은 가설 부활과 관찰 간 관계 환각을 막는지 보는 것")은 아직 실행되지 않았다. 평가 계획은 사전 등록(preregistration), 맹검 held-out 사례, 상태 교정 이벤트, 죽은 가설 부활률(dead-hypothesis resurrection rate), 출처 정밀도·재현율(provenance precision/recall), 조사 성공(발견·재현·이용 단계별), 분석가 시간, 총비용(추출 + embedding + judge + reader)을 측정해야 한다. 대조군은 동일 기간의 full-context/벡터 메모리 세션이다.

9. 반증·갱신 기준과 한계

  • Lemmalog가 "LLM 메모리 문제를 해결했다"고 주장하려면: 외부 연구자가 동일 스냅샷에서 원시 실행 파일·프롬프트·모델 버전으로 재현해야 한다. 현재 공개 저장소에는 그 재현 자산이 없다.
  • 실용 승리는 취약점 조사 자체의 종단 결과(가설 부활률 감소, 조사 시간 단축, 발견 유지)로 판정해야 하며, LongMemEval/LoCoMo F1로 판정해서는 안 된다.
  • 한계: 미지원 추출과 불완전 규칙은 여전히 결론을 만들거나 놓칠 수 있다. Datalog는 환각·진리 유지·취약점 연구·장기 에이전트를 해결하지 않는다. 원문도 "Datalog가 LLM 메모리를 해결했다고 주장하지 않겠다"고 명시한다.

10. 종합

이 에세이는 "기억을 개선하는 것"이 아니라 "우리가 왜 믿는지 잊지 않는 것"이라는 문제를 정확히 지적한다. 유지되는 연역 상태는 검색 메모리의 설득력 있는 보완이며, Knowledge Update 0.579(원문)처럼 유지 상태가 보상되는 범주에서 두드러진 결과가 나온 것은 의미 있다. 그러나 현재 근거는 저자 실행 3회 분산에 불과하고 추출 프런트엔드가 병목이며, 공식 리더보드 순위도 아니다. "때로는 더 큰 컨텍스트 윈도 대신 상태를 유지하면 된다"는 결론은 그 범위 안에서만 타당하다. 취약점 연구에서 실제로 죽은 가설을 되살리지 않는지는 다음 실험의 몫이다.
