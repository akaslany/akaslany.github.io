1. 문서의 성격 및 검증 범위 선언
본 보고서는 독립적인 제3자 평가 기관이나 동료 심사(Peer Review)에 의한 검증 결과가 아니며, 모델 개발사인 구글 딥마인드(Google DeepMind)가 직접 작성하고 공개한 공식 기술 문서인 「EmbeddingGemma 2 model card」 단 1건만을 유일한 절대적 근거(Source of Truth)로 하여 작성된 시스템 연구원 관점의 상세 해설 보고서입니다.

2. 모델 개요 및 핵심 정체성

임베딩젬마 2(EmbeddingGemma 2)는 구글 딥마인드(Google DeepMind)가 개발한 오픈 멀티모달 임베딩 모델로, 텍스트(소프트웨어 코드 포함), 이미지, 비디오, 오디오 및 이들의 복합 조합(Interleaved Inputs)을 단일한 768차원 통합 벡터 공간(Unified Vector Space)으로 매핑하는 네이티브 멀티모달(Native Multimodal) 표현 학습 시스템입니다.

모바일 기기, 노트북 등 사용자용 단말 및 엣지(Edge) 환경에서 최적화되어 동작하도록 설계되었으며, 저전력·저지연 의미론적 표현(Semantic Representation)을 제공하여 온디바이스(On-device) 검색, RAG(검색 증강 생성), 텍스트 및 미디어 분류, 클러스터링 등의 하류(Downstream) 과제를 강력하게 지원합니다.

주요 사양 요약
  • 라이선스: 아파치 2.0 (Apache 2.0)
  • 제작사: 구글 딥마인드 (Google DeepMind)
  • 기반 아키텍처: 젬마 4(Gemma 4) 아키텍처
  • 전체 파라미터 구성: 총 7억 4,000만 개 (740M)
    • 텍스트 백본(Text Backbone): 2억 7,000만 개 (270M) — 트랜스포머 레이어 1억 3,000만 개(130M) + 임베더 1억 4,000만 개(140M)
    • 비전 인코더(Vision Encoder): 1억 7,000만 개 (170M)
    • 오디오 인코더(Audio Encoder): 3억 개 (300M)
  • 멀티모달 설계: 4가지 핵심 모달리티(텍스트, 이미지, 비디오, 오디오)를 별도의 변환 레이어 없이 공유된 768차원 공간에 투영하는 네이티브 멀티모달 구조

3. 핵심 기능 및 기술적 특징

다국어 및 코드 지원 (Multilinguality and Code)

140개 이상의 언어를 아우르는 다국어 표현 능력을 보유하고 있으며, 특히 전작(EmbeddingGemma 1) 대비 코드(Code) 임베딩 및 검색 과제 성능이 약 14% 대폭 향상되었습니다.

유연한 메모리 공간 (Flexible Footprint)

모듈형 인코더 구조로 구현되어 시스템 배포 파이프라인에서 불필요한 인코더를 로드하지 않고 필요한 모달리티만 선택적으로 메모리에 올릴 수 있습니다. 이를 통해 텍스트 전용 시스템 구축 시 모델 메모리 점유 크기를 2억 7,000만 개(270M) 파라미터 수준으로 경량화할 수 있습니다.

마트료시카 표현 학습 (Matryoshka Representation Learning, MRL)

MRL 기법이 적용되어 네이티브 출력인 768차원 벡터의 상위 차원을 절단(Truncation)하여 512차원, 256차원, 128차원으로 정규화 후 축소 사용할 수 있습니다. 표현 품질의 하락을 극도로 제한하면서 벡터 데이터베이스 저장 비용 및 유사도 연산 오버헤드를 최대 6배까지 절감합니다.

넓은 컨텍스트 창 (8K Context Window)

8,192(8K) 토큰의 대용량 컨텍스트 창을 제공하여 수천 단어의 장문 문서나 분 단위 길이의 오디오, 비디오 멀티모달 데이터 스트림을 단일 입력 패스로 처리합니다.

태스크 지시 프리픽스 (Task Instruction Prefixes)

경량 텍스트 지시 프롬프트를 입력 최전단에 결합하여 검색, 질의응답, 분류, 클러스터링 등 과제 특성에 부합하는 최적의 임베딩 표현으로 공간 구조를 조율(Task-steered representation)합니다.

  • 256차원 영역: 256차원까지 절단 시 전체 MTEB 및 멀티모달 점수의 손실이 미미하여 실질적인 무손실(Lossless) 압축 효율을 달성합니다. 벡터 저장소 공간 및 메모리 대역폭을 3배 절감하면서도 프로덕션 환경의 정밀도를 유지할 수 있습니다.

7. 실무 활용 및 구현 지침 (Best Practices)

7.1. 빠른 시작 및 태스크 지시 프리픽스 (Task Instruction Prefixes)

임베딩젬마 2는 입력 텍스트 최전단에 과제별 지시 프리픽스를 결합할 때 최고의 표현 정밀도를 발휘합니다.

  • 적용 범위: 프리픽스는 텍스트 입력에만 적용하며, 이미지, 비디오, 오디오 파이프라인에는 접두사를 결합하지 않습니다.
  • 과제 유형 구분:
    • 비대칭 과제 (Asymmetric Tasks): 질의(Query)와 데이터베이스 코퍼스(Document)의 형식과 의미론적 성격이 다른 과제(예: 웹 검색, 질의응답, 사실 확인, 코드 검색). 질의와 문서에 각각 지정된 전용 프리픽스를 구분하여 부여합니다.
    • 대칭 과제 (Symmetric Tasks): 비교되는 대상들 간의 특성이 동등한 과제(예: 텍스트 분류, 클러스터링, 문장 유사도). 모든 입력에 동일한 프롬프트를 적용합니다.

주의: 문서 제목 서식 및 prompt_name="Document" 동작 메커니즘
제목이 존재하는 문서의 경우 반드시 title: {title} | text: {content} 서식을 수동으로 구성해야 합니다. 제목이 없는 경우 title: none을 지정합니다.
SentenceTransformers 라이브러리에서 prompt_name="Document"를 파라미터로 지정할 경우 내부에 title: none 접두사가 자동으로 결합됩니다. 따라서 제목이 존재하는 문서를 임베딩할 때 자동 프롬프트를 지정하면 제목 정보가 누락되므로, 자동 파라미터를 배제하고 f"title: {title} | text: {document}" 형태로 문자열을 직접 서식화하여 파이프라인에 전달해야 합니다.

과제별 프롬프트 매핑 표
유즈케이스 과제 유형 프롬프트 이름 (Prompt Name) 질의 지시어 (Query Instruction) 문서 지시어 (Document Instruction)
웹/문서 검색 비대칭 SearchQuery task: search result | query: {query} title: {title} | text: {content}
질의응답 비대칭 QuestionAnswering task: question answering | query: {question} title: {title} | text: {passage}
사실 확인 비대칭 FactChecking task: fact checking | query: {claim} title: {title} | text: {evidence}
코드 검색 비대칭 CodeRetrieval task: code retrieval | query: {query} title: {title or filename} | text: {code}
텍스트 분류 대칭 Classification task: classification | query: {content} 해당 없음 (N/A)
클러스터링 대칭 Clustering task: clustering | query: {content} 해당 없음 (N/A)
유사도 측정 대칭 SentenceSimilarity task: sentence similarity | query: {content} 해당 없음 (N/A)
기본 빠른 시작 예제 코드 (Quick Start)
from sentence_transformers import SentenceTransformer

# 모델 로딩
model = SentenceTransformer("google/embeddinggemma-2")

# 검색 질의 및 문서 정의
query = "What causes the northern lights?"
document = "The northern lights are caused by charged particles from the sun."

# 태스크 프리픽스를 적용한 임베딩 생성
query_emb = model.encode(query, prompt_name="SearchQuery")
doc_emb = model.encode(document, prompt_name="Document")

# 코사인 유사도 연산
similarity_score = model.similarity(query_emb, doc_emb)
print(f"Similarity Score: {similarity_score}")
7.2. 선택적 인코더 로딩 (Selective Encoder Loading)

온디바이스 및 모바일 시스템 환경의 메모리 제한을 극복하기 위해, 사용하지 않는 비전/오디오 인코더를 로딩 단계에서 제거할 수 있습니다.

활성화 모달리티 config_kwargs 설정 매개변수 유효 파라미터 크기
텍스트 전용 (Text only) {"vision_config": None, "audio_config": None} 270M
텍스트 및 이미지 (Text and image) {"audio_config": None} 440M
텍스트 및 오디오 (Text and audio) {"vision_config": None} 570M
전체 멀티모달 (Full multimodal) {} 740M
7.3. 벡터 절단 후 L2 재정규화 및 차원 일치 조건

경고: L2 재정규화 생략 시 무오류 정밀도 붕괴 위험
단위 길이를 가진 L2 정규화 벡터의 일부분을 슬라이싱(Truncation)하면 수학적으로 단위 길이가 유지되지 않으므로 L2 Norm이 1에서 벗어나게 됩니다. 벡터 절단 후 코사인 유사도를 연산하기 전에 반드시 L2 재정규화(Re-normalization)를 수행해야 합니다. 재정규화를 생략하면 런타임 오류가 발생하지 않는 대신, 겉보기에 그럴듯하지만 완전히 잘못된 유사도 랭킹 점수(Plausible-looking invalid scores)가 출력되어 시스템 정밀도를 파괴합니다.

또한, 768차원 질의 벡터를 128차원 인덱스 코퍼스에 직접 연산하는 것과 같이 상이한 차원 간의 유사도 비교는 원천적으로 불가능하며, 질의와 코퍼스의 임베딩 차원은 반드시 동일해야 합니다.

MRL 벡터 절단 및 자동 정규화 구현 코드
# MRL 128차원 절단 및 L2 재정규화 동시 수행
query_emb_128 = model.encode(
    query,
    truncate_dim=128,          # 지원 차원: 512, 256, 128
    normalize_embeddings=True  # L2 재정규화 수행 (필수)
)
7.4. 수치 정밀도 및 float16 엄격 금지 (Numerical Precision & Dynamic Range)

경고: float16 연산 엄격 금지 (Do NOT Use float16)
임베딩젬마 2 모델 추론 시 float16 정밀도를 절대 사용하지 마십시오.
구조적 사유: 임베딩젬마 2의 기반인 젬마 4 아키텍처는 내부 트랜스포머 레이어의 활성화 값 범위(Activation Range)가 float16의 표현 한계(최대 약 $65,504$)를 빈번하게 초과합니다. float16으로 추론할 경우 언더플로우/오버플로우가 발생하여, 예외 에러 메시지 출력 없이 NaN 벡터를 반환하거나 임베딩 표현력이 소리 없이 붕괴(Silent degradation)됩니다.

반면 bfloat16은 float32와 동일한 8비트 지수부(Exponent)를 갖고 있어 동일한 동적 범위를 안전하게 표현합니다. GPU 메모리를 float32 대비 절반으로 줄이면서도 연산 안정성을 제공하므로 bfloat16 또는 float32만 사용해야 합니다.

동적 정밀도 설정 및 모델 로딩 코드
import torch
from sentence_transformers import SentenceTransformer

# 하드웨어의 bfloat16 지원 여부를 판별하여 안전한 Precision 동적 선택
dtype = torch.bfloat16 if torch.cuda.is_bf16_supported() else torch.float32

# 안전한 torch_dtype 전달을 통한 모델 인스턴스화
model = SentenceTransformer(
    "google/embeddinggemma-2",
    model_kwargs={"torch_dtype": dtype}
)
7.5. 멀티모달 입력 인터리빙 및 토큰 예산 관리 (Multimodal Interleaving & Vision Budget)

단일 8,192 토큰 컨텍스트 창 안에서 텍스트와 이미지, 비디오, 오디오를 자유롭게 시퀀스로 배치하는 인터리빙(Interleaving)을 지원합니다. 미디어 요소의 위치는 플레이스홀더 토큰(<|image|>, <|video|>, <|audio|>)을 텍스트 내에 배치하여 매핑합니다.

멀티모달 인터리빙 구현 코드
# 텍스트, 이미지, 비디오가 혼합된 인터리빙 데이터 임베딩 생성
emb_interleaved = model.encode({
    "text": "Waterproof running shoes. <|image|> Featuring a breathable mesh upper. <|image|> Grip test on wet rock: <|video|>",
    "image": ["shoe.jpg", "mesh.jpg"],
    "video": "demo.mp4",
})
모달리티별 컨텍스트 토큰 소모 비용 및 입력 한계
모달리티 토큰 소모 비용 (Token Cost) 최대 입력 한계 (단일 모달리티 전용 기준)
텍스트 서브워드당 1 토큰 8,192 토큰
이미지 기본 이미지당 280 토큰 약 29장 (기본 설정 시)
비디오 기본 프레임당 140 토큰 약 58 프레임 (기본 설정 시)
오디오 초당 25 토큰 약 327 초
비전 토큰 예산(Vision Token Budget) 메커니즘

이미지 및 비디오 프레임당 생성되는 소프트 토큰(Soft token)의 수량을 기본 280/140개에서 70개부터 1,120개 범위로 엔지니어링 목적에 맞게 조정할 수 있습니다.

  • 고예산 설정 (Up to 1,120 tokens): 시각적 정밀도를 극대화하여 세밀한 이미지/문서 그래픽 인식 능력을 향상시키지만, 메모리 점유율과 컴퓨팅 지연시간(Latency)이 증가합니다.
  • 저예산 설정 (70 tokens): 개별 시각 해상도 표현력은 다소 감소하지만, 토큰 소모량을 최소화하여 8K 컨텍스트 창 내에 최대 114장의 이미지 또는 비디오 프레임을 동시에 입력받을 수 있도록 확장성을 제공합니다.
7.6. 입력 샘플링 기본값
  • 비디오 샘플링: 비전 인코더를 통과하는 비디오는 기본 초당 1프레임(1 FPS)으로 샘플링되며, FPS 비율은 애플리케이션 요구사항에 맞춰 수정 가능합니다.
  • 오디오 샘플링: 오디오 인코더 파이프라인에는 16 kHz 모노(mono) 음원을 기본 형식으로 공급해야 합니다.

8. 학습 데이터 및 데이터 전처리

학습 데이터 구성
  • 컷오프 시점: 2025년 1월
  • 언어 범위: 140개 이상의 자연어 언어 포함
  • 데이터 유형: 웹 문서, 오픈소스 코드 코퍼스, 이미지, 비디오, 오디오 데이터 세트 및 모달리티 간 공간 정렬을 위한 교차 모달리티 교차 샘플(Cross-modality samples)
데이터 전처리 및 정제
  • CSAM 정밀 필터링: 파이프라인 전반에서 다단계 알고리즘을 적용해 아동 성 학대 소재(CSAM)를 완전히 검출 및 삭제.
  • 개인정보 및 민감 정보 필터링: 개인 식별 정보(PII) 및 기타 민감 데이터를 자동화된 정제 기법으로 사전 제거.
  • 안전성 및 품질 정제: 구글의 AI 원칙(AI Principles) 및 내부 책임 정책에 부합하는 정밀 컨텐츠 품질 필터링 적용.

9. 안전성, 윤리적 고려사항 및 하류 위험 완화책

사후 정렬 및 안전 튜닝 부재

임베딩 모델은 문장을 생성하는 생성형 모델과 달리 사후 학습 정렬(Post-training alignment), RLHF, 안전 튜닝, 출력 수준 모더레이션 레이어가 존재하지 않습니다. 따라서 안전성 관리는 사전 학습 데이터 단계에서의 필터링에 집중되어 있습니다.

위험의 주체 및 하류 애플리케이션 책임

임베딩 모델은 고차원 표현 벡터만 출력하므로 실제 윤리적·기술적 위험은 해당 임베딩을 이용하는 하류(Downstream) 애플리케이션 구축 단계에서 발생합니다. 따라서 시스템 개발자 및 배포자는 구글의 'Gemma 금지된 사용 정책(Prohibited Use Policy)'을 준수해야 하며, 검색 필터링, 편향성 검증, 공정성 테스트 등 애플리케이션 차원의 안전장치를 직접 구현해야 합니다.

식별된 위험 요소 및 완화책
  • 악의적 오용 (Misuse): 오용 방지를 위해 책임감 있는 AI 개발 툴킷(Responsible GenAI Toolkit) 및 개발자 교육 문서, 오용 신고 메커니즘을 제공.
  • 개인정보 침해 (Privacy Violations): 데이터셋 단계에서의 PII 제거 및 하류 개발자의 차분 프라이버시(Differential Privacy) 등 개인정보 보호 기술 준수를 권고.
  • 편향 지속 (Perpetuation of Biases): 대규모 실제 데이터셋에 잠재된 사회문화적 편향이 벡터 공간에 내재될 수 있으므로, 하류 시스템 구축 시 지속적인 편향 모니터링 및 편향 제거(De-biasing) 기법 적용을 권장.

10. 의도된 사용 사례 및 기술적 한계

의도된 사용 사례 (Intended Usage)
  • 검색 (Retrieval): 텍스트, 코드, 이미지, 비디오, 오디오 전반에 걸친 의미론적 검색, 엔터프라이즈 지식베이스 대상 RAG, 음성 코퍼스 기반 검색.
  • 분류 (Classification): 입력 데이터의 사전 정의 레이블 분류 (감성 분석, 콘텐츠 모더레이션, 오디오 이벤트 감지, 이미지 카테고리화).
  • 클러스터링 (Clustering): 의미론적 유사도 기반의 데이터 그룹화, 고객 피드백 주제별 클러스터링, 교차 모달리티 중복 콘텐츠 감지.
  • 의미론적 유사도 (Semantic Similarity): 임베딩 간 거리 측정을 통한 추천 시스템, 패러프레이즈 식별, 다국어 콘텐츠 정렬.
  • 사실 검증 (Fact Verification): 명제/주장에 대한 증거 문서를 검색 및 추출하는 자동화된 사실 확인 시스템.
기술적 한계 (Limitations)
  1. 학습 데이터 범위 및 편향: 100개 이상의 언어를 지원하나 언어 및 문화권별 임베딩 표현의 정밀도가 완전하게 동일하지 않을 수 있습니다.
  2. 복잡한 개방형 과제: 프롬프트나 지시어가 명확하지 않은 개방형(Open-ended) 과제 및 극도로 복잡한 비구조적 수식/논리 처리 시 표현 능력이 하락할 수 있습니다.
  3. 언어적 미묘함과 은유: 자연어의 은유, 풍자(Sarcasm), 비유적 표현 및 미묘한 문맥 차이를 완벽히 공간상에 분리하지 못할 위험이 존재합니다.
  4. 프리픽스 누락 시 성능 하락: 텍스트 과제 수행 시 권장 태스크 프리픽스를 누락하면 의미론적 공간 조율이 실패하여 검색 정밀도가 저하됩니다.
