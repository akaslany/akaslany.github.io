What Is DeepSeek Super-agent Design and How Does It Work?

1. 개요 (Overview)

단일 세션(Single Session) 기반 에이전트는 단일 작업의 자동화 영역에서 유의미한 성과를 거두었으나, 복수의 과업을 동시에 처리하는 다중 작업 환경에서는 구조적 아키텍처 한계에 직면한다. 한 사람이 인지적 부담 없이 동시에 추적할 수 있는 활성 세션의 수가 제한적(약 3개~5개)이기 때문에, 사용자가 세션 간 맥락을 직접 전달하고 작업을 전환해야 하는 '인간의 주의력 병목'이 발생한다. 또한 기존의 단일 세션 구조는 동기식 차단(Synchronous Blocking) 실행 방식으로 인해 백그라운드 도구 연산 도중 사용자 대화 입력이 차단되고, 세션 간 맥락이 파편화되어 단절되며, 개발자의 로컬 기기가 오프라인이 되면 시스템 전체의 작동이 즉시 중지되는 고질적 문제를 안고 있다. 이러한 단일 세션의 한계를 극복하고 차세대 에이전트 시스템을 구축하기 위해 제안된 아키텍처 개념이 바로 '슈퍼 에이전트(Super-agent)'이다. [위치: Section 1]

슈퍼 에이전트는 단일 세션에 갇힌 에이전트 루프를 해제하고, 다중 세션과 다양한 도구 및 실행 환경에 걸쳐 맥락과 과업을 영속적으로 유지·선동하는 시스템 차원의 아키텍처 접근법이다. 딥시크 하네스 팀(DeepSeek Harness Team)은 슈퍼 에이전트의 4가지 핵심 특성으로 연속성(Continuity), 효율성(Efficiency), 능동성(Proactivity), 영속성(Persistence)을 제시한다. 이는 사용자가 개별 세션의 존재를 인식하지 않고 단일 에이전트와 지속 소통하는 듯한 맥락 연속성을 제공하고, 다수의 복잡한 과업을 병렬로 고속 처리하며, 환경 이벤트를 상시 감시하여 명시적 프롬프트 없이도 능동적으로 개입하고, 클라우드 연산 및 자동 복구 메커니즘을 통해 기기 상태와 무관하게 24시간 끊김 없는 영속적 가용성을 보장하는 것을 목표로 한다. [위치: Section 1]

본 보고서는 기존 딥시크(DeepSeek) 상용 제품의 기능 발표나 서비스 출시 안내가 아니며, 딥시크 하네스 팀이 내부 시스템 아키텍처 관점에서 연구·제안하고 프로토타입(dsh-superagent-prototype)을 통해 기술적 가능성을 실증한 아티클 내용을 엔지니어링 분석 전문가의 시각에서 체계적으로 정리·해설한 기술 문서이다. [위치: What Is DeepSeek Super Agent?, Section 9]

2. 주요 논점 (Key Arguments & Technical Details)
2.1. 2계층 아키텍처 (A Two-Layer Architecture)
  • 논점: [사실] 단일 세션 기반의 맥락 연속성 유지와 다중 세션 기반의 다중 작업 처리량(Throughput) 간 교환 관계(Trade-off)를 해결하기 위해, 시스템 제어 노드인 라우터(Router) 계층과 실무 실행 노드인 워커(Worker) 계층을 완전히 분리한 2계층 아키텍처를 도입한다. [위치: Section 2]
  • 근거 및 세부 요소:
    • 라우터 계층 (Router Layer): [사실] 모든 채널의 인간 상호작용 및 전역 조정을 전담하는 영속적 글로벌 노드이다. 처리량 병목을 방지하기 위해 가벼운 언어 모델을 사용하며, Bash와 같은 고비용 도구를 직접 실행하지 않고 오직 작업 할당과 인터랙션만 전담한다. 외부 이벤트가 몰릴 경우 여러 트리가(Trigger)를 다음 추론 라운드에 자동으로 포함시키는 배치 처리(Batching)를 수행한다. [위치: Section 2.1]
    • 에이전트 팀(Agent Team)과의 비교: [사실] 전통적인 에이전트 팀의 '팀 리드(Team Lead)'는 단일 복잡 작업의 세부 단계를 직접 분해하고 조율해야 하므로 높은 추론 부담을 지는 반면, 슈퍼 에이전트의 라우터 계층은 작업 간의 고차원 관계와 할당만 담당하고 하위 작업 분해를 직접 수행하지 않으므로 경량화된 모델로도 고성능 처리가 가능하다. [위치: Section 2.1]
    • 워커 계층 (Worker Layer): [사실] 독립된 컨텍스트 환경에서 고성능 대형 언어 모델과 전체 도구 세트를 사용하여 부여된 작업을 실행한다. 인간 사용자 및 외부 채널과 직접 대화하지 않고, 수행 경과와 결과만을 라우터 계층에 보고함으로써 독립적이고 안전하게 고도화된 작업을 병렬 처리한다. [위치: Section 2.2]
  • 소스 주장 및 작성자 해석: [소스 주장] 사용자가 세션을 직접 관리하도록 강제하는 것은 언어 모델 API의 구체적 구현 형태가 사용자 경험으로 전파된 탓이며, 제품 경험과 기술적 세션을 아키텍처 차원에서 탈구착해야 한다. [작성자 해석] 컴퓨터 시스템의 전역 라우터-작업 노드 분리 구조를 이식한 것으로, 라우터가 작업 세부사항을 직접 추론하지 않도록 절연함으로써 시스템 전체의 동시 처리 능력을 극대화하는 아키텍처적 장치를 제공한다. [위치: Section 2, Section 2.1]
2.2. 이벤트 기반 작동 방식 (Event-Driven Operation)
  • 논점: [사실] 에이전트의 구동 방식을 수동적인 프롬프트 입력 중심에서 환경에서 발생하는 반구조화된 이벤트인 '트리가(Triggers)' 중심의 능동적 이벤트 기반 아키텍처로 전환한다. [위치: Section 3]
  • 세부 구성 요소를 통한 설명:
    1. 이벤트 필터링 (Event Filtering): [사실] 고비용인 대형 언어 모델의 추론 부담을 줄이기 위해 컴퓨터 시스템의 Fast Path / Slow Path 개념을 이식한다. 1단계 Fast Path(확정적 코드 규칙 정책)는 이벤트 출처, 그룹 범위, 화이트리스트 등의 조건으로 노이즈 메시지를 사전 제거하며, 2단계 Slow Path(LLM 기반 의미론적 정책)는 프롬프트 정책에 따라 의미 파악이 필요한 이벤트만 모델에 전달하여 판단한다. [위치: Section 3.1]
    2. 이벤트 라우팅 (Event Routing): [사실] 스레드(Thread) 구독 메커니즘을 도입한다. 작업 소유권이 확정된 후 스레드 내 발생하는 후속 이벤트는 라우터를 거치지 않고 구독 중인 워커 세션으로 직접 전송(Direct Delivery)되는 Fast Path를 거침으로써 전역 라우터 노드의 부하를 차단한다. [위치: Section 3.2]
    3. 컨텍스트 조직화 (Context Organization): [사실] 제한된 컨텍스트 윈도우를 효율적으로 활용하기 위해 인라인 및 스필(Inline & Spill) 방식과 참조 그래프 기반 소환 사슬(Chain of Recall)을 사용한다. 자주 쓰이거나 임박한 정보는 인라인으로 프롬프트에 포함시키고, 대용량 정보는 스필(외부 저장) 처리한 후 고유 ID 기반 참조 사슬을 따라 필요 시 다중 홉(Multi-hop) 추적으로 소환한다. [위치: Section 3.3]
    4. 사전 행동 (Acting in Advance): [사실] 투기적 실행(Speculative Execution) 기법을 도입하여 환경 신호에 따라 백그라운드에서 사전에 작업을 수행한다. 딥시크 하네스 팀 내부 유저 그룹에 적용된 '무음 버그 재현 및 수정(Silently reproduce and fix)' 정책의 경우, 대화방에서 문제 제보 발생 시 에이전트가 백그라운드에서 재현 및 수정 검증을 우선 진행하고 확정된 수정 PR 작성이 가능할 때만 결과를 노출하며 실패 시 묵묵히 침묵을 유지하여 인간의 주의력을 방해하지 않는다. [위치: Section 3.4]
  • 소스 주장 및 작성자 해석: [소스 주장] 컨텍스트 윈도우 낭비는 모델의 지능을 낭비하는 것과 같으므로 시스템 차원의 맥락 캐싱 기법이 필수적이다. [작성자 해석] CPU 캐시 메모리 구조(Fast Path/Slow Path, Inline & Spill) 및 CPU 투기적 명령 실행 사상을 LLM 에이전트 실행 환경에 완벽히 대치시켜 적용한 엔지니어링 통찰이다. [위치: Section 3.1, Section 3.3, Section 3.4]
2.3. 인간 중심 상호작용 (Human-Centered Interaction)
  • 논점: [사실] 동기식 차단을 해제하여 전경 대화와 백그라운드 작업 수행을 분리하고, 소통 채널의 특성에 맞게 입출력 밀도를 최적화한다. [위치: Section 4]
  • 근거 및 세부 요소:
    • 전두강(Full-Duplex) 상호작용: [사실] 기존의 동기식 run() 호출 구조를 비동기식 start() 및 stop() 연산으로 대체한다. 모델이 start()를 실행하면 시스템은 즉시 시작 완료 신호를 반환하여 대화 루프를 차단 해제하며, 백그라운드 도구 실행이 완료되면 별도 이벤트로 결과를 수신한다. 실행이 장기화되면 stop()을 호출하여 제어할 수 있다. [위치: Section 4.1]
    • 채널별 상호작용 맞춤화: [사실] 인스턴트 메시징(IM) 채널에는 가벼운 결론 위주의 100단어 이내 응답 규칙을 적용하고, GitHub, 이메일, 문서 등 비동기 채널에는 변경 사항 및 검증 결과를 담은 고밀도 구조화 정보를 제공하도록 프롬프트를 차별화한다. [위치: Section 4.2]
  • 소스 주장 및 작성자 해석: [소스 주장] 모든 상세 추론 과정과 도구 호출 기록을 그룹 대화방에 그대로 노출하는 것은 협업을 방해하므로 라우터 계층을 통한 채널별 양식 가공이 필요하다. [작성자 해석] 대화형 UI의 사용자 경험과 긴 시간이 소요되는 실제 도구 실행 간의 시간적 비대칭성을 비동기 사건 처리 방식으로 해소한 아키텍처이다. [위치: Section 4.1, Section 4.2]
2.4. 연산, 상태, 실행 환경의 분리 (Separating Compute, State, and Environments)
  • 논점: [사실] 로컬 기기 의존성을 탈피하고 오프라인 상태에서도 영속 구동이 가능하도록 연산, 상태, 실행 환경을 2단계로 탈구착(Decoupling)한다. [위치: Section 5]
  • 근거 및 세부 요소:
    • 1단계 (연산과 상태의 분리): [사실] 에이전트 루프를 추진하는 연산(Compute) 노드를 클라우드의 상태 없는(Stateless) 탄력적 컨테이너로 구성하고, 세션 이력 및 맥락 등 상태(State) 데이터는 영속적 DB에 저장한다. 이를 통해 컨테이너 재스타트나 장애 시에도 작업 연속성을 유지한다. [위치: Section 5.1]
    • 2단계 (연산과 실행 환경의 분리): [사실] 클라우드 에이전트 루프와 무거운 상태를 갖는 실재 실행 환경(코드 베이스, 툴체인, 로컬 자격 증명 등)을 분리한다. 사용자 기기 측에는 상태가 없는 경량 데몬(Daemon)을 설치하여 클라우드 요청 시 로컬 명령을 실행한다. 사용자의 로컬 기기가 간헐적 네트워크 연결(Intermittent Connectivity) 상태에 있어 접속이 끊기더라도, 기기가 다시 온라인이 되면 클라우드 에이전트 루프가 대기 중이던 작업을 자동으로 트리거하여 완수한다. 이를 통해 BYOM(Bring Your Own Machine) 환경과 클라우드 온디맨드 인프라를 동시 지원한다. [위치: Section 5.2]
  • 소스 주장 및 작성자 해석: [소스 주장] 실재 작업 환경을 클라우드 샌드박스로 완벽히 복제·동기화하는 것은 불가능에 가까우므로 '뇌(Brain)와 손(Hands)을 분리'해야 한다. [작성자 해석] 앤스로픽(Anthropic)의 샌드박스 접근 방식이 VPC 내부 자원에 주로 집중된 반면, 본 아키텍처는 개발자의 개인 단말 기기 및 간헐적 접속 환경까지 포괄하는 확장된 분산 시스템 설계를 보여준다. [위치: Section 5.2]
2.5. 독립적 외부 제어 루프: 와치독 (Watchdog)
  • 논점: [사실] 장기간 지속 작동하는 시스템의 이상 상태 감지 및 자동 복구를 위해 메인 시스템 외부에서 독립적으로 작동하는 제어 루프 모듈인 와치독(Watchdog)을 배치한다. [위치: Section 6]
  • 근거 및 세부 요소:
    • 작업 진행성 및 목표 이탈 검증: [사실] 단순 하드웨어/OS 차원의 프로세스 생존성 검사(Liveness Probe)를 넘어, LLM 기반 모델 평가를 통해 워커 세션이 무의미한 루프에 빠져 있는지, 전체 작업 목표에서 실질적으로 이탈(Goal Drift)했는지를 검증한다. [위치: Section 6]

2.6. 예비 실험 결과 분석 (Preliminary Experiments)
  • 논점: [사실] 프로토타입 기반 모의 워크로드(Synthetic Workloads) 실험을 통해 슈퍼 에이전트 아키텍처의 효용성과 라우터 배치 처리 메커니즘을 입증한다. [위치: Section 7]
  • 근거 및 세부 요소:
    • 소멸 연구 (Ablation Study): [사실] 약 300개의 메시지(작업 요청 20개 포함) 스트림 환경에서 5회 반복 실험을 수행했다. 슈퍼 에이전트는 작업 완료 시간 p50 12.4분, p95 15.7분을 기록했다. 대조군인 단일 세션 방식 중 '중립 프롬프트(Neutral Prompt)' 조건에서는 모델이 5회 모두 서브에이전트를 호출하지 않고 직접 처리하다 작업이 계속 중단되어 p95가 29.5분에 달했다. '위임 우선 프롬프트(Delegation-first Prompt)' 조건에서는 5회 중 4회는 위임에 성공하여 소요 시간을 단축했으나, 1회 실험에서 작업을 '소규모'로 오판하여 직접 실행하다 롱테일(Long Tail) 지연이 발생했다. 또한 스레드 직송(Direct Delivery) 메커니즘을 제거할 경우 라우터 결정 횟수가 약 30% 증가하고 캐시 읽기 토큰 소비량이 2,323만 개에서 3,177만 개로 약 37% 증가했다. [위치: Section 7.1]
    • 라우터 배치 처리 (Batching): [사실] 라우터 세션의 트리가 도착률을 분당 1개에서 분당 40개로 늘리는 스트레스 테스트를 수행한 결과, 평균 배치 크기가 1.0에서 2.8로 증가했다. 이때 단일 요청 지연시간은 2.5초에서 3.9초로 완만하게 증가하여, 결정 1건당 상각 추론 시간이 6.4초에서 1.6초로 대폭 감소했다. [위치: Section 7.2]
  • 소스 주장 및 작성자 해석: [소스 주장] 프롬프트 엔지니어링에만 의존하는 방식과 달리 2계층 아키텍처는 시스템 차원에서 작업 위임을 구조적으로 강제하여 성능 안정성을 보장하며, 스레드 직송 및 배치 처리를 통해 단일 라우터 세션만으로도 팀 규모의 처리량을 병목 없이 감당할 수 있다. [작성자 해석] 확률적인 프롬프트 지시보다 아키텍처적 제약조건 부여가 시스템 안정성에 결정적이며, LLM 추론의 Prefill 연산 병렬화 특성을 고려한 시스템 최적화가 유의미한 비용/속도 이점을 제공함을 실증한다. [위치: Section 7.1, Section 7.2]

5. 한계와 불확실성 (Limitations & Uncertainties)
  1. 제품화 여부의 한계: 본 보고서의 내용은 기존 딥시크(DeepSeek) 상용 제품의 서비스 기능 발표가 아니며, 공개된 dsh-superagent-prototype 플러그인 역시 기술적 컨셉 검증을 위해 제공된 프로토타입일 뿐 공식 제품이 아니다. [위치: What Is DeepSeek Super Agent?, Section 9]
  2. 실험 환경의 한계: 소스 7장에 제시된 성과 측정 데이터는 실제 고난도 코딩 작업 대신 시간만 소모하는 모의(Mock) 도구와 합성 워크로드(Synthetic Workloads)를 사용한 예비 실험 결과이므로 실측 운영 환경에서의 결과와 차이가 발생할 수 있다. [위치: Section 7]
  3. 장기 기억 장치의 미비: 수개월 이상 장기간 시스템을 영속 운용할 때 필연적으로 발생하는 장기 기억(Long-term memory) 병목 문제에 대한 명확한 아키텍처적 해법이나 메모리 동기화 기술은 소스에서 제시되지 않았다. [위치: Section 8.1]
  4. 보안 및 자격 증명 위험: 클라우드의 에이전트 루프가 프롬프트 주입 공격 등으로 탈취될 경우 연결된 로컬 단말 기기가 전면 점거될 수 있는 보안 위협이 존재하며, 자격 증명(Credentials)의 프롬프트 직접 노출을 완전 차단하는 구체적 구현 수단은 미해결 과제로 남아있다. [위치: Section 8.4]
  5. 확인 불가 항목: 라우터 세션을 복수의 샤드(Shard)로 분할(Sharding)할 때 적용되는 세부 샤딩 알고리즘, 분산 샤드 간 컨텍스트 동기화 규칙, 및 자격 증명 무접촉 대리 호출의 구체적 프로토콜은 소스 문맥을 통해 확인할 수 없다. [위치: Section 2.1, Section 8.1, Section 8.4]
