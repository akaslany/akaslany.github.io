Archify 기술 심층 보고서 (고정 커밋: 0853a805003514776bef3593ecca091409828902)

본 보고서는 tt-a1i/archify 저장소의 특정 커밋 상태(0853a80)를 대상으로 수행된 기술 감사 결과입니다. 수석 기술 감사관의 관점에서 시스템의 아키텍처 명세 방식, 검증 메커니즘의 무결성, 그리고 도구가 보장하는 기술적 사실의 한계를 엄격히 규명합니다.

1. 제품 정의 및 운영 경계 (Product Boundary)

Archify는 소스 코드로부터 아키텍처를 추출하는 ‘자동 발견(Discovery) 엔진’이 아닙니다. 이 시스템은 외부 인텔리전스와 기계적 검증기 사이의 엄격한 역할 분리를 운영 전제로 합니다.

  • 에이전트와 도구의 분리: Cursor, Claude Code, Codex CLI, OpenCode 등 외부 코딩 에이전트가 소스 코드를 해석하여 시스템의 의미와 토폴로지를 담은 **제한된 JSON IR(Intermediate Representation)**을 작성합니다. Archify는 이 authored IR을 입력받아 후속 공정을 수행합니다.
  • 핵심 기능 정의: Archify는 작성된 IR을 스키마, 기하학적 제약, 소스 코드 근거(Evidence) 관점에서 검증하고 렌더링/패키징하는 다이어그램 컴파일러이자 증거 검증기입니다.
  • 운영 경계: 본 도구는 ‘AI가 이해했다고 주장하는 내용’을 기계적 규칙으로 통제하고 시각적 산출물로 변환하는 데 국한되며, 코드베이스의 의미를 스스로 판단하지 않습니다.
2. 다섯 가지 다이어그램 타입의 스키마와 의미론 (Schema & Semantics)

Archify는 모든 그래프를 단일 모델로 처리하지 않고, 목적에 따라 설계된 다섯 가지 독립적 문법을 제공합니다. 모든 스키마는 schema_version: 1을 따르며 common.schema.json을 통해 공통 정의를 관리합니다.

  • Architecture: 서비스, 데이터베이스, 보안/지역 경계(Boundaries) 및 구성요소(Components) 간의 물리적/논리적 연결과 기술적 근거를 정의합니다.
  • Workflow: 레인(Lanes)과 노드(Nodes)를 통해 작업 흐름, 분기, 오류 경로 및 역할별 책임을 명시합니다.
  • Sequence: 참여자(Participants) 간의 시간 순 메시지(Messages) 교환과 활성화 상태를 표현합니다.
  • Dataflow: 데이터가 단계(Stages)를 거치며 변환되는 이동 경로와 데이터 자산의 분류를 다룹니다.
  • Lifecycle: 객체나 서비스의 상태(States) 전이(Transitions)를 레인별로 관리합니다.

엄격성 정책: 모든 스키마는 additionalProperties: false를 적용하여 에이전트가 스키마에 정의되지 않은 필드를 생성하는 ‘문법적 환각’을 원천적으로 차단합니다.

3. 제약된 레이아웃 문법 및 진단 시스템 (Layout Grammar & Diagnostics)

Archify는 정보 전달의 무결성을 위해 미학적 자유도 대신 기계적으로 검증 가능한 ‘제약된 문법(Bounded Grammar)’을 채택합니다.

  • 기하학적 검증 규칙 (geometry.mjs):
    • Crossing/Corridor: 불필요한 선 교차와 동일 통로 내 선 겹침을 감지하여 시각적 모호성을 제거합니다.
    • Route Rhythm/Port Spread: 경로 굴곡의 일관성과 연결 포트 배치의 균등성을 검사합니다.
    • Border/Label Clearance: 컨테이너 경계와 텍스트 라벨 간의 최소 여백을 강제합니다.
  • 진단 메커니즘: validator.mjs는 입력된 IR이 '기계적 정확성(Mechanical Correctness)'을 만족하는지 진단합니다. 이는 레이아웃 취향(Layout Taste)의 문제가 아니라, 정보의 왜곡 없는 전달을 위한 물리적 제약 사항입니다.
  • 규모의 제한: 본 시스템은 대규모 그래프 배치를 위한 범용 엔진이 아닙니다. 가독성을 위해 주요 노드를 12개 이내로 유지하도록 권장하는 설계 한계(Product Boundary)를 가집니다.
4. 아키텍처 증거(Evidence)와 의미론적 무결성 구분

Archify는 다이어그램의 요소가 실제 소스 코드에 기인했음을 증명하는 참조 무결성 기능을 포함합니다.

  • 참조 무결성 검증 (repository-evidence.mjs):
    • 40자리 16진수 Git 커밋 객체 ID(감사한 저장소에서는 SHA-1 형식)와 정규화된 GitHub HTTPS URL의 정합성을 확인합니다.
    • git cat-file 등을 통해 지정된 파일과 줄 번호 범위(Line range)가 해당 리비전에 실제 존재하는지 물리적으로 검사하고 Receipt를 생성합니다.
  • 기술적 사실과 진실의 구분 (핵심 감사 포인트):
    • Schema-valid vs. Architecture Truth: 스키마와 기하 규칙을 통과했다고 해서 실제 시스템의 서비스가 누락되지 않았거나 관계가 정확함을 보장하지 않습니다.
    • Referential Integrity vs. Semantic Proof: repository-evidence.mjs는 파일의 '존재'를 증명할 뿐, 해당 코드가 다이어그램의 주장을 논리적으로 뒷받침하는지는 증명하지 못합니다. (예: 에이전트가 관련 없는 설정 파일을 근거로 연결해도 물리적 존재가 확인되면 검증을 통과함)
    • Deterministic Output vs. Semantic Correctness: 동일 입력에 대해 항상 일정한 렌더링 결과가 보장되나, 이는 모델의 의미론적 정확성과 무관합니다.
5. Architecture Delta 및 변경 관리

delta/architecture-delta.mjs를 통해 두 아키텍처 스냅샷 간의 구조적 차이를 분석합니다.

  • 모델 기반 비교: 단순 텍스트 diff가 아닌, 안정적인 ID를 기반으로 컴포넌트, 연결, 경계의 추가/삭제/이동 및 증거(Evidence) 변화를 분류합니다.
  • 판단 보류 원칙: Archify는 Delta 분석 결과에 대해 SAFE, LOW RISK, MERGEABLE 등 위험도를 단정하는 용어를 의도적으로 사용하지 않습니다. 이는 시스템이 변경의 의미론적 위험이나 병합 안전성을 판정할 능력이 없음을 명시적으로 인정하는 설계 철학입니다.
6. 결정론적 렌더링과 대화형 뷰어 (Rendering & Viewer)
  • 출력 형식: PNG, JPEG, WebP, SVG와 영상 형식인 WebM 출력을 지원합니다.
  • 뷰어 주요 기능: 정적 HTML 뷰어는 검색, Passport(노드 역할 및 근거 확인), Reachability(그래프 내 도달 가능성), Route Probe(최단 경로 탐색), Guided Story 기능을 제공합니다.
  • 운영 관점: 본 뷰어는 실시간 협업이나 런타임 관측성(Observability) 도구가 아니며, 특정 시점의 아키텍처를 고정하여 전달하는 '정적 상호작용 문서'입니다.
7. 원자적 전달 및 안전 장치 (Delivery & Preservation)

commandDeliver() 로직은 산출물 배포의 신뢰성을 위해 다음의 원자적 단계를 거칩니다.

  1. Staging Cleanup: 임시 스테이징 영역을 정리하여 이전 작업의 간섭을 차단합니다.
  2. Candidate Validation: 스테이징 영역에서 모든 검증 및 렌더링을 마칩니다.
  3. Receipt Generation: 스펙과 결과물의 SHA-256 해시를 기반으로 영수증을 생성합니다.
  4. Filesystem Rename: 모든 검증이 성공했을 때만 원자적인 rename 방식을 통해 최종 산출물을 교체합니다.
  5. Last-good Preservation: 작업 실패 시 기존의 정상 산출물을 보존합니다. 이는 문서의 가용성을 위한 장치이며, 시스템 전체의 배포 롤백이나 보안을 보장하는 장치는 아닙니다.
8. 구현 상태 및 신뢰 수준 분류 (Evidence Classes)

본 감사는 다음의 환경에서 실행된 결과를 바탕으로 합니다: Linux, Node v22.22.2, npm 10.9.7, Chrome(/usr/bin/google-chrome).

  • 1. Implemented + Locally Tested: 고정 트리 코드 기반. 750개 테스트 중 746개 통과(남은 4개는 특정 환경 계약에 따른 Skip).
  • 2. Inspection Only: 실행 경로가 확인되었으나 로컬 테스트에서 직접 구동되지 않은 일부 Export 세부 경로.
  • 3. Documented Intention: DESIGN.md 및 SKILL.md에서 규정한 에이전트 협업 규범.
  • 4. Upstream CI: GitHub Actions를 통한 Node 18~24 및 다중 OS(Ubuntu, macOS, Windows) 패키지 스모크 테스트 성공 보고.
  • 5. Roadmap: ROADMAP.md에 기재된 미구현 계획.
  • 6. ChatGPT Interpretation: 제공된 2차 분석 및 비교 데이터.
  • 7. Unsupported/Overstated: 자동 아키텍처 발견, 런타임 진실 보장, 실제 장애 전파(Blast Radius) 분석 등은 지원하지 않음이 확인되었습니다.
9. 도구 간 비교 분석 (Benchmark 축)
  • vs. Mermaid: Mermaid는 간결한 텍스트 기반 다이어그램에 집중하나, Archify는 타입화된 IR, 엄격한 진단, 소스 근거에 집중합니다. 특히 Archify는 Mermaid를 직접 파싱하지 않고 에이전트의 **'의미적 재해석(Semantic Reinterpretation)'**을 통해 IR을 새로 생성합니다.
  • vs. PlantUML/Graphviz: 범용 다이어그램 및 그래프 엔진과 달리, Archify는 아키텍처 가독성을 위해 의도적으로 제한된 문법과 기하학적 규칙을 적용합니다.
  • vs. Structurizr: C4 모델과 유사한 지향점을 가지나, Archify는 외부 AI 에이전트가 작성한 JSON IR의 검증과 패키징된 정적 산출물 전달에 최적화되어 있습니다.

활용, 실패 모드, 비교 기준

설계 리뷰·온보딩·변경 전후 authored snapshot 비교·evidence-bound 정적 문서 배포에 유용하다. 실패 모드는 agent omission/misread, schema-valid but semantically wrong model, evidence와 실제 의미의 불일치, 큰 graph의 readability 한계, Delta와 runtime blast radius의 혼동이다. Mermaid·PlantUML·Graphviz·Structurizr·manual diagram은 notation, 생태계, 범용 layout, model-as-code, 자유도에서 서로 다른 trade-off가 있다. 동일 조건 benchmark가 없으므로 Archify의 보편적 우월성을 주장하지 않는다.
