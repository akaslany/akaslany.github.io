원문

FreeToken: GPU 한 장으로 753B를 돌리는 로컬 MoE의 조건

1. 개요 (Executive Summary)

FreeToken은 로컬 환경에서 프론티어 급 Mixture-of-Experts(MoE) 모델을 효율적으로 실행하기 위해 설계된 엣지 네이티브(Edge-native) 서빙 시스템이다. 이 시스템은 개인용 컴퓨터를 단순히 '작은 GPU가 달린 장치'가 아니라 GPU, CPU, 호스트 DRAM, 그리고 PCIe 인터커넥트가 통합된 신축성 있는 추론 플랫폼으로 취급한다.

FreeToken의 핵심은 대규모 MoE 모델의 활성 파라미터(Active Parameters)는 GPU VRAM에 배치하고, 전체 전문가 풀(Expert Pool)은 호스트 메모리에 유지하면서 하드웨어 자원을 동적으로 조율하는 것이다. 이를 통해 8GB VRAM의 노트북에서 35B 모델을, 게임용 데스크톱에서 284B 모델을, 그리고 단일 워크스테이션 GPU에서 753B 모델을 인터랙티브한 속도로 구동할 수 있음을 입증했다.

2. MoE 모델의 로컬 서빙 과제와 병목 현상

2.1 오픈 웨이트(Open-weight)와 실제 서빙 가능성의 괴리

프론티어 급 오픈 웨이트 모델(Kimi-K3, GLM-5.2, DeepSeek-V4-Flash 등)이 공개되면서 누구나 모델을 얻을 수 있게 되었으나, 이를 실제로 실행하는 비용은 여전히 높다. 수백 기가바이트에 달하는 가중치를 로컬 GPU VRAM에 모두 담는 것은 불가능에 가깝기 때문이다.

2.2 MoE 희소 활성화의 역설

MoE 아키텍처는 매 토큰 생성 시 전체 전문가 중 일부만 활성화하여 연산량은 줄이지만, 전체 전문가 가중치(Memory Footprint)는 줄이지 않는다. 따라서 비활성 전문가는 호스트 메모리에 상주해야 하며, 실행 경로에 따라 이를 동적으로 불러와야 하는 시스템적 과제가 발생한다.

2.3 엣지 하드웨어의 다층적 병목

로컬 추론 환경은 다음과 같은 복합적인 병목 현상을 마주한다.

  • GPU VRAM: 용량이 제한적이며 시스템 컴포지터, 브라우저 등과 공유됨.
  • 호스트 DRAM: GPU 메모리보다 크지만 대역폭(50~90 GB/s)이 VRAM(1~1.8 TB/s)에 비해 현저히 낮음.
  • PCIe 대역폭: CPU와 GPU 간 데이터 전송 속도를 결정하며, 노트북(x8 링크)이나 구형 사양에서 주요 병목이 됨.
  • CPU: 연산 능력과 메모리 대역폭이 GPU에 비해 낮아 단독 추론 시 속도가 크게 저하됨.
2.4 에이전트 워크로드의 특수성

에이전트가 도구를 호출하거나 문맥을 편집(thinking block 삭제 등)할 때마다 반복적인 프리필(Repeated Prefill)이 발생한다. 이는 초기 응답 시간(TTFT)을 급격히 증가시키고 전체 시스템의 가용성을 떨어뜨린다.

3. FreeToken의 핵심 기술 분석

FreeToken은 세 가지 주요 메커니즘을 통해 위 병목을 해결한다.

3.1 대역폭 적응형 실행 (Bandwidth-Adaptive Execution)

하드웨어의 실측 대역폭에 맞춰 연산과 전송을 최적화한다.

  • Prefill Double Buffering: 현재 레이어($l$)의 GPU 연산이 진행되는 동안, 다음 레이어($l+1$)의 전문가를 PCIe를 통해 미리 스트리밍하여 전송 시간을 연산 시간 뒤로 숨긴다.
  • $q^*$ 대역폭 정책: 디코드 단계에서 발생하는 캐시 미스를 처리할 때, 실측된 PCIe 대역폭($B_P$)과 호스트 가공 대역폭($B_H$)의 비율에 따라 GPU 캐시 채우기와 CPU 현장 실행 비중을 동적으로 나눈다.
3.2 시맨틱 인식 캐싱 (Semantic-Aware Caching)

문맥의 의미적 구조를 파악하여 메모리 효율을 극대화한다.

  • Semantic Anchors: <think>, <tool_call>, <tool_output> 등 대화 경계(Boundary)에 반복 상태 체크포인트(Recurrent-state checkpoint)를 보존한다. 문맥 편집 시 전체를 다시 계산하는 대신, 가장 가까운 앵커에서부터 새 접미사(Suffix)만 프리필한다.
  • Global LRU Expert Cache: 토큰 간의 전문가 라우팅 지역성(Locality)을 이용하여, 자주 사용되는 전문가를 GPU VRAM에 전역 LRU 방식으로 캐싱한다.
3.3 신축적 메모리 관리 (Elastic Memory Management)

로컬 환경의 가변적인 자원 상태에 대응한다.

  • Elastic VRAM Management: 실행 중 다른 애플리케이션의 VRAM 사용량 변화에 맞춰 전문가 캐시와 KV 캐시의 비중을 재배분한다. 엔진 재시작이나 모델 재로드 없이 캐시 구조를 동적으로 재구축한다.
  • 고속 부트스트랩: 전문가 풀을 디스크에서 읽어올 때 최종 호스트 레이아웃으로 직접 로드하여 초기 구동 속도를 높인다.

4. 실험 결과 및 성능 보고

논문 저자들은 다양한 하드웨어와 모델을 대상으로 성능을 측정하여 보고했다. 모든 결과는 저자들에 의해 보고된 수치이며, 독립적인 재현 결과가 아님에 유의해야 한다.

4.1 하드웨어 및 모델 조건
하드웨어 구분 주요 사양 (VRAM / Host DRAM) 대상 모델 성능 (저자 보고)
RTX 4060 Laptop 8GB VRAM / 32GiB DRAM Qwen3.6-35B (NVFP4) 39.3 tok/s
RTX 5090 Desktop 32GB VRAM / 192GiB DRAM DSV4-Flash 284B 22~25 tok/s
RTX PRO 6000 96GB VRAM / 512GiB DRAM GLM-5.2 753B 14.9 tok/s
4.2 주요 벤치마크 지표
  • RTX 5090 성능: Qwen3.6-35B에서 77~83 tok/s를 기록했으며, 이는 기존의 강력한 베이스라인 대비 1.5~2.3배 높은 수치다.
  • 응답성(TTFT): 에이전트 워크로드에서 FreeToken의 최악의 경우(Worst-turn) TTFT는 44초 미만인 반면, 베이스라인 시스템(llama.cpp, Ollama 등)은 일부 사례에서 150초 이상(최대 946초) 소요되어 시간 초과를 유발했다.
  • 캐시 효율성: RTX 5090 환경에서 FreeToken의 전문가 캐시 미스율은 Qwen 16%, DSV4 39%로, llama.cpp(62%, 89%) 대비 현저히 낮았다.

5. 소스 정보 및 한계점

5.1 문서의 권위와 라이선스
  • 논문 상태: 본 보고서의 기초가 된 논문은 arXiv v1 상태(2608.16157v1)이며, 동료 심사(Peer-reviewed)를 거치지 않았다.
  • 라이선스 구분: 논문 라이선스는 'arXiv non-exclusive distribution license 1.0'이며, 코드 저장소는 'Apache 2.0' 라이선스로 배포된다. 두 라이선스를 혼동해서는 안 된다.
5.2 기술적 한계 및 주의사항
  • 단일 GPU의 의미: 'Single GPU' 구동이 가능하지만, 이는 GPU 메모리만으로 구동된다는 의미가 아니다. 보고된 성능을 내기 위해서는 충분한 Host DRAM(최대 512GiB), 고성능 CPU, PCIe 대역폭이 반드시 동반되어야 한다.
  • 품질 및 품질 보증의 부재: 파라미터 수(35B/284B/753B)가 모델의 품질을 직접 보장하지 않는다. 또한, Codex의 33 tok/s와 비교된 수치가 동등한 사용자 경험이나 서비스 품질을 입증하는 것은 아니다.
  • 비대칭 비교: 베이스라인 엔진마다 지원하는 모델과 서버 구성이 달라 실험의 모든 조건이 완전히 대칭적이지 않을 수 있다. 또한 에너지 소비, 장기적 안정성, 보안 등에 대한 포괄적인 평가는 포함되지 않았다.

6. 결론

FreeToken 연구는 로컬 프론티어 AI의 경계가 단순히 GPU VRAM의 용량에 의해 결정되는 것이 아니라, 서빙 소프트웨어와 호스트 자원의 오케스트레이션 능력에 의해 확장될 수 있음을 시연했다. 희소 MoE 모델의 특성을 하드웨어 대역폭 및 에이전트의 시맨틱 구조와 결합함으로써, 사용자가 이미 소유한 개인용 장비를 프론티어 급 지능을 위한 실용적인 플랫폼으로 전환할 수 있는 가능성을 제시한다.

공개 전 편집 검증 메모

  • 권위 경계: arXiv 2608.16157v1의 저자 보고이며 동료심사·독립 재현 결과로 표현하지 않는다.
  • 하드웨어 경계: single GPU를 GPU만으로 바꾸지 않는다. 284B는 192GiB, 753B는 512GiB host DRAM 조건을 함께 밝힌다.
  • 지표 경계: parameter count와 decode tok/s는 model quality, 전체 agent 성공률, total cost, energy 효율의 직접 지표가 아니다.
  • 비교 경계: baseline의 모델·workload 지원은 비대칭이고 agent trajectory가 달라 cross-engine 전체 wall-clock은 비교하지 않았다.
  • 라이선스 경계: paper는 arXiv non-exclusive distribution license, code는 Apache 2.0으로 구분한다.
