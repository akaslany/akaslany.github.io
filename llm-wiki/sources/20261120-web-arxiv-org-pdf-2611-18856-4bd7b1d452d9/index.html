원문

[해설 보고서] 지속적 재귀 셀프 개선(CRSI)과 자기 개선 메모리(SIM) 기반의 에이전트 하네스 자율 진화 연구 분석

1. 개요 (Overview)

[소스의 주장] 대형 언어 모델(LLM) 기반 에이전트 시스템은 하위 정책 모델(Policy Model)의 가중치 자체뿐만 아니라 컨텍스트 맥락, 도구 세트, 실행 흐름 및 인터페이스 계약을 전반적으로 관여하고 제어하는 오케스트레이션 런타임 미들웨어인 하네스(Harness) 환경의 구조적 완성도에 크게 의존합니다 [Section 1]. [소스의 주장] 최근 연구에서는 정책 모델의 가중치를 직접 파인튜닝하지 않고도 하네스 코드를 자율적으로 수정·개선함으로써 에이전트의 오케스트레이션 수행 능력을 대폭 끌어올리는 재귀 셀프 개선(Recursive Self-Improvement, RSI) 기술이 활발히 연구되고 있습니다 [Section 1]. [사실] 기존의 하네스 RSI 방식은 에이전트의 실행 피드백 및 트레이스를 바탕으로 제안자(Proposer)와 선택자(Selector) 루프를 거쳐 후보 하네스 코드를 반복적으로 제안, 평가, 채택하는 방식으로 작동하지만, 대다수의 기존 연구는 단일 타깃 벤치마크와 고정된 정책 모델이라는 한정된 환경 조건 내에서만 최적화를 수행했습니다 [Section 1, Section 2].

[소스의 주장] 그러나 실제 소프트웨어 엔지니어링 및 에이전트 배포 환경에서는 정책 모델이 하위 버전에서 상위 버전으로 업데이트되거나(Model Evolution), 단일 하네스가 서빙 레이어에서 다중 모델을 동시에 지원해야 하거나(Multi-model Serving), 에이전트가 이전에 경험하지 못한 새로운 과제 분포에 직면하는 상황(Data Adaptation)이 필연적으로 발생합니다 [Section 1]. [사실] 이처럼 타깃 벤치마크나 정책 모델이 변경될 때, 소스 환경에서 진화시킨 하네스를 타깃 환경에 직접 적용(Direct Transfer)하면 초기 성능이 급격히 하락하거나 최적화를 거치지 않은 초기 시드(Seed) 하네스보다 도리어 낮은 성과를 보이는 사례가 발생합니다 [Section 1, Figure 1, Figure 3, Figure 4, Table 5, Table 6]. [사실] 실제로 Claude Opus 5.5 모델 환경에서 진화시킨 하네스를 Gemini 3.8 Flash 모델의 Workspace 도메인에 직접 적용했을 때, 초기 시작 점수는 68.41점을 기록하여 시드 하네스의 초기 점수인 73.89점보다 하락하는 현상이 확인되었습니다 [Section 1, Figure 4, Table 6]. [사실] 또한 텍스트 분류 도메인에서 소스 데이터셋으로 진화한 FewShotAll 하네스 역시 타깃 벤치마크 적용 시 시작 점수가 72.92점에 그쳐 시드 하네스의 75.72점보다 낮은 성과를 나타냈습니다 [Section 1, Figure 3, Table 5]. [작성자의 해석] 이는 하네스의 최종 텍스트 코드만 단독 전파될 뿐, 소스 RSI 과정에서 축적된 근원 원인 가설(Root Cause), 수정 의도 및 이유(Rationale), 예측 효과, 실제 집행 결과 등 심도 있는 최적화 이력 문맥(Provenance & Outcome)이 상실되어 타깃 최적화 에이전트가 이전의 비효율이나 착오를 무의미하게 반복하게 되기 때문입니다 [Section 1].

[소스의 주장] 연구진은 이러한 구조적 한계를 극복하기 위해, 호환 가능한 하네스 실행 인터페이스를 유지하면서 벤치마크나 정책 모델이 전환된 후에도 하네스 자율 진화를 지속할 수 있는 지속적 재귀 셀프 개선(Continual Recursive Self-Improvement, CRSI) 프레임워크를 정립하였습니다 [Section 1, Section 3.1]. [소스의 주장] 이와 함께 과제 수행 정책 모델이 아닌 하네스 최적화 에이전트(Proposer 및 Selector) 측면에 진화 경험 이력을 체계적으로 제공하는 외부 구조체인 자기 개선 메모리(Self-Improvement Memory, SIM) 메커니즘을 제안하였습니다 [Section 1, Section 3.2]. [작성자의 해석] SIM은 반복적으로 관측되는 하네스 결함 항목별로 근원 원인, 수정 코드 및 제안 이유, 예측 및 실측 평가 결과, 출처 문맥을 구조화하여 저장하고 갱신함으로써, 최적화 에이전트가 과거 경험을 바탕으로 타깃 환경에 맞춰 기존 하네스 메커니즘을 지속적으로 보존(Retain), 수정(Revise), 교체(Replace), 또는 제거(Remove)할 수 있도록 정밀하게 안내하는 핵심 계층으로 기능합니다 [Section 1, Section 3.2, Figure 2].

2. 주요 논점 (Key Arguments & Evidence)
2.1. 기존 하네스 RSI의 한계 및 지속적 재귀 셀프 개선(CRSI)의 필요성

[소스의 주장] 고정된 단일 환경에서 우수한 성과를 내는 기존 하네스 RSI 기법은 모델 적응(Model Adaptation)과 데이터 적응(Data Adaptation)이라는 두 가지 핵심 전이 과제에 직면할 경우 명확한 성능 한계와 구조적 부작용을 드러냅니다 [Section 1].

  • 모델 적응(Model Adaptation) 문제: [사실] 소스 정책 모델인 Claude Opus 5.5에서 최적화된 하네스를 Gemini 3.8 Flash 정책 모델 기반의 Workspace 도메인 과제에 직접 적용했을 때, 초기 점수는 68.41점으로 시드(Seed) 하네스의 73.89점보다 5.48점 낮게 측정되었습니다 [Section 1, Figure 4, Table 6]. [소스의 주장] 이는 특정 정책 모델의 생성 및 추론 특성(예: 쿼테이션 이스케이프 처리 방식, 추론 조기 종료 경향 등)에 과도하게 맞춤화되어 진화된 하네스 메커니즘이 다른 정책 모델과 결합할 때 불장난 같은 간섭 부작용(Interference)을 야기하기 때문입니다 [Section 1].
  • 데이터 적응(Data Adaptation) 문제: [사실] 정책 모델을 Gemini 3.8 Flash로 고정한 상태에서 과제 분포만 전환한 텍스트 분류 실험에서, 소스 데이터셋으로 최적화된 FewShotAll 하네스의 타깃 스위트 시작 점수는 72.92점으로 시드 하네스의 시작 점수인 75.72점보다 2.80점 낮았습니다 [Section 1, Figure 3, Table 5]. [소스의 주장] 이는 소스 과제에서 유효했던 방어 메커니즘(예: 명령어 정상 실행 여부만 확인하는 단순 완료 게이트)이 타깃 과제의 새로운 검증 요구사항(예: 해의 실행 타당성뿐만 아니라 최적성까지 검증해야 하는 요구)을 충족하지 못하고 오작동하는 장애 요소로 변질될 수 있음을 보여줍니다 [Section 1].
  • 이유 파악 불가의 문제 (Loss of Rationale & Provenance): [작성자의 해석] 소스 최적화 단계에서 생성된 최종 하네스 코드 파일만 단독으로 추출되어 타깃 최적화 환경으로 전달되는 경우, 해당 수정안이 어떤 하네스 결함을 해결하기 위해 도입되었는지, 어떠한 가정을 바탕으로 작동하는지, 이전 제안에서 실패하거나 성공했던 맥락이 무엇인지에 대한 실행 이력이 완전히 상실됩니다 [Section 1]. [소스의 주장] 이로 인해 타깃 최적화 에이전트는 계승받은 코드의 수용 의도를 파악하지 못해 이미 검증 및 폐기된 오류 방식을 재시도하거나 유용한 보존 메커니즘을 무분별하게 파괴하는 비효율을 겪게 됩니다 [Section 1].
2.2. 자기 개선 메모리(SIM)의 구조 및 작동 메커니즘

[소스의 주장] SIM은 하네스 최적화를 담당하는 제안자(Proposer)와 선택자(Selector) 에이전트가 이전 최적화 루프의 개입 이력을 직접 참조하고 지속적으로 확장·갱신할 수 있도록 설계된 외부 데이터 구조체입니다 [Section 3.2, Figure 2].

[사실] SIM 항목 데이터 구조: SIM의 개별 메타 엔트리 $m_i$는 근원 원인 가설 $c_i$와 이에 대응하는 시도 이력 리스트의 결합으로 아래와 같이 정식화됩니다 [Section 3.2, Equation 2].

$$m_i = \left(c_i, \left[\left(a_{ij}, o_{ij}, p_{ij}\right)\right]_j\right)$$

  • $c_i$: 근원 원인 가설 (Root-Cause Hypothesis, 예: 실행 검증 없는 조기 완료 처리 문제) [Section 3.2].
  • $a_{ij}$: $j$번째 시도의 수정 코드 내용 및 제안 이유 (Modification and Rationale, what, files 필드 저장) [Section 3.2, Appendix D.3].
  • $o_{ij}$: 해당 수정안이 해결할 것으로 예측된 과제 목록과 실제 평가를 통해 관측된 성과 (Predicted and Observed Task Outcomes, predicted, fixed, missed, passed/total 필드 저장) [Section 3.2, Appendix D.3].
  • $p_{ij}$: 출처 문맥 (Provenance: 해당 시도가 수행된 도메인, 벤치마크, 정책 모델, 최적화 라운드 정보, domain 필드 저장) [Section 3.2, Appendix D.3].

[사실] 제안자(Proposer)와 선택자(Selector)의 활용 메커니즘: 제안자와 선택자는 별도의 정보 검색(Retrieval)이나 컨텍스트 잘라내기(Truncation) 절차 없이 시스템 프롬프트 상에서 전체 SIM 기록 $M_t$를 직접 참조합니다 [Section 3.2, Equation 3]. 외부 루프 작동 방정식은 다음과 같이 표현됩니다 [Section 3.2, Equation 3].

$$C_t = P(H_t, F_t, D_t; M_t)$$ $$H_{t+1} = S(H_t, F_t, C_t, F_t^C; M_t)$$

[작성자의 해석] 제안자는 SIM 전체 이력을 읽고 이전에 실패했던 방식을 무의미하게 재시도하는 것을 방지하는 동시에 기존 근원 원인 $c_i$에 새로운 시도안을 연결할지 여부를 결정하며, 선택자는 제안된 후보 하네스 $C_t$가 과거 관측 이력과 비교하여 타깃 환경에 비추어 타당한지 검증합니다 [Section 3.2].

[사실] 메모리 갱신 및 병합 연산자 $U(M_t, e_t)$의 명확한 동작: 선택자에 의해 최종 채택된 후보 수정안 $e_t$만이 메모리 갱신 연산자 $M_{t+1} = U(M_t, e_t)$를 통해 메모리에 기록됩니다 [Section 3.2]. 만약 해당 라운드에서 어떤 후보안도 채택되지 않은 경우($e_t = \emptyset$), 메모리는 변형 없이 그대로 유지됩니다 ($U(M_t, \emptyset) = M_t$) [Section 3.2]. 선택되지 않은 나머지 미채택 후보안들은 메모리에 보존되지 않고 폐기되지만, 선택자에 의해 채택된 수정안($e_t$)의 경우에는 설령 해당 수정안이 예측했던 특정 과제를 해결하지 못하거나 일부 성능 퇴보(Regression)를 야기했더라도 실측된 평가 관측 결과(fixed, missed, passed/total)가 있는 그대로 누적 기록됩니다 [Section 3.2, Appendix D.1, Appendix D.3]. 또한 제안자가 제시한 근원 원인 텍스트가 기존 엔트리의 텍스트와 완벽히 일치하는 경우, 기존의 모든 시도 및 성과 이력을 보존한 채 신규 시도 항목이 정식(Deterministic)으로 누적 병합(Merge)됩니다 [Section 3.2, Appendix D.1].

[사실] 실험 대조군 4가지 조건 정의 (Section 3.3, Figure 6):

실험 조건 (Condition) 시작 하네스 (Harness) 타깃 RSI 중 SIM 메모리 사용 여부 (SIM Memory) 상세 설명 및 제어 조건
Cold Start 시드 하네스 ($H_0$) 미사용 ($\emptyset$) 소스 RSI를 거치지 않은 초기 하네스에서 타깃 RSI 수행
Harness Transfer 소스 진화 하네스 ($H_S$) 미사용 ($\emptyset$) 소스에서 진화된 하네스만 계승하여 타깃 RSI 진행 (하네스 코드 단독 전파 기준선)
Problem-Only Memory 소스 진화 하네스 ($H_S$) 근원 원인 단독 계승 ($M_S^c$) 소스 메모리 중 근원 원인 가설($c_i$)만 남기고 수정안/결과/문맥 이력을 모두 제거 후 진행
Full SIM (제안 기법) 소스 진화 하네스 ($H_S$) 전체 이력 계승 및 타깃 갱신 ($M_S$) 근원 원인, 수정안, 예측/관측 결과, 출처 문맥 전체 계승 및 타깃 갱신 연산($U$) 적용
2.3. 4개 도메인 대상 데이터셋 및 모델 교차 전환 실험 결과

[사실] 연구진은 Coding, Text Classification, Workspace, Engineering 4개 도메인을 대상으로 교차 데이터셋 및 교차 모델 CRSI 실험을 수행하였습니다 [Section 4.1, Table 4].

[사실] 교차 데이터셋 CRSI 결과 (Cross-Dataset, Figure 3, Table 5): 동일한 정책 모델(Gemini 3.8 Flash) 환경에서 6개 데이터셋 전환을 평가한 결과, Full SIM이 6개 모든 설정에서 가장 높은 최종 평가 점수를 달성하였으며, Harness Transfer 대비 2.43~4.35점, Problem-Only Memory 대비 0.20~6.06점 높은 성과를 거두었습니다 [Section 4.2, Figure 3, Table 5].

  • Coding / AHE: Full SIM 24.85점 (Cold 19.39점 / Transfer 20.61점 / Problem-Only 18.79점) [Table 5].

[작성자의 해석] 세대 연쇄 동역학 및 모델 용량 포화 심층 분석: Gemini 3.5 Flash 및 3.8 Flash 등 중위권 추론 능력을 가진 모델 세대에서는 소스 하네스로부터 승계된 크로스 턴 오케스트레이션 및 실행 방어 구조(Scaffolding)가 모델의 미흡한 추론을 보완하여 CRSI+SIM이 독립 최적화(Fresh RSI) 대비 명확한 우위(+3.5%p, +1.6%p)를 제공합니다 [Section 4.3.2, Table 1]. 그러나 Gemini 4 Argon과 같이 정책 모델의 기본 역량이 극도로 높은 수준(~95% 성능 포화 구간)에 도달하면, 과거 모델 세대에서 형성된 복잡한 하네스 제약 및 과도한 인터셉션 로직이 오히려 에이전트의 자율적 문제 해결 능력을 과도하게 구속(Over-constraining)하는 리스크를 야기할 수 있어 독립 최적화 점수가 미세하게 상회하는 ceiling effect가 발생합니다 [Section 4.3.2, Table 1].

[사실] 다중 모델 공유 하네스 실험 (Multi-Model Shared Harness, Section 4.3.3, Table 2): Grok 4.20 Reasoning, Claude Opus 5.5, Gemini 3.8 Flash 3개 모델이 단일 하네스를 공유하는 설정(Text Classification 타깃 스위트)을 평가한 결과, 매 라운드 3개 모델의 실행 트레이스 피드백을 통합 합성한 기법(Unified synthesis, S2)이 보유 평가 세트(Held-out) 기준 평균 75.24점을 기록하여, 모델별로 개별 최적화된 하네스를 적용한 기준선(Per-model harnesses, B1: 75.20점)과 거의 대등한 성과를 보였습니다 [Section 4.3.3, Table 2]. 이는 공유 시드 하네스(B2: 73.28점), 순차적 CRSI(S1: 74.20점), 그리고 단일 모델로 진화시킨 하네스를 타 모델에 일방 전이한 개별 결과들(S3: 평균 66.84~72.24점)을 모두 명확히 상회하는 결과입니다 [Table 2].
