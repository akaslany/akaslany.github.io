Language Modeling Is Compression

웹 · 2026-08-12

요약

언어모델의 예측은 무손실 압축으로 이어지며, 실용성은 모델과 연산 비용에 달려 있다.

언어 모델은 왜 압축기인가 — 예측과 압축의 같은 목적함수

한눈에 보는 결론

이 논문의 핵심은 “LLM이 ZIP 프로그램을 대체한다”가 아니다. 더 정확한 주장은 다음 데이터를 잘 예측하는 확률 모델은 그 데이터를 더 짧은 비트로 무손실 부호화할 수 있다는 것이다. 로그손실을 줄이는 언어모델 훈련과 코드 길이를 줄이는 압축은 정보이론에서 같은 목적함수를 공유한다.

저자들은 이 관점을 텍스트뿐 아니라 이미지와 음성에 적용했다. 논문 초록은 Chinchilla 70B가 ImageNet 43.4%, LibriSpeech 16.4%를 기록했다고 주장한다. 그러나 v2 본문 Table 1의 대응값은 48.0%, 21.0%다. 설명 없는 내부 불일치이므로 여기서는 실험 조건이 명시된 Table 1 값을 사용한다. 동일 2,048-byte chunk 비교는 ImageNet 48.0% vs PNG 61.7%, LibriSpeech 21.0% vs FLAC 30.3%다. 그러나 이 수치는 70B 모델 자체의 저장비용과 거대한 계산비용을 제외한다. 실용 압축기의 종합 우위를 증명한 결과로 읽으면 안 된다.

1. 예측이 압축이 되는 생활 비유

택배 상자 안에 무엇이 들어 있는지 매번 긴 문장으로 적는 대신, 받는 사람과 보내는 사람이 같은 확률표를 공유한다고 하자. 다음 물건이 책일 확률이 90%라면 ‘책’에는 아주 짧은 표식을 주고, 희귀한 물건에는 긴 표식을 준다. 예측이 정확할수록 자주 나오는 항목에 짧은 코드를 배정할 수 있어 평균 메시지가 짧아진다.

산술 부호화는 이 확률표를 실제 비트열로 바꾸는 방법이다. 처음에는 0과 1 사이 전체 구간을 잡고, 다음 심볼의 확률만큼 구간을 나눈다. 실제 심볼에 해당하는 구간만 남기기를 반복하면 최종 구간을 가리키는 짧은 이진수 하나가 전체 시퀀스를 표현한다. 이상적인 코드 길이는 대략 -log2 P(sequence)다. 모델이 실제 데이터에 높은 확률을 줄수록 필요한 비트가 줄어든다.

2. 무손실이라는 조건

압축된 비트열만 보내서는 복원할 수 없다. 수신자도 동일한 확률 모델과 동일한 부호화 규칙을 가져야 한다. 그래서 모델을 이미 양쪽이 공유하는 온라인 서비스와, 모델까지 함께 전달해야 하는 파일 압축은 경제성이 다르다.

논문은 pretrained model을 고정하고 외부 데이터를 압축하는 offline in-context setting을 본다. 모델을 압축 대상에 맞춰 다시 학습하지 않고, 컨텍스트에서 패턴을 읽어 다음 byte를 예측한다.

3. 놀라운 이미지·음성 수치와 정확한 조건

실험은 텍스트, 이미지, 오디오를 각각 1GB로 맞춘다. Transformer의 짧은 context에 맞추기 위해 모두 2,048-byte chunks로 나눈다. ImageNet은 전체 컬러 파일을 그대로 넣지 않고 32×64 grayscale patches로 만들며, LibriSpeech는 원본 FLAC 파일이 아니라 16kHz int16 샘플을 1바이트로 줄인 스트림이며 2,048 bytes는 약 64ms다.

이 조건에서 v2 Table 1의 Chinchilla 70B raw compression rate는 ImageNet 48.0%, LibriSpeech 21.0%다. 같은 2,048-byte chunk 조건의 PNG는 61.7%, FLAC은 30.3%다. 초록은 43.4%·16.4%와 unchunked PNG 58.5%를 섞어 제시하지만, 표에서 대응 실험으로 확인되지 않는다. 텍스트 모델이 비텍스트 데이터의 국소 통계를 컨텍스트에서 포착할 수 있다는 강한 증거다.

그러나 ‘48.0%가 같은 chunk의 PNG 61.7%보다 작다’는 것과 ‘70B LLM이 PNG보다 실용적이다’는 전혀 다르다. raw rate는 모델 파라미터를 제외하고, 연산시간·메모리·전력도 포함하지 않는다. 데이터 표현과 chunking도 일반 파일 사용과 다르다.

4. 모델도 보내야 한다면 계산이 뒤집힌다

압축물을 보낼 때 70B 모델도 함께 보내야 한다면 모델 자체가 엄청난 짐이 된다. 저자들의 adjusted compression rate는 압축된 데이터 크기에 모델 파라미터 비용을 더하는 two-part code 관점이다.

작은 이삿짐을 보내면서 거대한 압축기계를 트럭에 같이 싣는다면 아무리 상자가 작아져도 총비용은 커진다. 데이터가 충분히 커져 기계 비용을 많은 byte에 나눌 수 있을 때만 큰 모델의 좋은 예측이 이득이 된다. 그래서 데이터 크기마다 최적 모델 규모가 있고, 무조건 큰 모델이 최선이라는 단순 scaling law가 깨진다.

5. 토크나이저는 공짜 압축기가 아니다

BPE 같은 토크나이저는 자주 등장하는 byte 묶음을 하나의 token으로 바꿔 시퀀스를 짧게 만든다. 덕분에 같은 token context에 더 많은 원문 byte가 들어가고 Transformer 계산을 절약한다. 하지만 token 알파벳이 커지면서 각 token 예측은 어려워질 수 있다.

논문은 tokenization이 일반적으로 순수 압축률을 자동 개선하지 않지만, 제한된 context와 이차적 attention 비용 안에서 더 많은 정보를 처리하게 해 예측 성능을 높이는 공학적 절충이라고 해석한다.

6. gzip도 생성 모델이 될 수 있다

어떤 문자열 뒤에 후보 심볼을 하나씩 붙여 압축 길이가 얼마나 늘어나는지 비교하면, 압축기가 어떤 다음 심볼을 자연스럽다고 보는지 추정할 수 있다. 길이가 덜 늘어나는 후보에 더 높은 가중치를 주고 반복 샘플링하면 gzip도 조건부 생성기처럼 작동한다.

이것은 압축과 예측의 역방향 연결을 보여주는 개념 증명이다. gzip은 장기 구조를 이해하지 못하고, 논문의 one-step 방식도 정규화된 확률분포가 아니어서 샘플이 편향될 수 있다. 생성 품질이 현대 LLM과 경쟁한다는 뜻이 아니다.

7. 논문이 증명한 것과 증명하지 않은 것

논문이 보여준 것은 세 가지다. 첫째, 확률 예측과 무손실 코드 길이가 실제 arithmetic coding으로 연결된다. 둘째, 대형 언어모델의 in-context 예측이 제한된 이미지·오디오 표현에서도 강한 raw compression rate를 낼 수 있다. 셋째, 모델 파라미터 비용을 포함하면 데이터 크기별 최적 모델 규모가 생긴다.

반면 모든 LLM이 범용 압축기보다 실용적이라는 것은 증명하지 않았다. 장기 문맥, 일반 파일 형식, 전송비용, 계산시간, 에너지, 하드웨어 비용을 포함한 end-to-end 우위도 증명하지 않았다. 압축률 하나가 추론·사실성·안전성·창의성을 모두 측정한다는 결론도 나오지 않는다.

재현과 반증 기준

주요 수치는 v2 코드와 동일한 직렬화, 1GB 데이터셋, 2KB chunk, header 처리, top-k 100 재정규화 조건에서 재현해야 한다. 모델 크기를 포함한 adjusted rate와 제외한 raw rate를 반드시 분리해야 한다. 다른 이미지 표현, 긴 context, 다양한 오디오 형식, 실제 전송·연산 비용까지 포함했을 때 우위가 사라진다면 실용 범용 압축기 해석은 철회해야 한다.

결론

좋은 언어모델은 세상을 ‘이해해서’ 압축한다고 단정하기보다, 데이터의 규칙성을 잘 예측하기 때문에 짧게 부호화할 수 있다고 말하는 편이 정확하다. 이 논문은 언어모델의 학습 목표를 정보이론의 오래된 질문과 연결한다. 가장 중요한 교훈은 더 큰 모델이 언제나 정답이 아니라, 예측 이득이 모델 자체의 비용을 넘어설 만큼 데이터가 충분히 큰가를 함께 물어야 한다는 것이다.

원문 내부 불일치를 어떻게 다뤄야 하나

초록·기여 요약의 43.4%와 16.4%는 v2 Table 1에서 찾을 수 없다. Table 1은 48.0%와 21.0%를 제시한다. 또한 초록의 PNG 58.5%는 unchunked이고 FLAC 30.3%는 2,048-byte chunk 값이다. 따라서 서로 다른 조건을 한 줄의 정면 비교처럼 제시하지 않는다. 영상은 Table 1의 동일 chunk 값 48.0 vs 61.7, 21.0 vs 30.3을 사용하고, 초록과 표가 불일치한다고 명시한다. 정성적 결론—모델 크기를 제외한 특정 가공 데이터 조건에서 Chinchilla가 전용 압축기보다 낮은 비율—은 Table 1로도 유지된다.

FP16 70B 모델은 약 140GB다. 이를 1GB 데이터에 전부 더하면 adjusted rate는 ImageNet 약 14,048%, LibriSpeech 약 14,021%가 되어 실용 압축이 아니다. 다만 송수신자가 모델을 이미 공유한다면 전송비 계산은 달라진다.
