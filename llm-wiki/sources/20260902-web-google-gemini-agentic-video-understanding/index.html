영상 토큰 88% 절감? Gemini 에이전틱 비디오 이해 검증

기준일: 2026-09-02 KST

결론부터

Google이 발표한 에이전틱 비디오 이해는 긴 영상을 무조건 한 번에 넣는 대신, 질의에 필요한 구간과 신호를 내부 도구로 골라 다시 보는 방식이다. 공개 차트와 발표에서 Google 보고 최대 88% 토큰 감소, 최대 66% 비용 감소, 최대 7% 품질 향상을 제시한다. 그러나 세 수치는 동일한 평균 결과가 아니라 서로 다른 평가·비용 계산에서 고른 Google 보고 최대치다. 원시 실행 로그와 완전한 평가 명세가 공개되지 않아 독립적으로 재현된 결과는 아니다.

핵심 가치는 분명하다. 긴 영상에서 모든 초의 프레임을 고정 비율로 컨텍스트에 넣는 낭비를 줄이고, 질문과 관련된 부분을 더 촘촘하게 볼 수 있다. 핵심 위험도 분명하다. 관련 구간을 처음부터 잘못 찾으면 보지 않은 증거는 추론으로 복구할 수 없고, 도구 왕복과 탐색 사고 토큰이 지연·비용을 늘릴 수 있다.

무엇이 바뀌었나

기본 정적 처리는 영상 프레임을 1 FPS로 추출하고 오디오와 함께 한 번에 컨텍스트에 넣는다. 빠른 동작은 1초 사이에 지나가므로 놓칠 수 있고, 긴 영상은 입력 토큰이 커진다.

에이전틱 처리는 다음의 제한된 도구 루프다.

  1. 질문에서 필요한 증거 유형을 추정한다.
  2. 영상 타임라인에서 후보 구간을 찾는다.
  3. 필요한 구간의 transcript, frame, audio를 불러온다.
  4. 빠른 동작이나 경계가 의심되면 FPS나 해상도를 바꿔 다시 본다.
  5. 수집한 증거를 바탕으로 답하고, 부족하면 다시 탐색한다.

이것은 범용 자율 에이전트가 아니다. Gemini 모델의 추론 단계와 Google이 제공하는 내부 미디어 로드 도구가 반복되는 제품 기능이다. Developer API 응답의 processing_call과 processing_result를 확인해야 실제 동적 탐색을 썼는지 검증할 수 있다.

API 계약과 제공 범위

2026-09-01 문서에서 지원 모델은 Gemini 3.7 Flash, 3.6 Flash, 3.5 Flash-Lite다.

  • Gemini Developer API Interactions: 비디오 입력에 processing: "agentic".
  • Gemini Enterprise Agent Platform GenerateContent: Python Part에 media_processing="agentic", REST에 mediaProcessing: "AGENTIC".
  • 정적 처리가 기본이고 에이전틱은 명시적으로 켜야 한다.

발표는 Gemini API를 Google AI Studio에서 쓰는 경로와 Gemini Enterprise Agent Platform을 현재 제공으로 적는다. 반면 Gemini 앱은 soon, Ask YouTube는 in the coming months라고 예고했을 뿐이다. 기준일에 소비자 제품 전면 rollout이 완료됐다고 말할 근거는 없다.

88%, 66%, 7%의 실제 의미

Google 차트의 Gemini 3.7 Flash 조건은 high thinking level, low media resolution, 정적 baseline 1 FPS다.

  • Minerva: 80.9K에서 33.6K tokens로 계산상 58.47% 감소. 정확도 73.7%에서 79.0%로 상대 7.19% 증가.
  • 1H-VideoQA: 397.6K에서 47.7K tokens로 88.00% 감소. 정확도 87.5%에서 88.5%로 상대 1.14% 증가.
  • LVBench: 300.3K에서 36.0K tokens로 88.01% 감소. 정확도 85.1%에서 88.6%로 상대 4.11% 증가.

따라서 88% 토큰 감소와 7% 품질 향상은 전형적 한 쌍이 아니다. 토큰 최대치는 1H-VideoQA·LVBench, 품질 최대치는 Minerva에서 나왔다. 7%는 5.3 percentage points를 73.7로 나눈 상대 증가다.

비용 66% 감소는 입력 토큰만으로 계산할 수 없다. 에이전틱 모드는 탐색 thought tokens와 tool-use tokens를 낸다. 2026-09-02 Gemini 3.7 Flash 유료 표준가는 2026-12-31까지 입력 100만 tokens당 0.75달러, 출력·thinking 100만 tokens당 3.75달러다. Google은 기능 추가요금이 없다고 하지만 평가별 입력·출력·thinking·tool-use 분해를 공개하지 않았다. 66%는 Google 보고 최대치로만 남는다.

benchmark를 어디까지 믿을 수 있나

LongVideoBench 공개 논문 v1은 최대 1시간의 3,763개 웹 비디오와 자막, 6,678개 인간 주석 객관식 문항, 17개 세부 범주를 제공한다. 이는 긴 입력에서 관련 장면을 찾고 추론하는 능력을 평가한다. Google 블로그는 별도 데모에서 LongVideoBench를 사용했다고 적지만, 헤드라인 차트의 세 행은 Minerva, 1H-VideoQA, LVBench다.

문제는 재현 명세다. 발표는 Minerva와 1H-VideoQA의 공개 데이터셋 카드, split, 질문 구성, scorer, 반복 수를 연결하지 않았다. LVBench라는 이름도 공개 문헌에 유사 명칭이 둘 이상 있어 정확한 논문·버전·split을 확정할 수 없다. 두 번째 1H-VideoQA 비용-정확도 그림에는 GPT 5.6 Sol/Terra, Claude Opus 5.0, Grok 4.6 비교가 있지만 점의 정확 좌표표, 모델별 가격 시점, API 설정, 반복 수, 신뢰구간, raw outputs가 없다. Pareto frontier는 그 공개 점 집합과 가격 가정 안의 주장이지 보편적 우위가 아니다.

최근 공개 연구 VESTA는 long-video agent에서 retrieval policy에 따라 benchmark별 gains가 달라지고 일부 benchmark에서는 기존 방법과 동률이라고 보고한다. 이는 어떤 구간을 어떻게 찾느냐가 독립적인 실패 원인임을 보여주는 강한 반대 근거다.

빠른 순간 탐색과 지연은 다른 문제

sub-second moment retrieval은 1초보다 짧은 상태 변화나 컷 경계를 찾아내는 공간·시간 해상도 주장이다. 전체 API 응답이 1초 미만이라는 뜻이 아니다. Google 문서도 5분 미만 짧은 영상에서는 내부 추론과 도구 왕복 때문에 time to first token이 약간 늘 수 있다고 적는다.

운영 판단에는 평균 정확도뿐 아니라 다음을 같이 재야 한다.

  • end-to-end latency, TTFT, p95/p99.
  • tool call 횟수와 재탐색 깊이.
  • retrieval miss와 false negative.
  • 총 입력·출력·thinking·tool-use tokens.
  • 영상 길이와 질의 유형별 분포.

실패 모드와 적용 경계

  • 빠른 동작: 정적 1 FPS는 놓칠 수 있지만 에이전틱 탐색도 해당 구간을 먼저 발견해야 한다.
  • 전 구간 정밀 검사: 모든 프레임을 보아야 하는 compliance·forensics에서는 선택적 탐색이 증거 누락을 만들 수 있다.
  • 비언어 소리: 공식 문서는 오인 가능성을 명시한다.
  • multi-turn: stateless 요청에서 step_list의 processing steps를 누락하면 비디오 컨텍스트가 사라진다.
  • safety: 정책 위반 영상은 응답 거부가 가능하다.
  • 비용: 짧은 영상이나 광범위 질문에서는 탐색 overhead가 절감분을 상쇄할 수 있다.
  • 품질: benchmark multiple-choice gains가 open-ended production correctness를 보장하지 않는다.

YouTube 입력과 데이터 처리

Gemini Developer API의 YouTube URL 입력은 공개 영상만 허용한다. Gemini 2.5 이상은 요청당 최대 10개이며 무료 tier는 하루 8시간, 유료 tier는 영상 길이 기반 일일 제한이 없다고 문서화한다. Enterprise Agent Platform 문서는 YouTube URL 요청당 1개와 모델군별 길이 제한을 별도로 둔다. 제품면의 제한을 서로 바꿔 쓰면 안 된다.

데이터 처리도 tier별로 다르다. 무료 Gemini API와 일반 무료 Google AI Studio는 입력·응답이 제품 개선에 사용되고 인간 검토가 가능하므로 민감·기밀·개인정보를 넣지 말아야 한다. 활성 billing project 또는 Workspace enterprise account의 Paid Service는 prompts/files/responses를 제품 개선에 쓰지 않으며 안전·보안 목적의 제한된 로그 처리가 남는다.

파트너 testimonial은 독립 근거가 아니다

Ponder는 자체 pipeline과 비슷한 recall에서 약 3.5배 적은 input tokens, Mosaic는 자체 production-style eval에서 median input tokens 97% 감소와 constraint coverage 약 2배, Resemble AI는 약 1,000개 라벨 영상·live deepfake workload에서 57% 적은 input tokens, Revyl은 빠른 앱 animation 검증 가능성을 말했다. 그러나 원시 로그, matched baseline, 평가자, 실패 사례, 불확실성이 없다. 공급자가 선택해 발표한 이해관계자 자기보고로 분리해야 한다.

도입 판단과 반증 기준

긴 영상의 특정 장면 질의라면 에이전틱 모드를 먼저 시험할 이유가 있다. 다만 실제 도입은 같은 모델·가격·media resolution에서 정적 모드와 paired evaluation을 해야 한다.

판단을 철회하거나 낮춰야 할 조건은 다음이다.

  • 동일 item에서 retrieval miss 때문에 정적 모드보다 오류가 늘어난다.
  • thought/tool 왕복을 포함한 총비용에서 우위가 사라진다.
  • TTFT 또는 p95가 서비스 요구를 넘는다.
  • 전 구간 감사에서 선택적 로딩이 중요 증거를 누락한다.
  • 외부 재현에서 최대치가 특정 benchmark·query mix에만 국한된다.

반대로 item-level outputs, exact prompts, scorer, run count, latency distribution, token breakdown이 공개되고 제3자가 비슷한 분포를 재현하면 현재의 Google 보고 최대치 평가는 더 강해질 수 있다.

최종 판단

이 기능은 긴 영상의 토큰 병목을 고정 샘플링에서 질문 기반 탐색으로 바꾸는 실용적 설계다. 공개 수치만 놓고 보면 토큰 효율과 정확도를 동시에 개선할 가능성이 있다. 그러나 88%·66%·7%는 최대치이고, benchmark 정체와 실행 명세가 부분적으로 비공개이며, 지연·retrieval miss·개인정보 조건이 남는다. 따라서 현 단계의 정확한 표현은 Google이 보고한 최대 효율 개선, 독립 재현 전이다.
