에이전트 하네스(Agent Harness)의 정의 및 역할

에이전트 하네스(Agent Harness)는 언어 모델(Model)과 수행할 과제(Task) 사이에 위치하는 소프트웨어 레이어로 정의된다. 하네스는 모델이 인지하는 문맥(Context)을 구성하고, 도구 호출(Tool Call)을 중계하며, 모델의 출력을 검증하고, 재시도(Retry)·승격(Escalate)·중단(Stop) 여부를 결정하는 핵심 제어 루프를 실행한다. 모델 관점에서 하네스는 과제에 접근하기 위한 인터페이스이며, 학습 시스템 관점에서는 외부에서 변경할 수 없는 고정된 외부 프로그램이다.

모델 성능 파편화 현상

동일한 언어 모델이라 하더라도 적용되는 에이전트 하네스 환경에 따라 계획 수립, 도구 선택, 과제 완수 능력이 크게 달라지는 성능 파편화 현상이 발생한다. 예를 들어 GLM-5.2 모델의 경우 동일한 SWE-벤치 프로(SWE-bench Pro) 평가에서 적용된 하네스 종류에 따라 과제 성공률(Pass@1)이 23%에서 52%까지 커다란 격차를 보인다. 이러한 하네스에 따른 성과 순위는 모델마다 달라져, 특정 모델에서 우수한 성적을 거둔 하네스가 다른 모델에서는 낮은 성적을 기록하기도 한다.

하네스에 따른 성능 변화 원인 분석

  1. 도구 형식(Tool Surface / Action Format) 하네스마다 사용하는 API 규격(OpenAI Chat Completions, OpenAI Responses, Anthropic Messages, Google Gemini 등)이 서로 다르며, 도구 명칭의 대소문자 표기 방식(Title case vs lower case)이나 인자(Argument) 명칭의 규격(예: file_path vs filePath)에 차이가 존재한다. 특정 하네스 형식에 맞춰 학습된 모델은 다른 규격을 사용하는 하네스로 이동했을 때 불일치하는 도구 이름을 호출하여 실제 실행 단계에 이르지 못하고 오류를 발생시킨다.

  2. 문맥 구조(Context Structure) 하네스별로 이전 수행 이력을 압축(Compaction)하는 방식, 역할 마크(Role Markers) 추가 방식, 공백 처리 유무 등이 상이하다. 단일 하네스 방식에 과도하게 적응된 모델은 이력이 압축되거나 역할 표시가 변경되었을 때 이전 단계에서 자신이 수행한 결과 위치를 정상적으로 찾지 못하고 이미 완료된 작업을 불필요하게 반복하는 오버피팅 현상을 일으킨다.

  3. 제어 흐름(Control Flow) 하네스가 내부적으로 제공하는 자동 재시도 및 오류 복구 규칙에 모델이 과도하게 의존하게 되는 현상이다. 특정 하네스의 오류 재시도 메커니즘에 익숙해진 모델은 중단 및 재시도를 스스로 판단하지 않고 하네스의 제어 흐름에 의존하게 되며, 이러한 보정 기능이 없는 다른 하네스 환경에서는 동일하게 실패한 명령을 무한히 반복 실행하게 된다.

2. 하네스 강화학습의 구조적 분류: 블랙박스(Black-box) vs 화이트박스(White-box)

루프 소유권(Loop Ownership)에 따른 구조 분류
화이트박스(White-box) 구조

전통적인 에이전트 강화학습 방식으로, 학습기(Trainer)가 전체 반복 실행 루프(Rollout Loop)를 직접 소유하고 통제한다. 학습기는 env.step() 명령을 호출하여 행동을 샘플링하고 관찰 결과를 직접 읽어 들인다. 이 구조에서는 모델이 생성한 모든 토큰이 이미 학습기의 직접적인 통제하에 존재하므로 완벽한 관찰이 가능하다.

블랙박스(Black-box) 구조

하네스가 독자적인 샌드박스(Sandbox) 내부에서 루프 실행, 도구 호출, 문맥 압축, 중단 여부를 완전히 소유하고 통제하는 방식이다. 외부의 학습기는 하네스 내부의 상태나 환경 변화를 직접 볼 수 없으며, 모델 엔드포인트(Model Endpoint)를 통해 오가는 API 요청-응답(Request-Response) 쌍만을 관찰할 수 있다.

용어의 이중적 사용 구분

KAT-Coder 보고서 등 일부 문헌에서는 하네스 내부의 이력 압축 유무에 따라 화이트박스(압축 없는 단순 루프, 예: Mini-SWE-Agent)와 블랙박스(문맥 압축 및 재구성 수행, 예: Claude Code, Codex 등)를 구분하기도 한다. 그러나 본 보고서에서의 화이트박스 및 블랙박스 구분은 반복 실행 루프(Rollout Loop)의 소유권 주체가 학습기인가 아니면 하네스인가를 기준으로 분류한 것이다.

화이트박스 구조와 블랙박스 구조 비교
화이트박스(White-box) 구조 블랙박스(Black-box) 구조
루프 소유권: 학습기(Trainer)가 반복 실행 루프(Rollout Loop)를 직접 소유하고 통제함. 루프 소유권: 에이전트 하네스(Agent Harness)가 샌드박스 내부에서 루프, 도구 호출, 문맥 압축, 중단 여부를 독자적으로 소유 및 실행함.
관찰 가능 범위: 환경 상태, 도구 실행, 에피소드 전체 과정을 학습기가 직접 관찰함. 관찰 가능 범위: 외부 학습기는 모델 엔드포인트(Model Endpoint)를 오가는 API 요청-응답(Request-Response) 쌍만을 관찰함.
토큰 보존 방식: 학습기가 행동 샘플링 시 토큰 식별자 및 확률을 직접 보유함. 토큰 보존 방식: 하네스와 엔드포인트 사이의 캡처 프록시(Capture Proxy)를 통해 토큰 식별자 및 로그 확률을 가로채어 보존함.

3. 오픈엔브이(OpenEnv) 프레임워크와 토큰 충실성(Token Fidelity) 파이프라인

프레임워크 시스템 흐름

블랙박스 형태의 하네스 환경에서 강화학습을 수행하기 위해 구축된 프레임워크는 다음 세 가지 주요 요소로 구성된다.

  • 하버(Harbor): 컨테이너화된 과제(Task)와 격리된 샌드박스(Sandbox) 실행 환경을 제공하며, 각 하네스를 샌드박스 내부로 연결한다.
  • 오픈엔브이 캡처 프록시(OpenEnv Capture Proxy): 하네스와 모델 엔드포인트 사이에 위치하여 통신을 중계하며, 하네스의 코드 수정 없이 정밀 데이터를 실시간 기록한다.
  • 티알엘(TRL): 캡처 프록시가 수집하여 그래프 형태로 재구성한 트레이스(Trace) 데이터를 전달받아 비동기 GRPO(Group Relative Policy Optimization) 강화학습을 집행한다.
캡처 프록시의 보존 데이터 및 메커니즘

캡처 프록시는 모델 엔드포인트 단에서 요청을 가로채어 정확한 토큰 식별자(Token ID), 생성 시점의 로그 확률(Logprob), 그리고 **손실 마스크(Loss Mask)**를 손실 없이 수집한다. 하네스가 수행하는 중복 실행, 서브 에이전트 생성, 문맥 압축 과정은 개별 호출 노드로 저장되며, 공통 토큰 접두사(Token Prefix) 연결 방식을 통해 손실 없는 트레이스 그래프(Trace Graph)로 복원된다.

정밀 온정책 수집을 위한 Sampling 및 캡처 제약 메커니즘

캡처 프록시는 온정책(On-policy) 강화학습 데이터의 정밀성을 보장하기 위해 생성 단계에서 top_p나 top_k 절단(Truncation)을 적용하지 않고 전체 분포에서 샘플링(top_p=1.0)을 수행한다. 분포를 절단할 경우 정책의 엔트로피 붕괴(Entropy Collapse)를 유발하며, vLLM 등의 추론 엔진이 절단 이후 계산하는 처리된 로그확률(Processed Logprobs)이 실제 정책의 확률과 불일치하는 문제가 발생한다. 실험에 따르면 top_p를 1.0으로 설정함에 따라 중요도 샘플링 비율(Importance Ratio)이 기존 0.985~0.993 범위에서 0.9984~0.9999 수준으로 비약적으로 안정화되었다.

또한 프록시는 캡처 수준을 3단계로 엄격히 구분하여 검증한다:

  1. 토큰 수집 단계(tokens): 프롬프트 식별자, 생성 식별자, 정렬된 로그확률이 모두 보존되어 강화학습(RL) 학습이 가능함.
  2. 로그확률 수집 단계(logprobs): 로그확률은 존재하나 연결할 토큰 식별자가 없음 (평가 전용/Eval only).
  3. 텍스트 수집 단계(text): 텍스트만 존재함 (평가 전용/Eval only).

OpenAI, Anthropic, Hugging Face Inference Providers 등 외부 호스팅 API는 생성된 토큰 식별자를 반환하지 않으므로 평가 전용 하네스로 제한되며, 이를 통한 역전파 학습은 차단된다.

예외 처리 및 비동기 분산 환경의 안정성

기존 인프로세스(In-process) 방식의 실행 체계에서는 하네스 내부에서 예외가 발생할 경우, 다중 GPU 분산 학습 환경에서 특정 프로세스 단절로 인해 나머지 GPU들이 NCCL 배리어(Barrier) 상태에서 무한 대기하며 전체 시스템이 다운되는 결함이 존재했다. OpenEnv HTTP 서버 구조는 하네스 내부 예외 발생 시 에러를 상위로 전지시키지 않고 ok=False, reward=None 응답을 반환하도록 설계하여 분산 학습 루틴의 중단 없이 비동기 환경을 안정적으로 유지한다.

토큰 충실성(Token Fidelity)에 관한 논쟁
원문 저자들의 입장

텍스트를 디코딩한 후 다시 토큰화하는 재토큰화(Re-tokenization) 과정을 거치면 토큰 경계(Token Boundary)가 변형되거나, 하네스가 수정한 텍스트에 대해 모델이 생성하지 않은 토큰으로 기울기(Gradient)가 업데이트되는 오류가 발생한다. 따라서 정밀한 온정책 강학학습을 위해서는 모델 엔드포인트 단에서 원래의 토큰 식별자와 생성 시점의 로그 확률을 엄격히 보존해야 한다는 입장을 취한다.

미해결 쟁점 및 반대 입장

OpenForgeRL 등의 연구에서는 토큰 식별자나 로그 확률의 정밀한 기록 없이, 프록시가 수집한 프롬프트-응답 쌍의 재구성만으로도 매우 높은 멀티 하네스 학습 성과를 달성했음을 보고하고 있다. 이로 인해 토큰 수준의 정밀한 보존 메커니즘이 멀티 하네스 강화학습의 필수 불가결한 요건인가에 대해서는 학계 및 연구진 사이에서 여전히 미해결 쟁점으로 남아있다.

4. 소형 모델(LFM2.5-2.6B) 멀티 하네스 강화학습 실험 분석

실험 설정 및 데이터셋 구체화

LFM2.5-2.6B 소형 모델을 대상으로 SmolDataEnvs 평가 데이터셋을 통한 실험이 진행되었다. 해당 데이터셋은 실제 Kaggle 데이터 분석 노트북을 기반으로 구축된 1,000개의 학습 과제(중간 난이도/Medium 400개, 높은 난이도/Hard 600개)와 중복이 없는 250개의 평가 과제로 구성된다.

학습 체계는 TRL을 활용하여 1,000 단계의 비동기 GRPO 방식을 적용하였으며, 4개 하네스(OpenCode, Claude Code, Codex, Mini-SWE-Agent) 환경에 모델을 임의로 노출시키는 멀티 하네스 학습을 수행하였다.

보상 구조 (Reward Structure)

과제 해결의 정확성을 검증하는 정답 보상(Correctness Reward)과 함께, 불필요한 도구 호출을 줄이고 효율적인 해결 경로를 찾도록 유도하는 도구 효율성(Tool Efficiency) 보너스가 복합적으로 적용되었다.

수치적 성과 (저자 보고 기준)
  • 평균 성공률 향상: 4개 하네스에 대한 평균 과제 해결 성공률이 학습 전 **42.2%**에서 학습 후 **54.2%**로 상승하였다.
  • 도구 사용 효율성: 공통으로 해결에 성공한 과제군에서 도구 호출(Tool Calls) 횟수가 약 31% 감소하였다.
단일 하네스 대비 비교 및 성능 해석

단일 하네스(OpenCode 전용) 환경에서만 학습한 모델과 4개 하네스에서 균등 학습한 멀티 하네스 모델 간의 평균 정확도 차이는 1.9%포인트 수준에 불과하며, 이는 통계적 잡음 범위(Noise Range) 내에 해당한다.

따라서 멀티 하네스 학습의 핵심 성격은 절대적인 단일 정확도 수치의 압도적 상승에 있는 것이 아니라, 특정 하네스 규격에 치우치지 않는 하네스 간 전이 가능성(Cross-harness transferability)의 확보 및 도구 사용의 효율성 증대에 있음을 알 수 있다.

지도 미세조정(SFT) 대비 강화학습(RL) 메커니즘 비교

대형 모델의 성공 트레이스를 활용한 지도 미세조정(SFT)과의 비교 분석 시, 검증 과정을 거쳐 선별된 **최적 체크포인트(Optimal Checkpoint)**와 학습 종료 시점의 최종 체크포인트(Final Checkpoint) 수치를 엄격히 구분해야 한다.

SFT 방식은 대형 모델의 정적 실행 기록을 모방하므로 특정 하네스의 스캐폴드/인터페이스 관습에 쉽게 과적합(Scaffold Overfitting)된다. 그 결과 학습 진행에 따라 최종 체크포인트로 갈수록 학습되지 않은 타 하네스로의 전이 능력이 급격히 하락하는 현상이 발생한다. 반면 멀티 하네스 RL(GRPO)은 다채로운 제어 구조 및 도구 인터페이스 규칙에 지속적으로 노출되며 동적 보상을 받으므로, 특정 스캐폴드 관습에 과적합되지 않고 지속적이며 안정적인 정책 업데이트를 유지할 수 있다.

5. 연구의 한계점 및 보고서의 성격 명시

연구의 5대 한계점
  1. 단일 시드(Single Seed) 사용: 모든 반복 실험 및 결과 도출이 단일 시드 상에서만 수행되어 확률적 변동성에 대한 추가 검증이 필요하다.
  2. 단일 과제군(Single Task Suite) 평가: 평가 및 학습이 SmolDataEnvs 데이터셋 영역에 한정하여 검증되었으므로, 일반적인 소프트웨어 공학 도메인 전체로 일반화하기에는 제한이 존재한다.
  3. 불균등 노출 및 연산량: 학습 과정에서 각 하네스별로 제공된 노출 빈도 및 투입된 연산 자원의 배분에 완전한 균형을 이루지 못했다.
  4. 효율 보너스 제거 실험(Ablation) 부재: 적용된 도구 효율성 보너스가 성능 향상에 미친 순수한 기여도를 격리하여 측정하는 통제 실험(Ablation Study)이 수행되지 않았다.
  5. 일반적 우월성 증명 미흡: 본 실험 결과는 제시된 프레임워크 조건하에서의 성과일 뿐, 모든 에이전트 환경이나 일반적인 강화학습 방법론의 절대적 우월성을 증명하는 것은 아니다.
보고서 성격 규정

본 보고서에 제시된 모든 성과 지표, 수치 및 메커니즘 분석은 별도의 외부 독립 검증 기관을 거친 결과가 아니며, 오직 제공된 원문 저자들의 보고서(Author Report) 내용에 기반하여 작성된 기술 보고서임을 명시한다.
