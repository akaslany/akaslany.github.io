1. 개요 (Overview)

[사실] 본 보고서는 일리노이 대학교 어바나-샴페인(UIUC) 및 구글 클라우드 AI 리서치(Google Cloud AI Research) 연구진(가오탕 리 / Gaotang Li 외)이 발표한 논문 "Object-Oriented Harness: Evolving Agent Harnesses through Object-Oriented Design"을 바탕으로 작성되었습니다. 본 연구는 대형 언어 모델 에이전트(Language Model Agent)를 둘러싼 프롬프트, 도구, 제어 흐름을 명시하는 실행 가능한 코드인 하네스(Harness)를 객체지향 설계(Object-Oriented Design) 원칙에 따라 계층적으로 진화시키는 최적화 프레임워크인 '객체지향 하네스(OO-Harness)'를 제안합니다. 복잡하고 이질적인 장기 작업(Long-horizon tasks) 환경에서 단일 글로벌 하네스(Global Harness)가 가지는 일반화 한계를 극복하고, 개별 작업의 고유한 실행 요구사항에 맞춘 최적의 에이전트 실행 환경을 자동으로 구축하는 것을 핵심 목적으로 합니다.

[소스의 주장] 기존의 하네스 최적화 방식은 전체 탐색 세트(Discovery Set)에 단일한 글로벌 하네스([SOURCE_IMAGE_1]a)를 학습시킴으로써, 난이도가 높은 작업을 위해 추가된 메모리나 특화 도구가 단순한 작업의 성능을 떨어뜨리는 부정적 전이(Negative Transfer) 및 공통 로직 오염 문제를 야기했습니다. 한편 독립적인 하네스 모듈들을 나열하는 플랫 하네스 패밀리([SOURCE_IMAGE_1]b) 방식은 공통 개선 로직의 전파와 공유가 불가능하여 코드 중복을 초래합니다. 반면 OO-Harness는 하네스가 파이썬(Python) 등의 실행 가능한 코드 형태로 존재한다는 점에 착안하여, 객체지향 프로그래밍의 상속(Inheritance), 메서드 재정의(Method Overriding), 신규 메서드 추가(Adding New Methods) 메커니즘을 하네스 진화에 도입했습니다([SOURCE_IMAGE_1]c). 이를 통해 공통 동작 방식은 상위 부모 클래스에서 유지하고, 작업군별 특화 동작은 자식 서브클래스(Subclass)로 분리하여 하네스 계층 구조($\mathcal{T}_H$)를 형성함으로써 코드 재사용성과 특화 성능을 동시에 달성합니다.

[사실] OO-Harness 프레임워크는 크게 훈련(Train) 단계와 테스트/배포(Test/Deployment) 단계로 명확하게 분리되어 작동합니다([SOURCE_IMAGE_2], [SOURCE_IMAGE_3]). 훈련 단계에서는 진화 에이전트(Evolution Agent, $\pi$)가 기본 하네스(Base Harness, $H_0$)의 실행 기록을 기반으로 유사한 실행 요구를 가진 작업들을 클러스터링하고([SOURCE_IMAGE_3]-1), 전체 데이터셋 재실행 없이 대상 클러스터에서만 자식 클래스를 검증하여 하네스 계층 구조를 확장하는 동시에 디자인 교훈($L_\pi$)과 라우팅 교훈($L_\rho$)을 축적합니다([SOURCE_IMAGE_3]-2). 테스트 단계에서는 하네스 계층 구조, 클래스 설명, 라우팅 교훈을 동결(Freeze)한 후([SOURCE_IMAGE_3]-3), 하네스 라우터(Harness Router, $\rho$)가 신규 작업 및 관찰 가능한 기본 실행 궤적을 분석하여 최적의 특화 하네스를 동적으로 선택하거나 기본 결과를 재사용함으로써 이상적인 다형성(Polymorphic) 실행을 구현합니다([SOURCE_IMAGE_3]-4).

2. 주요 논점 (Key Arguments & Mechanics)

2.1. 기존 하네스 최적화의 한계와 OO-Harness의 등장 배경
  • [사실] 기존 연구의 한계: 최근 등장한 APEX-Agents(투자 은행, 경영 컨설팅, 기업법) 및 FutureX(실제 사건 예측)와 같은 벤치마크는 도구 활용, 컨텍스트 관리, 완료 검사 조건이 작업별로 극도로 이질적입니다. 기존의 글로벌 하네스 최적화 방식인 Meta-Harness나 Agentic Harness Engineering(AHE)은 탐색 세트 전체에서의 평균 성과만을 기준으로 단일 하네스를 결정합니다. 이로 인해 메모리 모듈이나 특화 도구를 추가하는 수정이 복잡한 작업에는 유용할지라도, 단순한 작업이나 기존에 성공적이었던 작업의 성과를 크게 떨어뜨리는 현상(EvoHarnessBench 등에서 확인됨)이 지속적으로 발생했습니다.
  • [소스의 주장] 객체지향 설계의 당위성: 하네스는 프롬프트, 도구, 제어 흐름을 명시하는 실행 가능한 코드이므로, 객체지향 설계가 형태적 및 기능적 관점에서 하네스 최적화에 가장 적합한 패러다임입니다. 상속을 활용하면 성공적인 기반 로직을 복사 없이 재사용할 수 있으며, 다형성을 통해 동일한 실행 인터페이스 상에서 작업별로 최적화된 서브클래스 객체를 호출할 수 있습니다. 이는 기존 Git 브랜칭/리베이싱에 의존하던 적응형 오토 하네스(Adaptive Auto-Harness, AAH)와 달리, 파이썬 클래스의 상속, 메서드 재정의, super() 호출을 통해 메모리 및 제어 흐름 단에서 완벽한 다형성을 제공한다는 결정적 차별성을 갖습니다.

  • [소스의 주장] 핵심 비교 근거 정리:
    • 글로벌 최적화 방식은 이질적 작업 집합 전체에서 최적의 균형을 찾으려 하므로 개별 작업 요구사항에 맞춰 과감한 특화를 진행하기 어렵습니다.
    • 독립적 플랫(Flat) 구조는 공통 개선 사항이 발생했을 때 이를 전체 하네스에 전파하기 어렵고 코드 중복이 심화됩니다.
    • OO-Harness는 상속 구조를 통해 공통 기법의 전파와 작업별 독자적 특화를 완전히 분리함으로써 이 문제를 해결합니다.
2.2. OO-Harness의 계층적 구조 및 진화·라우팅 메커니즘

[사실] OO-Harness의 동작 구조는 훈련 단계(Train Phase)와 테스트/배포 단계(Test/Deployment Phase)의 2단계로 명확히 구분됩니다.

  1. 진화 단계 (Train Phase):

    • 초기화 (Initialization): 기본 하네스 $H_0$를 탐색 작업 데이터셋($D_{tr}$)에서 실행하여 기본 궤적 및 실패 기록을 수집합니다. 실행 기록상에서 유사한 실행 요구사항이나 실패 패턴을 공유하는 작업들을 클러스터링하여 작업 클러스터 ${C}$ 및 작업 집합 ${D_c}$를 생성하고, 초기 계층 구조를 $\mathcal{T}_H = {H_0}$로 설정합니다 ([SOURCE_IMAGE_3]-1).
    • 진화 반복 (Iteration 및 Algorithm 1): 진화 에이전트($\pi$)는 파일 시스템 접근 권한을 가진 코드 워크스페이스에서 보조 에이전트(Subagent)를 활용해 실행 기록을 분석합니다. 진화 에이전트는 대상 클러스터 $c$와 부모 클래스를 선택한 후, 자식 서브클래스 $H'$를 작성합니다. 자식 클래스는 부모의 메서드를 상속받으며, super()를 호출하여 부모 동작을 포함하거나 특정 메서드를 재정의(Override) 및 신규 추가합니다.
    • 수용 기준 및 국소적 검증: 제안된 자식 클래스 $H'$는 전체 탐색 세트가 아닌 대상 클러스터 $D_c$에서만 실행 및 평가됩니다. 후보 $H'$가 수락되기 위해서는 클러스터 점수 조건인 $S_c(H') > S_c^{\text{current}}$를 만족하고 벤치마크별 검증 통과 수용 기준을 충족해야 하며, 판단이 모호한 경우에는 평가 에이전트(Judging Agent)가 결과를 판정합니다. 수락된 클래스는 계층 구조 $\mathcal{T}H$에 등록되고 해당 클러스터의 대표 하네스로 지정됩니다. 만약 연속적인 제안이 거절될 경우 해당 클러스터의 탐색 우선순위가 하향 조정되며, 필요시 클러스터 재할당, 분할, 병합이 수행됩니다. 이 과정에서 얻은 성공/실패 결과는 디자인 교훈($L\pi$) 및 라우팅 교훈($L_\rho$)으로 축적됩니다.

  2. 테스트 단계 (Test/Deployment Phase):

    • 동결 (Freeze): 탐색 과정이 완료되면 하네스 계층 구조 $\mathcal{T}H$, 클래스 설명, 라우팅 교훈 $L\rho$을 동결합니다. 실행 모델(Executor, $M$)의 가중치와 하네스 코드 구조는 더 이상 수정되지 않습니다 ([SOURCE_IMAGE_2], [SOURCE_IMAGE_3]-3).
    • 동적 라우팅 및 다형성 실행: 신규 작업 $t$가 주어지면 먼저 기본 하네스 $H_0$를 통해 관찰 가능한 기본 궤적 $\omega(t)$를 얻습니다. 하네스 라우터($\rho$)는 작업 정보, 기본 궤적 $\omega(t)$, 하네스 클래스 설명, 동결된 라우팅 교훈을 종합하여 최적의 하네스 $H^* = \rho(t, \omega(t), {H_0} \cup {H_c}{c \in \mathcal{C}}, L\rho)$를 선택합니다. 만약 $H^* = H_0$로 판단되면 기존 Base 실행 결과를 그대로 재사용하고, 특화 하네스가 선택되면 단일 인스턴스 상에서 다형성 인터페이스를 통해 실행합니다 ([SOURCE_IMAGE_3]-4).

[작성자의 해석] 진화 단계에서 후보 하네스를 전체 탐색 세트가 아닌 대상 클러스터에서만 검증하는 방식은 프레임워크의 효율성과 일반화 성능을 획기적으로 향상시킵니다. 논문의 실험 결과(Figure 4)에 따르면, OO-Harness의 평균 탐색 소요 시간은 29.0시간으로 Meta-Harness의 109.1시간 대비 약 73.4%의 절대적 시간 및 API 비용 절감 효과를 증명했습니다. 전체 데이터셋 재실행을 회피함으로써 탐색 속도를 대폭 높이는 한편, 특정 클러스터의 수정이 다른 노드에 악영향을 주지 않도록 격리하여 훈련 세트 오버피팅 및 부정적 전이(Negative Transfer)를 완벽히 방지합니다.

2.3. 주요 실험 결과 및 성능 비교

[사실] OO-Harness의 성능을 검증하기 위해 업무 워크플로우 벤치마크인 AutomationBench, 파일 및 애플리케이션 작업 벤치마크인 Workspace-Bench(Lite-100), 다중 도구 사용 벤치마크인 Toolathlon-GYM 등 3대 장기 작업 벤치마크에서 평가를 진행했습니다. 모든 실험은 동일한 고정 실행 모델(gemini-3.5-flash)과 훈련/테스트 분할 환경에서 수행되었습니다.

2.4. 소스 기반 심층 분석 및 절제 연구 (Ablation & Case Studies)
라우팅 증거의 효과 (Routing Evidence)

[사실] 라우팅 입력 정보의 범위가 성과에 미치는 영향을 분석하기 위해 '작업 정보만 사용(Task only)'하는 라우터와 '작업 + 기본 실행 궤적(Task + trajectory)'을 모두 관찰하는 라우터를 비교했습니다 (Table 2).

  • AutomationBench: Mean 기준 'Task only' 64.88% 대비 'Task + trajectory'가 77.52%로 12.64%p의 압도적 성과 상승을 기록했습니다.
  • Toolathlon-GYM: PASS 기준 'Task only' 33.33% 대비 'Task + trajectory'가 37.70%로 4.37%p 향상되었습니다.
  • Workspace-Bench: Mean 기준 'Task only' 40.03% 대비 'Task + trajectory'가 40.56%로 0.53%p의 미미한 차이를 보였습니다.

[작성자의 해석] Workspace-Bench는 문서 작성(.docx), presentation, spreadsheet 등 요구되는 출력 파일 형식이 작업 설명에 명확히 드러나므로 작업 정보만으로도 라우팅이 원활합니다 (Figure 6b). 반면 AutomationBench와 Toolathlon-GYM은 도구 호출 예산 초과, 데이터 쓰기 미완성, API 쿼리 파싱 오류 등 실행 중 발생하는 동적 오류를 해결하는 하네스가 다수 포함되어 있으므로, 기본 실행 궤적을 관찰하는 것이 최적 하네스 라우팅의 필수 조건으로 작용합니다 (Figure 6c).

상속 구조의 유용성 (Inheritance Structure)

[사실] Workspace-Bench에서 하네스 코드 재사용 구조가 성과에 미치는 영향을 절제 연구한 결과는 다음과 같습니다 (Figure 5).

  • OO (상속 기반 계층 구조): 마이크로 루브릭 통과율 40.56% 달성.
  • Flat (코드 복사 기반 재사용): 마이크로 루브릭 통과율 35.60% 달성.
  • Base-reset (코드 이월 없음, 매번 Base에서 진화 시작): 마이크로 루브릭 통과율 29.39% 달성.

[작성자의 해석] Flat이 Base-reset보다 높은 성과를 낸 것은 이전에 진화된 성공 로직을 재사용하는 자체의 유용성을 입증합니다. 나아가 OO가 Flat을 4.96%p 앞선 결과는 단순히 이전 진화 코드를 복사해 단일 모듈에 집어넣는 방식보다, 상속을 통해 계층적으로 코드를 조직화하고 다형성을 부여하는 객체지향적 접근이 우수함을 명확히 증명합니다.

Base 재사용 및 OOD 성능

[사실] 분포 외(Out-of-Distribution, OOD) 환경 평가를 위해 Toolathlon-GYM 데이터셋을 미중복 애플리케이션 데이터(훈련 254개 / 테스트 49개)로 분할하여 평가했습니다 (Figure 7).

  • Meta-Harness는 훈련 시 학습한 단일 글로벌 하네스를 낯선 테스트 애플리케이션에 강제로 적용하다가 성능이 44.90%로 급락했습니다.
  • OO-Harness는 하네스 라우터가 훈련 시 접하지 못한 낯선 애플리케이션 환경을 감지하고 범용 Base 하네스 재사용 전략을 선택함으로써 59.18%의 PASS 성과를 그대로 보존했습니다.
  • AutomationBench 분석(Table 3)에서도 라우터가 Base 실행 결과가 우수한 작업(평균 리워드 77.15%)은 Base를 재사용하도록 유지하고, Base 성과가 낮은 작업(평균 리워드 44.40%)만 특화 하네스로 라우팅하는 합리적 선택을 내렸음이 확인되었습니다.
사례 연구 (Case Studies)
  • [사실] Workspace-Bench Word 문서 생성 (Figure 8 / B.1): office-doc-write 하네스는 파일 백엔드의 write() 메서드를 오버라이딩하여, 텍스트 형태의 드래프트가 입력되었을 때 정식 바이너리 .docx 문서로 렌더링하도록 전환합니다. 만약 렌더링 실패가 발생할 경우 안전장치로서 부모 백엔드로 롤백(Fallback)되며, 기존 타깃 문서는 훼손하지 않은 채 원본 텍스트 작성을 보존합니다.
  • [사실] AutomationBench 계통적 실행 검사 (Figure 9 / B.2): discovery-setup 계층 구조에서 조상 노드 $s_9$는 미완성 쓰기 작업 시 턴 추가 요청 로직을 구현했고, 자식 노드 $s_{12}$는 턴 제한 임박 경고 안내를 오버라이딩했습니다. 손자 노드 $s_{29}$는 복구 불가능한 도구 오류 지침을 신규 추가하면서 super()를 호출하여 조상들의 모든 검사 로직을 완벽히 유지 및 중첩 적용했습니다.
  • [사실 및 작성자의 해석] Toolathlon 퍼센트 셀 검사 및 다형성 코드 동작 (Listing 1 / B.3):
    • Listing 1의 코드 구조 및 다형성 메커니즘: 부모 클래스 FormulaLiteralHarness($s_7$)는 manage_context 메서드를 오버라이딩하여 수식 원본 저장 대신 계산된 리터럴 값을 고정합니다. 자식 클래스 PercentCheckHarness($s_{30}$)는 manage_context를 별도로 재정의하지 않아 부모의 수식 관리 로직을 그대로 상속받으며, verify_before_finish 메서드를 오버라이딩합니다. 자식 노드의 verify_before_finish 내부에서는 parent = super().verify_before_finish(messages, state)를 먼저 호출하여 부모가 가진 검사 로직을 실행 및 통과한 후, 자식 고유의 추가 검사를 수행함으로써 객체지향적 상속의 이점을 극대화합니다.
    • 퍼센트 단위 검사 트리거 조건: $s_{30}$ 하네스는 작업 완료 전 저장된 .xlsx 워크북을 읽어 퍼센트(%) 라벨이 붙은 셀의 값이 $0$과 $1$ 사이의 소수로 저장되어 있는지 확인합니다. 해당되는 경우 1회 수정 요청(Correction pass)을 발생시켜 해당 셀의 값에 100을 곱한 퍼센트 포인트 단위(예: $0.2 \rightarrow 20$)로 수정하도록 가이드합니다.
    • 도구 출력 압축 조율 메커니즘: completeness-finalize 계통 하네스는 부모 노드가 길어진 도구 출력을 압축하여 컨텍스트를 절약하지만, 이른 종료 시도(Early finish attempt) 이후 발생하는 이후 도구 출력에 대해서는 자식 노드가 조건부 오버라이딩을 수행하여 압축을 우회(Bypass)시킴으로써 최종 정제 과정의 정보 손실을 방지합니다.

5. 한계와 불확실성 (Limitations & Uncertainties)

[사실] 논문의 'Limitations' 섹션 및 본문에서 기술된 프레임워크의 한계점 및 소스 기반 불확실성은 다음과 같습니다.

  1. [사실] 호스트 환경 및 외부 API 의존성: OO-Harness는 호스트 시스템이 제공하는 API 및 실행 환경에 전적으로 의존합니다. 호스트 서비스의 일시적 중단(Service Outages)이나 호출 제한(Rate Limits)이 전체 진화 및 라우팅 시스템의 신뢰성에 직접적인 영향을 미칩니다.
  2. [사실] 인터페이스 변경 시 재조정 필요성: 하위 시스템의 인터페이스가 변경되는 경우, 이미 진화되어 동결된 하네스 코드 및 계층 구조를 업데이트하거나 재학습시켜야 하는 한계가 존재합니다.
  3. [사실] 보안 및 권한 설정 문제: 사설(Private) 서비스나 인증이 필요한 외부 서비스를 통합할 경우, 안전한 자격 증명(Credential) 처리 및 세분화된 권한 설정 메커니즘 구축이 필수적입니다.
  4. [소스에서 다루지 않음 / 확인 불가] 타 언어 모델 적용 시 성과 변화: 본 연구는 실행 모델로 gemini-3.5-flash, 진화 모델로 Claude Opus 4.8만을 활용하여 검증했습니다. 오픈소스 LLM(예: Llama 계열)이나 타사 모델을 실행기로 사용할 경우 OO-Harness의 성능 향상 폭이 동일하게 유지될지 여부는 본 소스 문서만으로는 확인 불가합니다.
  5. [소스에서 다루지 않음 / 확인 불가] 절대적 금전 비용 및 리소스 액수: API 호출 기반 연산 비용이 주요 리소스 소비원임을 명시하고 있으나, 진화 및 라우팅 전체 과정에 소요된 정확한 달러($) 단위의 절대적 금전 비용 수치는 소스에 명시되지 않아 확인 불가합니다.
