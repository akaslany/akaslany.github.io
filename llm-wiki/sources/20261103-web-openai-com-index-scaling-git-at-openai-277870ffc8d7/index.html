1. 개요 (Overview)

본 보고서는 2026년 11월 2일 OpenAI가 발표한 기술 문서(Scaling Git at OpenAI)를 바탕으로, AI 모델 Codex 도입 이후 급격한 속도로 성장한 OpenAI 모노레포(Monorepo)의 버전 관리 인프라 한계를 극복하기 위해 개발된 신규 Git 백엔드 시스템 'Pando'의 아키텍처와 성과를 분석합니다.

OpenAI는 Codex를 통한 개발 자동화 및 엔지니어와 AI 에이전트 간 병렬 작업 확대로 인해 커밋, 브랜치 생성, 푸시, 패치 및 클론 수량이 폭발적으로 증가하는 환경에 직면했습니다. 기존 버전 관리 백엔드 시스템은 푸시 및 패치 지연, 머지 실패율 증가 등으로 인해 신뢰도가 90% 미만으로 떨어지는 구조적 병목을 나타냈습니다. 이에 OpenAI는 단일 모노레포 환경에서 수천 명의 사용자 및 에이전트가 동시에 작업할 수 있도록 쓰기 및 읽기 스루풋을 극대화하는 새로운 백엔드 시스템인 Pando를 구축했습니다.

Pando의 핵심 개발 목적은 두 가지입니다. 첫째, 여러 브랜치에 대한 동시 푸시 연산을 수평적으로 확장(Horizontally scalable writes)하는 것입니다. 둘째, 클라이언트가 이용 가능한 네트워크 대역폭을 완전히 활용하여 데이터를 전송받을 수 있도록 읽기 스루풋(Read throughput)을 극대화하는 것입니다. Pando는 이러한 성능 목표를 달성하면서도 기존 Git 프로토콜 및 클라이언트와의 완벽한 호환성을 유지하여, 개발자와 에이전트가 기존 워크플로우를 수정하지 않고 시스템을 수용할 수 있도록 설계되었습니다.

Pando는 10주간의 개발 기간을 거쳐 2026년 4월 실운영 환경에 성공적으로 적용되었습니다. 이를 통해 머지 신뢰도를 99.99%로 향상시켰으며, 푸시 중위 지연 시간을 약 80%(약 5배) 단축했습니다. 현재 Pando는 하루에 약 1 페타바이트(PB)의 Git 데이터를 전달하며, 피크 시간대에는 시간당 57 테라바이트(TB)의 팩파일 데이터를 99% 이상의 디스크 캐시 적중률로 전송하고 있습니다.

2. 주요 논점 (Key Arguments & Technical Analysis)
2.1. 기존 버전 관리 시스템의 한계 및 신규 시스템 필요성

  • Codex 도입에 따른 개발 규모의 변화 [사실]

    • Codex 도입으로 엔지니어가 다수의 작업을 병렬로 수행하게 되면서 브랜치, 푸시, 머지 연산과 더불어 개발 환경, 연구 작업, CI(지속적 통합)로부터의 패치 및 클론 요청이 급증했습니다.
    • 단일 엔지니어가 동시에 여러 변경 사항을 CI에 전송함에 따라, 푸시 1회당 동일 커밋을 가져오는 작업이 연쇄적으로 발생했습니다.
    • 2024년 Q1 대비 2026년 Q4의 master 브랜치 커밋 성장률은 실제 측정 및 추정치 기준 +2,442%에 달했습니다.

  • 기존 시스템의 신뢰도 저하 및 구조적 마찰 [소스의 주장]

    • 지난해 말(2025년 말)부터 모노레포 지원 시스템이 하중을 견디지 못해 패치 및 푸시 속도가 저하되고 머지 실패가 빈번해졌으며, 시스템 신뢰도가 90% 미만으로 떨어졌습니다.
    • 20여 년 전 이메일로 커널 패치를 주고받던 방식에서 출발한 전통적 Git 운영 구조 및 백엔드는 대규모 동시 병렬 작업을 수행하는 최신 모노레포 환경과 구조적 마찰을 일으켰습니다.

  • 병목 원인 및 Pando의 구축 목표 [해석]

    • 병목 원인: 중앙 집중식 단일 순서 제어 및 완벽한 리포지토리 전체 정합성 보장 메커니즘으로 인해, 서로 다른 브랜치로 들어오는 동시 푸시가 서로를 대기시키는 현상이 발생함. 또한 클라이언트마다 개별 팩파일을 서버에서 동적으로 생성함으로써 계산 및 디스크 I/O 병목이 발생함.
    • 구축 목표:
      1. 서로 다른 브랜치에 대한 병렬 푸시가 독립적으로 처리되는 수평 확장형 쓰기 구조 확보.
      2. 캐시 가능한 팩파일(Packfile)의 재사용을 통한 최고 속도의 읽기 스루풋 제공.
      3. 기존 Git 프로토콜 및 개발자/에이전트 워크플로우와의 완전한 호환성 유지.
2.2. 기존 분산 Git 서비스 패턴 비교 (3PC vs WAL)

기존 분산 Git 확장 방식은 크게 3상 커밋(Three-phase commit, 3PC) 방식과 상태 기록 로그(Write-ahead log, WAL) 방식으로 나뉘며, Pando는 이들과 차별화된 아키텍처를 채택했습니다.

  • 3상 커밋 (3PC) 방식 분석 [사실]

    • 메커니즘: 여러 복제본(Replica)에 리포지토리 전체 사본을 유지합니다. 푸시 수신 시 패크파일을 모든 복제본에 전송하고, 코디네이터(Coordinator)가 여러 단계의 통신(Pre-commit, Commit 등)을 거쳐 정족수(Quorum) 이상의 복제본에서 레퍼런스(Ref) 잠금 및 업데이트 승인을 받아 처리합니다.
    • 원인-결과 체인 및 한계: 모든 레퍼런스 변경을 리포지토리 전체 단위로 순차 정렬하므로, 무관한 브랜치에 대한 푸시라도 정족수 합의 과정을 대기해야 합니다. 결과적으로 복제본의 디스크 I/O 포화(Saturation)와 네트워크 RTT 지연이 푸시 경로 전체의 쓰기 병목을 유발합니다.

  • 상태 기록 로그 (WAL) 방식 분석 [사실]

    • 메커니즘: 블롭 저장소에 팩파일을 업로드한 후, 공유 매니페스트(Shared manifest)에 레퍼런스 업데이트 정보를 기록합니다. 매니페스트 업데이트 시 비교-교환(Compare-and-swap, CAS) 연산을 사용하여 원자적으로 상태를 변경합니다.
    • 원인-결과 체인 및 한계: 팩파일 업로드는 병렬로 수행할 수 있으나, 서로 다른 브랜치에 대한 푸시라 하더라도 단일 공유 매니페스트 수정 과정에서 CAS 경합을 일으킵니다. 또한 각 복제본이 읽기 요청을 처리하기 위해 지속적으로 매니페스트를 읽고 저널 팩을 색인(Indexing)하는 과정을 거쳐야 하므로, 쓰기량이 증가할수록 읽기 전용 서버의 색인 지연으로 인해 클라이언트의 읽기 지연(Read latency)이 대폭 증가합니다.

  • 3PC, WAL, Pando 아키텍처 비교 [해석]

  • 본 비교표의 구분 항목별 특성은 소스 문서에 명시된 기술적 사실[사실]에 기반함.

2.3. Pando 아키텍처 핵심 원리

  • 제약 조건의 재정의 [사실]

    • 리포지토리 전체 일관성 포기: 모든 레퍼런스의 단일 시점 스냅샷을 보장하는 전통적 요구사항을 철회하고, 레퍼런스 단위의 독립적 변경을 허용하여 서로 다른 브랜치 간 푸시 경합을 근본적으로 제거했습니다.
    • 클라이언트별 고유 팩파일 생성 중단: 클라이언트의 개별 보유 상태에 맞춰 서버가 매번 개별 팩파일을 동적으로 압축·생성하는 연산을 중단하고, 미리 생성되어 블롭 저장소에 저장된 불변(Immutable) 팩파일을 재사용하도록 변경했습니다.

  • 인과적 일관성 (Causal Consistency, CC) [사실]

    • Pando는 브랜치별 변경 사항에 대해 직렬성(Serializability)을 보장하지만, 전체 리포지토리에 대해서는 인과적 일관성을 제공합니다.
    • 푸시가 발생하면 팩파일을 불변 블롭으로 저장하고, 메타데이터 저장소에 새로운 팁(Tip), 해당 팩, 의존하는 이전 레퍼런스 버전을 포함하는 '레퍼런스 버전(Ref version)'을 기록합니다.
    • 클라이언트가 읽기 연산을 수행할 때 전체 리포지토리의 글로벌 순서는 보장되지 않으며, 서로 다른 브랜치를 동시에 조회하는 두 클라이언트가 각 브랜치에 대해 서로 다른 시점의 버전을 관찰할 수 있습니다. 단, 단일 레퍼런스 내에서는 변경 순서가 엄격히 유지됩니다.

  • 쓰기 및 읽기 연산 복잡도 및 동기화 메커니즘 [사실]

    • 푸시 파이프라인 및 쓰기 복잡도: 푸시 수신 시 Pando는 데이터를 로컬 리포지토리에 풀지 않고 **단일 패스 디코딩(Single pass decode)**으로 검증하면서 블롭 저장소로 직접 스트리밍합니다. 검증 완료 후 메타데이터 저장소의 레퍼런스 포인터를 변경할 때 **원자적 멀티 키 트랜잭션(Multi-key transaction)**을 사용하여 'Read-your-own-write' 일관성을 보장합니다. 이 연산은 메타데이터 읽기 및 쓰기에 있어 **$O(1)$**의 상수 시간 복잡도를 가집니다.
    • 대규모 푸시 시 메타데이터 처리: 매우 큰 푸시의 경우, 푸시 크기와 무관하게 $O(1)$ 연산 성능을 유지하기 위해 동기적(Synchronous) 메타데이터 업데이트 시에는 커밋의 일부 서브셋(Subset)만 기록하며, 컴팩션 스케줄링 등 기타 작업은 동일 트랜잭션 내 비동기(Asynchronous) 영역으로 분리하여 처리합니다.
    • 읽기 연산 복잡도: 클라이언트가 클론/패치 시 제시하는 haves(보유 커밋)와 wants(요청 커밋) 사이의 가장 짧은 레퍼런스 버전 거리를 $\Delta$라 할 때, 팩파일 선택을 위한 메타데이터 조회 복잡도는 **$O(\log \Delta)$**입니다.

  • 브랜치 광고 (Ref Advertisement) 전략 [사실]

    • 일반적인 Git 서버는 푸시 요청 시 수백만 개의 전체 레퍼런스를 광고하므로 광고 데이터만 100 MiB를 초과할 수 있습니다.
    • Pando는 신규 피처 브랜치 푸시 시 지정된 트렁크(Trunk) 브랜치 등 제한된 레퍼런스 집합만 클라이언트에 광고합니다.
    • 이로 인해 반복 푸시 시 트렁크 외의 변경 사항이 중복 전송되어 팩파일 용량이 커지는 트레이드오프가 발생하나, Pando 적용 모노레포에서 이 방식으로 생성된 팩파일 크기의 중위값은 20 KiB 미만, 99 percentile은 3 MiB 미만으로 집계되어 효율성을 입증했습니다.

  • 컴팩션 (Compaction)과 계층형 팩파일 (Skip List 색인) [사실]

    • LSM-tree(Log-structured merge-tree) 구조와 유사하게, 개별 푸시는 L0 팩파일을 생성합니다. 백그라운드 컴팩션 워커는 L0 팩파일들을 기하급수적 계층 구조(L0 ~ L4)의 팩파일 커버(Cover)로 병합합니다.
    • 이 계층 구조는 팩파일 내부 객체의 압축률을 높일 뿐만 아니라, 레퍼런스 버전에 대한 스킵 리스트(Skip list) 역할을 수행합니다. Pando는 각 계층의 색인을 동시에 스캔(Simultaneous index scan)하여 클라이언트에게 전송할 최적의 팩파일 집합을 대수 시간($O(\log \Delta)$) 내에 계산해 냅니다.
    • 기존 Git 서버와 달리, Pando는 컴팩션 후에도 이전 계층의 팩파일을 파기하거나 가비지 컬렉션(GC)하지 않고 모든 계층의 팩파일을 유지함으로써 다양한 요청 상태의 클라이언트에 동적으로 대응합니다.

  • 캐싱 인프라 체계 (Express Service) [사실]

    • 역할 및 구조: Express는 Pando의 읽기 성능을 결정짓는 핵심 지역 캐싱 계층으로, 블롭 저장소를 캐싱하는 Express 서비스와 메타데이터 저장소를 캐싱하는 별도 서비스로 구성됩니다.
    • packfile-uri 우회 메커니즘: Git 프로토콜은 패치/클론 시 단 하나의 팩파일만 HTTP 응답 본문에 전송할 수 있도록 제한되어 있습니다. Pando는 Git의 packfile-uri 기능을 활용하여 메인 HTTP 응답 본문에는 **"빈 팩파일(empty packfile inline)"**을 전송하고, 실제 복수 팩파일 데이터는 Express 캐시 서버의 URI 주소로 리다이렉트하여 다운로드하도록 처리합니다.
    • 대역폭 포화 성능: 일관성 해싱(Consistent hashing)을 통해 팩파일 요청을 Express 서버로 라우팅하며, 99% 이상의 디스크 캐시 적중률을 달성합니다. 이를 통해 서버 가용 대역폭을 최대로 활용하여 표준 클라우드 VM 환경에서 10 Gbps 네트워크 대역폭 포화(Line-rate fetch) 성능을 검증했습니다.
2.4. 구축, 검증 및 배포 (Building, Verification & Deployment)

  • Codex 및 에이전트 활용 [사실]

    • Pando의 핵심 아키텍처 설계는 단 1명의 엔지니어가 담당하였고, 구현은 에이전트 팀이 수행했으며, 수명의 엔지니어가 배포를 담당하여 킥오프부터 실운영 적용까지 10주 만에 완료했습니다.
    • 구현 언어로 Rust를 채택하였으며, 표준 Git 동작 검증을 위한 적합성 테스트 수트(Conformance test suite) 및 결정론적 시뮬레이션 테스트 환경을 구축했습니다.
    • GPT-6 Astra 모델을 활용하여 에이전트들이 Lean 및 TLA+ 언어로 Pando의 이론적 사양(Theory of Pando)을 수식화하고 정형 검증을 수행했습니다. 또한 Daybreak 지원 모델 기반 에이전트를 통해 Pando 및 Git 연동 부하에 대한 레드팀 테스트를 24시간 가동했습니다.

  • 무중단 배포 및 프록시 체계 [사실]

    • 초기 배포 시 Pando를 기존 버전 관리 시스템의 읽기/쓰기 대리 프록시(Read- and write-through proxy)로 배치하여 데이터를 동기화함으로써 서비스 중단 없이 이관을 진행했습니다.
    • Git CLI 내부 래퍼(Wrapper), 개발 환경 이관용 Codex 스킬(Skills), 외부 커스텀 도구 및 100여 개 이상의 기존 통합 연동 서비스를 단계적으로 마이그레이션했습니다.
    • 자체 배포용 Git 빌드를 엔지니어 작업 공간 및 ChatGPT 데스크톱 앱 내에 탑재하여 적용했습니다.

  • 성과 데이터 [사실]

    • 머지 신뢰도: 이관 전 86%~90% 수준에서 이관 후 99.99% 달성.
    • 푸시 지연 시간: 중위 지연 시간 약 80%(약 5배) 감소.
    • 데이터 전송량: 일일 약 1 페타바이트(PB) 전달. 피크 시간대 시간당 57 테라바이트(TB) 전송 (이 중 99% 이상이 로컬 디스크 캐시에서 처리됨).
    • 네트워크 대역폭: 표준 클라우드 VM 환경에서 클론 및 패치 연산 시 10 Gbps 네트워크 대역폭 포화 상태 검증.
2.5. Git 오픈소스 프로젝트 기여 (Upstream Contributions)

OpenAI는 Pando를 개발하며 발견한 문제점을 해결하고, 자체 Git 빌드(github.com/openai/git)에서 검증된 기능들을 공식 Git 업스트림 프로젝트에 기여했습니다 [사실].

  • packfile-uri 기능 관련 개선: 동시 다운로드 예외 처리, 중단된 전송의 정리 로직, 완료된 다운로드 재개 시 오류 수정 및 검증 로직 추가.
  • packfile-uri 다운로드 추적(Tracing) 및 팩 생성 시 바이트 수 계측 기능 추가.
  • 클라이언트 단에서 독립된 팩파일들을 병렬로 다운로드하고 색인(Indexing)하는 기능 구현.
  • 명시적 haves (Explicit haves) 개념 도입: 서버가 브랜치 팁을 독립적으로 광고할 수 있게 하여, 클라이언트가 --force-with-lease 옵션을 사용할 때 피처 브랜치의 변경 여부를 검증하면서 트렁크 기준으로만 최적화된 팩을 생성할 수 있도록 기여.

5. 한계와 불확실성 (Limitations & Uncertainties)

소스 문서에 기반하여 확인된 기술적 한계 및 정보의 불확실성은 다음과 같습니다 [사실].

  1. 약화된 일관성 모델(Causal Consistency)에 따른 브랜치 간 시점 불일치 (Technical Trade-off)
    • Pando는 브랜치별 직렬성은 보장하지만 리포지토리 전체에 대해 인과적 일관성을 적용합니다.
    • 이에 따른 기술적 한계(Trade-off)로, 클라이언트가 한 번의 클론이나 패치 과정에서 여러 브랜치를 동시에 조회할 경우 리포지토리 전체의 단일 시점(Point-in-time) 스냅샷을 보지 못하고 브랜치별로 상이한 시점의 상태를 관찰하게 될 수 있습니다. (다만 소스에서는 일반 개발자와 에이전트가 단일 레퍼런스의 변경 순서에 의존하므로 실제 워크플로우상 문제는 발생하지 않는다고 설명함).
  2. 구체적 내부 소스 코드 미공개 (Information Absence)
    • Pando 백엔드의 구체적인 내부 구현 소스 코드는 공개되지 않았습니다. ([소스 내 내용 없음 / 확인 불가])
  3. 사용된 타사 인프라 솔루션 명칭 미기재 (Information Absence)
    • Pando가 메타데이터 저장소(Metadata store) 및 블롭 저장소(Blob store)로 활용한 데이터베이스 제품명, 스토리지 솔루션 명칭은 언급되지 않았습니다. ([소스 내 내용 없음 / 확인 불가])
  4. 외부 공개 및 상용화 일정의 불확실성 (Uncertainty)
    • OpenAI는 Pando 기술을 외부 사용자들과 공유할 방법을 모색(exploring ways) 중이라고 언급했으나, 오픈소스화 시점이나 별도 상용 제품화에 대한 구체적 일정 및 계획은 명시되어 있지 않습니다. ([소스 내 내용 없음 / 확인 불가])
