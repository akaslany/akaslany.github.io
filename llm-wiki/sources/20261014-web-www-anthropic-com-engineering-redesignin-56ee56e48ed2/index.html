1. 개요 (Overview)

[사실] Anthropic에서는 코드 생성 AI인 Claude가 연구 루프 반복, 프로그램 최적화, 신규 서비스 구축 등을 자율적으로 수행함에 따라 인간 개발자 규모에 맞춰 구축되었던 기존 소프트웨어 개발 인프라(버전 관리, 빌드, CI)가 전체 시스템의 주요 병목 요인으로 부상했습니다. 2026년 5월 Anthropic의 단일 리포지토리(Monorepo) 내 일일 코드 병합 건수는 평균 약 2,500건 수준이었으나, 불과 4개월 후인 2026년 9월에는 일일 30,000건 이상으로 10배 이상 폭발적으로 증가했습니다.

[소스의 주장] 코드 생성 AI의 발달로 소프트웨어 작성 과정 자체는 더 이상 병목이 아니며, 인프라 병목을 제거할 때마다 코드 생산량이 더욱 가파르게 증가하는 잠재적 수요가 존재합니다. 따라서 무제한에 가까운 코드 생성 및 병합 요구를 수용하기 위해 인간 중심의 전통적 버전 관리 체계에서 벗어난 새로운 차원의 인프라 전환이 필수적이었습니다.

[작성자 해석] 이러한 요구에 대응하여 Anthropic은 인하우스 버전 관리 시스템인 'Scion'을 구축하고, 단 5개월 만에 대규모 단일 리포지토리를 Git에서 Scion으로 성공적으로 완전 마이그레이션했습니다. 이 과정에서 코드 리뷰 플랫폼인 'Antique', 코드 검색 시스템, 소스 컨트롤 전용 IAM(식별 및 권한 관리) 체계, 대량의 리뷰 완료 코드를 안전하게 반영하기 위한 머지 인프라 등 관련 도구 생태계 전체를 동시에 재설계 및 구축해 냄으로써 에이전트 규모(Agent-scale) 소프트웨어 엔지니어링 환경을 구현했습니다.

2. 주요 논점 및 세부 분석 (Key Issues & Detailed Analysis)
2.1. 기존 Git 시스템의 한계와 에이전트 규모(Agent-Scale) 환경의 특성

[사실]

  • 단일 리포지토리 규모: Anthropic의 단일 리포지토리는 메인 브랜치의 이력 용량만 약 100 GB에 달하며, 압축된 작업 복사본(Working copy)의 크기조차 25 GB 이상을 차지합니다.
  • 트래픽 및 연산 수치: 개발자 환경, 에이전트 샌드박스, 연구 작업을 제외하고도 지속적 통합(CI)을 위한 코드 체크아웃 횟수만 일일 약 2,500만 회에 달합니다. 최적화 없이 단순 방식으로 데이터를 가져올 경우 일일 발생 예상 Git 트래픽은 600 PB 이상입니다.
  • 기존 우회책과 운용 한계: 얕은 복제(Shallow clone), 희소 체크아웃(Sparse checkout), 프로미서 리모트(Promisor remotes) 등 Git의 자체 기능과 함께, 수백 대의 내부 Git 미러 서버 운용, Blob 스토리지 기반 리포지토리 스냅샷(Seed) 활용 등 다각도의 우회책을 적용했습니다. 그러나 메인 브랜치의 갱신 속도가 극도로 빨라지면서 Seed와 메인 브랜치 최신 지점 간의 격차가 빠르게 벌어졌고, 부분 복제본(Partial clone) 상태에서 이력 추적(blame) 및 변경 사항 비교(diff) 연산의 계산 복잡도와 장애 발생률이 지속적으로 증가했습니다.

[소스의 주장]

  • Git은 모든 클라이언트가 독립된 완전한 리포지토리 복사본을 유지하고 오프라인 상태에서도 diff, 이력 조회, blame, 커밋 체크아웃 등을 수행할 수 있도록 설계된 분산형 구조입니다. 그러나 상시 온라인 상태인 AI 에이전트와 자동화 작업이 주를 이루는 대규모 단일 리포지토리 환경에서는 Git의 중앙집중식 실제 운용 형태와 분산형 설계 전제 사이의 불일치가 확장성의 근본적인 장애물로 작용합니다.
  • 따라서 '클라이언트 에이전트는 항상 온라인 상태에 있다'는 현실적 전제하에 소스 컨트롤 아키텍처를 원점에서 새로 설계해야 한다는 필요성이 도출되었습니다.

[작성자 해석] 전통적인 Git 아키텍처에서는 클라이언트가 전체 리포지토리 상태를 보유하려고 시도하므로, 수백만 건의 자율적 에이전트 작업이 일일 2,500만 회 이상의 체크아웃을 수행할 경우 네트워크 대역폭(Bandwidth)과 클라이언트 메모리에 리포지토리 크기에 비례하는 막대한 비용 부담이 발생합니다. 100 GB의 이력과 25 GB의 작업 복사본을 갖춘 리포지토리에서 매 체크아웃마다 델타 압축 팩파일(Packfile)을 재계산하거나 대용량 데이터를 전송하는 방식은 에이전트 규모 개발 환경에서 인프라 병목을 초래합니다.

2.2. Scion의 핵심 설계 원칙 및 데이터 구조

[사실] Scion은 Google의 Piper 및 Meta의 Sapling 등 대규모 소스 컨트롤 시스템의 아키텍처 경험을 참조하여 다음과 같은 6가지 핵심 설계 원칙을 정립했습니다.

  1. 클라이언트의 상시 접속 (Clients are always online): 클라이언트가 항상 서버에 접속할 수 있다고 전제하여, 클라이언트에 전체 복사본을 두지 않고 필요한 시점에 서버로부터 동적으로 데이터를 전달받도록 설계합니다.
  2. 클라이언트-서버 비대칭성 (Client-server asymmetry): 서버가 파일 이력 및 blame 조회, 커밋 생성, 병합, 리베이스 등 정밀한 핵심 연산을 전담합니다. 클라이언트는 용량이 제한된 로컬 객체 캐시 유지, 디스크 내 작업 복사본 배치, 파일시스템 변경 감지 등 최소한의 역할만 수행하여 로컬 데이터 요구량을 획기적으로 줄입니다.
  3. 포괄적 API 기반 응용 (A comprehensive source control service can power many novel applications): 소스 컨트롤의 모든 쿼리를 API로 노출하여, CI 작업이나 자동화 도구(자동 디버깅 및 롤백 파이프라인 등)가 로컬 리포지토리 전체를 복사하지 않고도 필요한 정보에 프로그래밍 방식으로 원격 접근할 수 있게 합니다.
  4. 수평적 확장성 (Everything must be horizontally scalable): 리포지토리 데이터를 분산 처리하며, 서버나 클라이언트 어디에도 완전히 구체화된 리포지토리 복사본이나 Git 스타일의 팩파일(Packfile)을 유지하지 않아 리포지토리 유지보수(Maintenance) 부담을 제거합니다.
  5. 저렴하고 증분적이며 잠금 없는 커밋 (Commits must be cheap, incremental, and lock-free): 모든 커밋, 리베이스, 병합 연산이 서버 측에서 실행되며, 연산 비용은 전체 리포지토리 크기가 아닌 오직 변경 사항의 크기(Size of the change)에 비례합니다. 전역 동기화 병목을 방지하기 위해 메인 브랜치 등 필수적인 경우를 제외하고는 참조(refs)의 생성을 지양합니다.
  6. 선택적·가상화된 희소 체크아웃 (The working copy is optional, and sparse by design): 불필요한 체크아웃 자체를 최소화하며, 클라이언트가 요청한 디렉토리만 포함하는 희소 체크아웃(Sparse checkout)과 파일 접근 시 동적으로 생성하는 가상화 체크아웃(Virtualized checkout)을 기본 구조로 채택합니다.

[소스의 주장]

  • 체인지셋(Changeset) 구조: Scion의 기본 작업 단위는 선행 기록 로그(Write-ahead log)의 항목인 '체인지셋'입니다. Git 커밋이 트리를 직접 가리키는 것과 달리, 체인지셋은 첫 번째 부모(First parent) 대비 변경된 파일 목록과 Blob 스토리지 내 압축 컨텐츠를 가리키는 콘텐츠 주소 지정(Content-addressed) 포인터를 저장합니다. 서버 측에서 즉시 생성되어 전역 공유되며, 팩파일 생성이나 서버 간 동기화 잠금이 필요 없습니다.
  • 첫 번째 부모(First parent) 추적의 당위성: 변경 사항을 첫 번째 부모 단일 기준 상대 경로로 저장하는 것은, 단일 리포지토리 기반 트렁크 개발 모델(Trunk-based development)에서 주 메인 라인의 이력과 blame 조회가 핵심이라는 점을 반영한 의도적 설계 선택입니다.
  • 참조(Refs) 업데이트 메커니즘: Scion은 참조 활용을 제한하지만, 메인 브랜치 등 전역 참조 이동이 필요한 경우 체인지셋 생성 연산과 완전히 분리하여 단일 Spanner 행에 대한 Compare-and-swap(단일 행 비교 및 교환 연산)을 통해 처리합니다.
  • 파생 데이터(Derived Data) 계산 메커니즘: 체인지셋 단독으로는 blame이나 파일 경로 이력을 즉시 추적할 수 없으므로, blame 구조, 경로 이력, 커밋 그래프 스킵 리스트 등의 '파생 데이터'를 범용 재귀 메커니즘을 통해 부모 체인지셋으로부터 계산합니다. 파생 데이터는 필요에 따라 즉시 계산(Eager)하거나 연기(Defer)할 수 있어, 클라이언트 변경 없이 새로운 인덱스(복사 감지, 경로 기반 검색 등)를 서버 측에서 유연하게 추가할 수 있습니다.

[작성자 해석] Scion의 데이터 구조는 불변 데이터(Write-ahead log 형태의 체인지셋)와 가변 상태(Spanner 단일 행 Compare-and-swap 참조 연산)를 명확히 분리함으로써, 대규모 병렬 에이전트 환경에서 발생하는 동시성 충돌 및 쓰기 병목을 해소했습니다.

2.3. 계층형 아키텍처 및 성능 최적화 성과

[사실]

  • 아키텍처 구성: Scion은 클라이언트 CLI(scn), 노드 대몬(scion-daemon), 지역 캐시 서버(scion-cache), 권한 보유 원천 서버(scion-server)로 구성된 계층 구조를 가집니다.
  • 객체 협상 및 Caching 프로토콜: Scion은 Git처럼 클라이언트의 보유 상태를 서버에 전송하는 델타 압축 협상 방식을 사용하지 않습니다. 클라이언트는 루트 트리부터 시작하여 필요한 트리와 블롭(Blob)의 콘텐츠 주소 지정 해시(Hash) 값을 확인하고, 로컬에 없는 객체만을 재귀적(Recursive)으로 요청합니다.
  • 장애 격리 구조(Failure Domain Isolation): 모든 계층(scion-daemon, scion-cache, scion-server)은 동일한 RPC 인터페이스에 응답하므로 이론적으로는 모든 계층 간 직접 통신이 가능하지만, 지역 캐시(scion-cache) 장애 발생 시 권한 서버(scion-server) 및 백엔드 Spanner 데이터베이스로 장애가 전파(Cascading failure)되는 것을 차단하기 위해 엄격한 계층 구조 통신 통제를 적용합니다.

Scion 도입을 통해 기존 Git 미러링 인프라 대비 거둔 정량적 최적화 성과는 아래 표와 같습니다.

평가 항목 기존 Git 인프라 대비 성과 / 정량적 측정값
인프라 자원 사용량 (CPU 및 메모리) 기존 Git 미러링 인프라 대비 200배 감소
CI 및 연구 작업 코드 체크아웃 속도 분(Minutes) 단위에서 초(Seconds) 단위로 단축 (100배 이상 향상)
클러스터 전체 CI CPU 용량 확보 클러스터 전체 CI CPU 용량 25% 확보

[소스의 주장]

  • 각 대몬(scion-daemon)은 주기적 스냅샷에서 출발하여 지역 캐시(scion-cache)와 통신하고, 캐시는 메모리 상에서 대몬이 소비할 디스크 포맷 형태로 객체를 직접 스트리밍하므로 델타 압축 연산에 CPU를 소비하지 않습니다.
  • 모든 객체 요청은 불변의 콘텐츠 주소 지정 객체에 대한 것이므로 캐시 무효화 통신이 필요 없으며, 계층별 99% 이상의 캐시 적중률을 달성하여 수평 확장이 가능해졌습니다.

[작성자 해석] 대규모 분산 환경에서 캐시 둔화와 서버 과부하를 막는 핵심은 델타 압축 연산을 배제하고, 불변 객체 중심의 해시 기반 재귀 요청 및 엄격한 계층적 장애 격리(Failure domain isolation)를 구축하는 것에 있음을 보여줍니다.

2.4. AI 에이전트 활용 개발, 보안 및 조직 운용에 미친 영향

[사실]

  • 개발 및 마이그레이션 추진 규모: 단 7명의 엔지니어로 구성된 소규모 팀이 Claude를 활용하여 Scion, Antique(코드 리뷰 플랫폼), 소스 컨트롤 IAM, 머지 인프라 등 제반 생태계를 5개월 만에 구축하고 완전 마이그레이션을 완수했습니다.
  • Claude Mythos Preview를 통한 파이프라인 최적화: 초기에 수작업으로 작성했던 Git-to-Scion 수집 파이프라인 프로토타입을 사내 초기 스냅샷 버전인 Claude Mythos Preview에게 재작성을 요청한 결과, 암묵적 순서 보존 규칙 및 데이터 구조 불변성을 유지하면서 메모리 사용량 20배 절감 및 처리 속도 4배 향상이라는 최적화를 이뤄냈습니다.

[소스의 주장]

  • 단일 리포지토리 보안 및 세부 권한 제어: Scion은 설계 초기부터 단일 리포지토리의 보안과 컴플라이언스를 고려하여 구축되었습니다. 전체 리포지토리 권한 관리는 물론, 민감한 코드를 보호하기 위해 단일 리포지토리의 장점을 유지하면서도 특정 디렉토리 단위의 미세 세부 권한(Directory-level permissions)을 적용할 수 있습니다.
  • Antique의 의미론적 승인 제어(Semantic Approval Constraints): 새롭게 구축된 코드 리뷰 플랫폼 Antique는 코드 변경 유형에 대한 복잡한 의미론적 제약 조건을 지원합니다. 단순 주석 수정(Comment-only edits)과 같은 비기능적 변경과 시스템 핵심 로직 변경(Sensitive logical changes)을 구별하여 처리함으로써, 인간 리뷰어가 가장 중요한 변경 사항에 집중할 수 있도록 돕습니다.
  • 엔지니어 역할의 근본적 전환: Claude의 코드 작성 능력이 인간 엔지니어를 능가함에 따라, 엔지니어의 역할은 직접적인 코드 구문 작성에서 시스템 고위상 아키텍처 설계, 제약 조건 설정, 트레이드오프 결정, 변경의 "의도(Intent) 검토"로 전환되었습니다. 엔지니어의 핵심 역할 중 하나는 AI가 제시하는 시스템의 과잉 엔지니어링(Over-engineering)이나 불필요한 규칙 위반 시도에 대해 "아니오(No)"라고 제어하는 것입니다.
  • 운용 방식의 혁신 (슈퍼팬 모니터링): Claude Tag를 활용하여 특정 시스템 컴포넌트(scion-daemon, scion-cache, Antique merge queue 등)의 텔레메트리 및 로그 모니터링을 전담하는 전용 AI 에이전트("슈퍼팬", Superfans)를 Slack 채널에 각각 배치했습니다. 이들은 지속적으로 차트와 로그를 관찰하여 단순 다차원 경보 시스템이 포착하기 어려운 미세하고 복잡한 이상 징후를 감지합니다.
  • 머지 큐 및 CI 관념의 재정의: 수천 건의 에이전트 변경이 동시 다발적으로 일어나는 환경에서는 전통적인 글로벌 리포지토리 잠금(Global repository lock) 기반 머지 큐가 불가능하므로, Post-merge(병합 후) 및 Pre-deploy(배포 전) 자동 테스트 체계로 전환했습니다. 동시 병합으로 발생하는 코드 충돌은 Claude가 동적으로 즉시 수정하도록 조치합니다.

[작성자 해석] AI 에이전트 시대의 엔지니어링은 '코드 생성'에서 '제약 조건 및 의도 통제'로 패러다임이 이동했음을 보여주며, 보안 제어 역시 정적 파일 접근 권한을 넘어 코드 변경의 의미(Semantic)를 파악해 승인 절차를 가등화하는 방향으로 진화하고 있습니다.

5. 한계와 불확실성 (Limitations & Uncertainties)

[사실]

  • 범용 소프트웨어로서의 한계: Scion은 일반적인 Git의 완전한 대체재가 아닙니다. 수만 명의 엔지니어나 대규모 AI 에이전트 군집이 폭발적으로 코드를 생성하는 극단적 규모의 단일 리포지토리 환경에 특화되어 있습니다.
  • 독자적 커스텀 생태계 결합 문제: Scion은 Anthropic 내부의 코드 리뷰 도구(Antique), 코드 검색, CI 파이프라인과 깊게 결합(Bespoke)되어 있어, 외부 조직이 단독 패키지로 즉시 도입하거나 오픈소스로 활용하기 어렵습니다.

[소스의 주장]

  • 광범위한 오픈소스 및 개발자 생태계 제언: Anthropic은 독자적인 Scion 전체 시스템을 패키지 형태로 공개하는 대신, Git 오픈소스 커뮤니티(GitHub, GitLab, OSS 커뮤니티 등)에 다음과 같은 아키텍처적 기여 방향을 제안하고 있습니다.
    1. 서버 측 RPC 표준화: Git 클라이언트와 서버의 작동 방식을 분리하여, 여러 플랫폼(Forges) 전반에 걸쳐 표준화된 서버 측 RPC를 제공하고 Git 클라이언트가 이를 직접 활용할 수 있도록 지원.
    2. 객체 협상 프로토콜 개선: 무거운 델타 압축 팩파일 응답 대신, 희소(Sparse) 및 얕은(Shallow) 기능이 결합된 협상 프로토콜 도입.
    3. 서버 아키텍처 개선: Git 모델을 완전히 폐기하지 않고도 Scion의 불변 객동 Caching 및 계층화 아키텍처 개념을 기존 Git 플랫폼 서버에 이식.

[작성자 해석 및 미확인 항목]

  • 구체적 스토리지 사양 미확인: Scion 서버가 메타데이터 및 참조 관리용으로 사용한 Google Cloud Spanner 외에, Blob 객체 수집에 사용된 클라우드 스토리지의 구체적 제품 사양이나 분산 DB 인덱스 세부 구조는 소스 상에 명시되지 않아 확인 불가합니다.
  • 내부 구현 코드 미확인: Antique, 코드 검색, 소스 컨트롤 IAM 등의 세부 알고리즘 및 구체적 소스 코드는 소스 상에 명시되어 있지 않아 확인 불가합니다.
  • 팀원들의 공식 직책 미확인: 작성자 Nick G. 외 소스 컨트롤 팀원(S.G., R.K., Dan C., Garrett H., Ben L., Colin M., Joe P.) 및 지원 인물(Vilas J., Sergiu D.)의 사내 공식 직책 및 구체적 업무 분담 내용은 소스 상에 기술되지 않아 확인 불가합니다.
