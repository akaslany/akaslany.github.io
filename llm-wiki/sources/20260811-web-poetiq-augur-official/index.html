2. Augur가 해결하려는 문제: 고정형 벤치마크의 한계와 도메인 특화 배포

기존의 '고정된 리더보드(Fixed leaderboard)'는 실제 기업의 '도메인 특화 배포(Domain-specific deployment)' 환경에서 발생하는 성능 병목을 진단하는 데 한계가 있습니다. 공개 리더보드에서 상위를 차지한 모델이 언더라이팅, 임상시험 문서, 고객 운영 등 고도의 전문성을 요하는 비즈니스 도메인의 실질적 성패를 예측하기 어렵기 때문입니다. Augur는 특정 도메인 내에서 각 모델의 성공과 실패 지점을 동적으로 파악하여, 기업이 실제 과업에 적합한 모델을 선택할 판단 근거를 제공하고자 합니다.

3. 동적 프로브(Dynamic Probe)를 통한 모델 경계 탐색 방식

Augur는 고정된 질문 세트에 의존하지 않고, 모델의 능력이 끝나는 지점(Capability boundary)을 찾기 위해 질문을 점진적으로 정교화하는 '날카롭게 만들기(Sharpening)' 메커니즘을 사용합니다.

  • 기술적 차별점과 경계: Poetiq은 동적으로 생성되는 benchmark는 모델이 암기할 수 없다고 강하게 주장합니다. 동적 질문은 고정 question set 암기 위험을 낮출 수 있지만, 그것만으로 사전학습 노출, 생성기 leakage, contamination, 반복 probe의 패턴 학습이 불가능하다고 입증되지는 않습니다. 따라서 여기서는 제품 설명상 모델이 '어디까지 견딜 수 있는지'를 찾는 스트레스 테스트로 이해하되, 오염 내성은 독립 검증 과제로 남깁니다.

4. 능력 측정의 세 가지 차원: 지식, 도구, 추론

Poetiq은 모델의 실패를 명확히 구분하기 위해 다음 세 가지 핵심 차원을 정의합니다.

  • 지식(Knowledge): 외부 도구의 도움 없이 내부 메모리(Internal memory)만으로 팩트를 인지하고 있는지 여부.
  • 도구(Tools): 모델 간 의견이 불일치할 때 실시간 검색 등 외부 도구로 해결 가능한지, 아니면 팩트 자체가 출처 간에 경합 중(Contested)인지 여부.
  • 추론(Reasoning): 개별 팩트를 논리적으로 조합하여 하나의 정답을 도출하는 능력.

5. '3 대 verified 2' 도식: Five-Right-Facts-One-Wrong-Answer

Poetiq은 원자적 팩트는 인지하고 있으나 조합에 실패하는 '추론 실패' 사례를 다음과 같이 도식화하여 설명합니다.

  • [질문] 특정 시점(Year-Y)에 재임 중이던 A~E사 CEO 중 N년 후에도 직을 유지 중인 인원은 몇 명인가?
  • [검증된 개별 응답] 5명의 CEO와 각각의 재임 여부에 관한 원자적 질문에는 모두 정확히 답변함. 이는 숨은 사고 과정을 재현한 것이 아니라 공개된 입출력 수준의 schematic입니다.
  • [모델 답변] "총 3명입니다."
  • [실제 정답] "2명" (Verified answer)
  • [실패 원인] 개별 지식은 보유했으나, 이를 카운트하거나 논리적으로 연결하는 '추론 과정'의 붕괴.

6. Poetiq의 모델 라우팅 휴리스틱(Company Routing Heuristic)

Augur는 실패 유형에 따라 모델 개선 경로를 제안합니다.

  • 지식 격차(Knowledge Gap): SFT(지도 미세 조정) 또는 프리트레이닝 데이터로 활용.
  • 추론 실패(Reasoning Failure): 강화학습(RL) 과제로 전환. Poetiq은 위 CEO 사례처럼 검증 가능한 exact-match reward가 있고 모델이 원자적 지식을 보유한 사례를 RL에 적합한 후보라고 설명합니다. 이것은 회사의 routing heuristic이며, 모든 reasoning failure에 자동으로 최적인 학습법이라는 독립 결론은 아닙니다.
  • 경합 소스(Contested Source): 데이터셋 오염 방지를 위해 폐기(Discard).

주의: '팩트를 모르면 RL 리워드가 항상 0이라 학습이 불가능하다'는 주장은 도구 사용이 배제된 단순화된 논리이며, 일반적인 강화학습의 모든 사례에 적용되는 보편 법칙은 아닙니다.

7. 도메인별 불일치 분석 데이터 (Poetiq 자체 측정치)

다음은 Poetiq이 DeepSeek-V4와 여러 OpenAI closed model을 비교했다고 설명한 자체 측정 결과입니다. 정확한 모델 version·snapshot, evaluation set 크기와 sampling은 공개되지 않았습니다.

  • 단일 팩트 불일치 중 실제 지식 격차(Genuine Knowledge Gap) 비율:
    • 하드웨어 68%, 비디오 게임 52%, 소프트웨어 51%, 법률 34%, 음악 30%.
  • 도구 사용 후에도 남은 disputed facts:
    • 음악 27%, 법률 9%, 소프트웨어 9%.
    • 비판적 분석: 글은 앞선 single-fact disagreement의 나머지를 contested source 또는 재샘플링 시 뒤집히는 instability로 구분하지만, 위 27%·9%·9%의 정확한 분모, sample 수, 검색 도구와 source adjudication 절차를 공개하지 않습니다.
  • 전체 불일치 중 '추론 능력 차이' 비율 (원자적 팩트는 같으나 종합 답안이 다른 경우):
    • 법률 58%, 비디오 게임 48%, 음악 43%, 소프트웨어 40%, 하드웨어 32%.
  • 모델 간 불일치가 전혀 없었던 질문 비율:
    • 하드웨어 약 20%(1/5), 음악 약 40%(2/5).

8. 모델 쌍의 도메인 특화 유사성 및 상호운용성

Poetiq은 모델 간 '교체 가능성(Interchangeable)'이 고정된 속성이 아니라 '특정 과업'에 종속된다고 주장합니다. 특정 도메인에서 두 모델이 유사한 성능을 보일지라도, 다른 도메인에서는 성능 차이가 급격히 벌어질 수 있으므로 과업별로 상호운용성을 재측정해야 한다는 시각입니다.

9. 케이스 스터디: Kimi K3 vs K2.6 및 금융 과업

Kimi K3 모델에 대한 분석 결과는 엔터프라이즈 배포 시 중요한 시사점을 제공합니다.

  • K3의 성능 특징: Poetiq은 단순 팩트 회상이 테스트한 대부분 도메인에서 major frontier model과 유사했으나, 기후 변화(Climate change)는 그 유사성이 성립하지 않은 notable exception이라고 보고합니다. 원문만으로 성능 하락의 절대 크기나 원인은 알 수 없습니다.
  • 추론 실패의 본질: K3가 추론에 실패하는 사례 중 75% 이상은 이미 모든 원자적 팩트를 알고 있는 상태였습니다.
  • 세대 간 비교: K2.6 대비 실제 지식 격차는 약 3/4 감소했습니다. 그러나 난독화된 C 및 파이썬 코드(Obfuscated C and Python) 영역은 이미 한계치에 도달했던 K2.6와 유사한 수준을 유지했습니다.
  • 금융 과업: 임원 이력이나 M&A 관련 과업에서 팩트 보유량은 높으나, 이를 조합하여 통계를 내거나 체인을 추적하는 능력이 부족했습니다.

10. 아키텍처 패턴: 동적 벤치마크, LoRA 및 RSI 루프

  • Benchmarking / Model Routing: 모델 평가 및 선택 프로세스.
  • Training-data Generation: SFT/RL용 고신호 데이터 추출.
  • Augur + LoRA: 지식 및 추론 맵에 따라 경량 어댑터를 동적으로 교체하는 아키텍처를 제안합니다. 이는 '비용 효율성'과 '모듈성' 측면에서 가치가 있으나, 아직 엔드투엔드 벤치마크로 성능이 완전히 입증된 것은 아닙니다.
  • Recursive Self-Improvement (RSI): Poetiq은 경계 mapping → data generation → training → re-measurement를 자율 loop로 설명하고 Metasystem이 Augur의 probing efficiency도 최적화한다고 주장합니다. 그러나 benchmarking, model routing, data generation, 실제 SFT/RL 성능 향상, 개선 절차 자체의 반복 개선은 서로 다른 단계입니다. 이 글만으로 strong RSI가 구현·입증됐다고 볼 수 없습니다.
  • Catastrophic Forgetting: Augur는 학습으로 인해 파괴된 기존 능력을 탐지하고 이를 복구하기 위한 데이터를 제공한다고 설명합니다.

11. 구현 및 검토 체크리스트 (Reproduction Checklist)

실제 도입 검토를 위해 아키텍트가 확인해야 할 핵심 항목들을 카테고리별로 제안합니다.

[데이터 및 모델 검증]

  • Exact model version & snapshot
  • Sample size & Domain sampling
  • Contamination & Holdout test
  • Confidence interval (신뢰 구간)

[학습 및 최적화 검증]

  • Prompt generator & Sharpening depth 분포
  • Resampling strategy, repeated runs & Instability 판정 규칙
  • Source trust hierarchy & Contested-source adjudication
  • Target gain vs Unrelated-domain regression (목표 외 영역 성능 저하 여부)
  • Reward hacking prevention

[운영 및 보안 검증]

  • Tool/search budget & Latency
  • Cost-effectiveness of LoRA swap
  • Privacy/Access control/Deletion/Audit logging
  • Human-in-the-loop audit protocol

12. 최종 주의사항

본 브리핑은 Poetiq의 1차 자료를 분석한 것으로, '동적 생성'만으로 오염이 원천적으로 불가능하다고 단정할 수 없습니다. 'Single most efficient', 'Autonomous', 'Exact data', 'Real errors' 등의 표현은 Poetiq사의 주장으로 귀속하여 해석해야 합니다. Augur가 제안한 중요한 아이디어는 점수표보다 실패 경계를 찾아 훈련 데이터로 연결하는 것입니다. 아직 확인할 것은 그 경계 판정과 실제 개선이 독립적으로 재현되는가입니다. 본 문서는 투자나 제품 구매 권유가 아니며 숨은 chain-of-thought를 재현하지 않고 공개된 상위 메커니즘 분석에 집중합니다.
