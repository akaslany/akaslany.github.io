본 보고서는 Pi AgentHarness v2의 아키텍처 설계 사양과 상세 구현 계획을 수석 시스템 아키텍트의 관점에서 분석한 기술 문서입니다. 본 문서는 분산 에이전트 환경에서 시스템 내구성을 보장하기 위한 상태 관리 규칙, 실행 모델, 복구 메커니즘 및 확장 체계에 대한 엄격한 명세를 정의합니다.

1. 문서의 성격 및 증거 등급 (Nature of Document & Evidence Grade)

본 문서는 Durable AgentHarness v2의 설계 사양(Design Specification) 및 **구현 계획(Implementation Plan)**을 정의하며, 시스템 아키텍처의 목표, 타입/저장소 계약, 불변식(Invariants), 그리고 충돌 지점(Crash-site)별 복구 의미론을 다룹니다.

본 보고서의 모든 기술적 사실은 GitHub 커밋 f7f933c6e0a127bd2b56336338512092fec0399d 시점의 소스 컨텍스트를 절대적 근거로 합니다.

주의 및 경고: 본 문서에 기술된 설계상의 보장(Guarantees)과 목표(Goals)는 시스템이 지향하는 기술적 계약입니다. 이를 현재의 실제 구현 완료 상태, 테스트 통과 여부, 또는 실운용 환경(Production)에서의 검증 증거와 동일시해서는 안 됩니다. 특히 문서 하단에 명시된 H/J/R/I/C/N/O 구현 트랙 중 체크되지 않은 항목은 실체화되지 않은 설계 단계의 기능임을 명확히 인지해야 합니다.

2. 네 가지 세션 상태의 역할과 분리 (Architecture of Four Session States)

AgentHarness v2는 세션 상태를 네 가지 범주로 분리하여 관리합니다. 이는 '능동적(Active)' 상태와 '수동적(Passive)' 상태를 엄격히 분리함으로써 시스템 복잡성을 제어하고 복구 정합성을 유지하기 위함입니다.

  1. 공유 추가 전용 트리 (Shared Append-only Tree): 대화의 엔트리(메시지, 모델 생각, 도구 활성화 등)만을 담는 수동적(Passive) 데이터 구조입니다. 부모 체인(Parent chain)은 불변이며, 대화 외의 레인 상태나 오케스트레이션 기록을 포함하지 않는다는 강력한 불변식을 가집니다.
  2. 레인 (Lanes): 실제 작업이 수행되는 능동적(Active) 단위입니다. 각 레인은 이름과 현재 위치(Leaf)를 가지며 세션 내에서 독립적인 실행 지점을 형성합니다.
  3. 레인별 작업 로그 (Per-lane Operation Logs): 내구성 구현의 핵심으로, 작업 시작, 단계 시도, 도구 시작/완료 등 복구에 필요한 실행 의도(Intent)를 기록합니다. 정상 실행 중에는 읽지 않으며, 오직 복구 시에만 참조되는 능동적 상태입니다.
  4. 전역 사실 (Global Facts): 세션 이름, 엔트리 라벨 등 세션 범위의 설정 값입니다. 추가 전용 이력을 유지하되 조회 시 최신 값을 반환하는 수동적 상태입니다.

이 구조의 핵심 불변식은 **"오퍼레이션 로그 레코드는 트리에 영향을 주지 않는다"**는 점입니다. 로그를 모두 삭제하더라도 유효한 대화 트리는 보존되어야 하며, 트리에 대화 외의 상태를 넣지 않음으로써 데이터 오염을 원천 차단합니다.

3. 실행 모델: 병렬성 및 단일 작성자 원칙 (Execution Model: Parallelism & Single Writer)

시스템은 효율적인 작업 처리를 위해 병렬 실행을 지원하면서도, 데이터 정합성을 위해 엄격한 단일 작성자(Single Writer) 모델을 채택합니다.

  • 병렬 레인 실행: 하나의 세션 내에서 여러 레인이 병렬로 실행될 수 있습니다. 예를 들어, 슬랙 채널이 세션이라면 각 스레드는 독립적인 레인이 되어 동시에 작업을 수행합니다.
  • 단일 작성자(Single Writer) 원칙: 하네스 하나가 한 번에 하나의 세션만 작성할 수 있습니다. 서빙 레이어는 특정 세션에 대한 모든 트래픽을 해당 하네스를 보유한 단일 프로세스로 라우팅하여 멀티 라이터 충돌을 방지합니다.
  • 레인 뮤테이션 라인(Lane Mutation Line): 각 레인의 상태 변경 작업은 프로세스 내 로컬 FIFO(Promise Chain)인 '뮤테이션 라인'을 통해 선형화(Linearized)됩니다. 이는 **"검증(Validate) → 내구성 있는 쓰기(Durable Write) → 메모리 상태 업데이트(Update State)"**의 3단계 모델을 따르며, 결정 단계에서 데이터가 최신 상태임을 보장하여 경쟁 상태(Race Condition)를 차단합니다. 각 레인은 최대 하나의 'Open Operation'만 가질 수 있습니다.

4. 내구성 메커니즘: Intent-before-effect (Durability Mechanism)

시스템 내구성의 핵심 철학은 '효과 발생 전 의도 기록(Intent-before-effect)' 규칙에 있습니다.

  1. 의도 기록 및 Provisioned ID: 외부 효과(Provider 요청, 도구 실행 등)가 발생하기 전, 시스템은 수행할 작업의 유형과 결과로 생성될 엔트리 ID(Provisioned ID)를 로그에 먼저 기록합니다.
  2. 결과 확정: 외부 효과가 성공적으로 수행되면, 미리 할당된 ID를 사용하여 결과 엔트리를 트리에 추가(Append)합니다.
  3. 복구 시 결정 로직: 충돌(Crash) 발생 시, 로그에는 의도(Intent)가 있으나 트리에는 결과(Entry)가 없는 상태가 발견될 수 있습니다. 복구 프로세스는 유형에 따라 다음 중 하나를 선택합니다.
    • Complete: 기록된 의도를 바탕으로 작업을 완료.
    • Retry: 작업을 재시도 (멱등성이 보장되거나 안전한 경우).
    • Synthetic Result: "중단됨(Interrupted)"과 같은 인위적인 결과로 작업을 종결하여 상태 불일치를 해소.

이 메커니즘은 '부분적 결과(Partial Outcomes)'가 절대 관찰되지 않도록 보장합니다.

5. 결정론적 테스트: Manual Drive의 설계 목적 (Deterministic Manual Drive)

시스템은 신뢰성 검증을 위해 drive: "manual" 모드를 제공합니다. 이는 프로덕션과 동일한 절차를 제어 가능한 경계(Boundary) 단위로 구동하기 위한 장치입니다.

  • 주입된 경계(Injected Boundary): Durable Write, Provider 요청, 도구 실행, Hook 호출, 타이머 등 모든 외부 효과는 주입된 경계를 통과합니다.
  • 제어 프리미티브: Manual Drive 모드에서 하네스는 각 외부 효과 직전에 실행을 멈춥니다(Park). 테스트 코드는 peekAction()으로 다음 단계를 관찰하고, executeAction()으로 한 단계씩 진행하거나 runToCompletion()으로 전체를 수행할 수 있습니다.
  • 설계 목적: 이 모드의 궁극적 목적은 매 **충돌 경계(Crash Boundary)**를 결정론적으로 시험하는 것입니다. 특정 지점에서 실행을 멈추고 세션을 닫았다가 다시 여는 방식으로, 어떠한 중단 시점에서도 시스템이 올바르게 복구되는지 검증합니다.

6. 복구 프로세스의 구분: Restore vs Resume (Recovery Logic)

시스템 재시작 시 발생하는 복구 로직은 효율적인 탐색(Discovery) 알고리즘을 기반으로 합니다.

  • Restore (복원): 세션을 열 때 모든 레인을 독립적으로 복원하는 과정입니다. 외부 효과를 시작하지 않고, findOpenOperations 인덱스 쿼리를 통해 로그 전체를 스캔하지 않고 미완료 작업을 찾습니다. 이후 'Reduction' 과정을 통해 LaneState를 재구성합니다.
  • Resume (재개): 복원된 상태에서 실제 작업을 이어가는 과정입니다. 새로운 작업을 시작하는 것이 아니라, 기록된 마지막 안전한 경계부터 기존의 열린 작업을 잇습니다.
  • 부동점 자기 점검(Fixed-point self-check): Resume이 완료되거나 중단될 때, 하네스는 저장소의 데이터를 기반으로 재계산된 상태와 메모리 내의 LaneState를 비교합니다. 불일치가 발견되면 시스템 오염으로 간주하고 하네스를 폴트(Fault) 상태로 전환하여 무결성을 유지합니다.

7. 확장 시스템: Hooks와 Events의 차이 (Extension System: Hooks vs Events)

시스템 확장을 위한 두 채널은 실행 흐름에 대한 영향력과 지속성 측면에서 엄격히 구분됩니다.

  • Hooks (후크): 실행 흐름을 가로채고 변경할 수 있는 대기형 인터셉션(Awaited Interception) 지점입니다. 컨텍스트 변조, 요청 수정, 도구 실행 차단 등이 가능하며 결과는 로그에 지속(Persist)됩니다.
  • Events (이벤트): 시스템 상태 변화를 관찰하는 수동적 관찰 채널입니다. 실행 흐름에 영향을 줄 수 없으며, 영구 저장되지 않고(Non-persisted), 복구 시 재실행되지도 않습니다(Non-replayed).

멱등성 요구사항: Hook 자체의 외부 사이드 이펙트에 대한 'Exactly-once' 보장은 설계 목표가 아닙니다(Non-goal). 커밋 직전 충돌 시 Hook이 재실행될 수 있으므로, Hook 내부에서 발생하는 외부 효과(HTTP 호출 등)는 반드시 **멱등성(Idempotent)**을 가져야 합니다.

8. 지연된 요청 처리 (Deferred Provider Requests)

긴 시간이 소요되는 모델 요청을 처리하기 위해 Deferred provider requests 메커니즘을 사용합니다.

  1. 지속성 핸들(Persisted Handle): 프로바이더가 즉시 결과를 줄 수 없는 경우, 시스템은 나중에 결과를 회수할 수 있는 핸들이 포함된 어시스턴트 메시지를 먼저 기록하고 레인을 일시 중단(Suspend)합니다.
  2. 회수(Redeem) 및 Fetch: Resume 시점에 미회수된 핸들이 있다면, 시스템은 새로운 요청을 생성하지 않고 기존 핸들을 통해 결과를 가져옵니다(fetch). 만약 fetch가 실패하면 stopReason: "error"로 처리하여 결정론적 상태를 유지합니다.
  3. 구분: 이는 스트림 중간부터 다시 시작하는 partial stream resumption(지원하지 않음)과 명확히 구분되는 기능입니다.

9. 하위 호환성 정책 (Backward Compatibility Policy)

AgentHarness v2의 하위 호환성 범위는 의도적으로 좁게 설정되었습니다.

  • 유일한 요구사항: 기존 coding-agent v3 JSONL 세션 파일을 변경 없이 열고, 유휴 상태(Idle)로 복원(Restore)할 수 있어야 합니다.
  • 보장 제외: 그 외의 모든 API, 내부 데이터 형식, SQLite 스키마 등에 대해서는 마이그레이션이나 스키마 버전 관리를 보장하지 않습니다. 이는 혁신 속도를 저해하지 않기 위한 전략적 선택입니다.

10. 결론: 설계의 장점 및 구현 검증 항목 (Conclusion)

본 설계는 'Intent-before-effect'와 'Lane Mutation Line'을 통해 분산 환경에서도 강력한 내구성과 경합 없는 병렬 처리를 가능하게 합니다. 특히 Manual Drive를 통한 결정론적 검증 체계는 에이전트 시스템의 신뢰성을 아키텍처 수준에서 보장합니다.

향후 구현 및 검증이 필요한 핵심 트랙별 과제는 다음과 같습니다.

  • Track H (실행 엔진): 재시도 정책, 큐 관리, 지연 쓰기 및 중단 로직의 통합(H2~H8). 특히 도구 복구 로직(H7)의 완성도가 중요합니다.
  • Track J (JSONL 저장소): v3 세션의 노멀라이제이션 처리 및 원자적 쓰기 보장(J4~J6).
  • Track R (복구 로직): 인덱스 기반의 findOpenOperations 쿼리 최적화 및 정합성 검증(R3).
  • Track I (프리미티브): 뮤테이션 라인 FIFO 및 효과 경계(Effects Boundary) 게이트 구현(I3~I5).
  • Track C/N/O (기타): 컨텍스트 오버플로 복구(C3), 이동 후 요약 생성(N1), 그리고 전체 세션/레인 스냅샷 관찰 체계(O1) 구축.

11. 절대적 경계 및 금지 사항 (Absolute Boundaries)

보고서를 마무리하며 아래의 설계 제약 사항을 다시 한번 강조합니다.

  1. 구현 상태의 엄격한 분리: 상기 명시된 트랙 중 체크되지 않은 작업은 완료된 것으로 간주하지 마십시오.
  2. 지원하지 않는 기능(Non-goals):
    • 외부 효과(Hook 등)의 Exactly-once 실행 보장.
    • 멀티 라이터(Multi-writer) 접근 또는 분산 복제(Replication) 지원. (단일 라이터 모델 유지)
    • 끊긴 프로바이더 스트림의 중간 재개(Stream Resumption).
  3. 데이터 무결성: 설계 명세에 근거하지 않은 성능 수치나 벤치마크 데이터를 조작하여 포함하는 것을 금지합니다.

본 문서는 Pi AgentHarness v2의 시스템 무결성을 유지하기 위한 최상위 지침이며, 모든 후속 구현은 본 사양의 불변식을 엄격히 준수해야 합니다.
