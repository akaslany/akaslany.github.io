대규모 언어 모델을 활용한 정식 소프트웨어 검증(Formal Verification) 보고서

1. 개요 (Overview)

본 보고서는 앤트로픽(Anthropic)의 프론티어 레드팀(Frontier Red Team)과 시어럼(Theorem) 연구진의 협업을 통해 추진된 대규모 언어 모델(LLM) 기반의 정식 소프트웨어 검증(Formal Verification) 연구 결과를 분석한다. 2026년 10월 22일 발표된 본 연구는 그동안 막대한 시간과 고숙련 전문가 인력이 요구되어 극히 일부의 국가적·기업적 임무 수행 필수(Mission-critical) 시스템에만 한정 적용되던 정식 검증 기법을 대규모 언어 모델인 클로드(Claude)를 활용해 양산형 오픈소스 소프트웨어 생태계 전체로 확대할 수 있음을 실증하였다.

연구팀은 실제 널리 사용되는 123개의 C/C++ 오픈소스 라이브러리에 존재하는 239개의 퍼즈(Fuzz) 테스트 엔트리 포인트를 RISC-V 기계어 수준의 수학적 명세(Specification)로 변환하고, 이를 로크(Rocq) 커널을 통해 검증할 수 있는 정식 증명 코드를 자율적으로 생성해냈다. 특히 이 과정에서 수조 회의 퍼즈 테스트 실행으로도 발견하지 못했던 고난도 메모리 안전성 및 논리 버그를 다수 발견하였으며, 사람이 개입하지 않고도 클로드가 자율적으로 소스 코드를 패치(Patch)하고 명세를 재구성하여 증명을 완성하는 완전 자동화 워크플로우를 구현하였다.

소스 문서에 근거한 사실 관계(Fact), 소스 측의 주장(Claim), 그리고 보안 분석가의 해석(Interpretation)을 체계적으로 구분하면 다음과 같다.

  • 사실 관계 (Fact): 연구팀은 123개 오픈소스 라이브러리의 239개 퍼즈 엔트리 포인트에 대해 약 1억 8,000만 줄의 로크(Rocq) 정식 증명 코드를 작성하여 무크래시(No-crash) 증명을 완료했다. 기존 운영체제 커널인 seL4의 정식 검증에는 20인년(Person-years)의 인력이 투입된 반면, 이번 연구에서는 LLM이 컴파일된 기계어(RISC-V) 수준에서 자율적으로 정식 증명을 완성했다.
  • 소프트웨어 및 소스 측 주장 (Claim): 프론티어 LLM의 추론 능력이 급속히 향상됨에 따라, 정식 소프트웨어 검증은 동적 퍼즈 테스트를 대체하고 안전한 소프트웨어 개발 수명주기(SDLC)의 필수적 근간으로 자리 잡을 것이다.
  • 기술 분석가의 해석 (Interpretation): 본 연구는 AI가 보안 취약점을 탐지·공격하는 시대에 대응하여, 소프트웨어 공급망 전체의 보안 보증(Security Guarantees) 패러다임을 '단순 테스트'에서 '수학적 증명'으로 근본적으로 전환할 수 있는 경제적·기술적 전환점을 마련한 것으로 평가된다.

2. 주요 논점 (Key Arguments & Claims)

2.1. 기존 정식 검증의 한계와 LLM을 통한 패러다임 전환

기존의 정식 검증은 프로그램의 모든 가능 실행 경로에 대해 보안 규칙 위반이 없음을 수학적으로 증명하는 가장 명확한 보안 기법이다. 그러나 증명 코드가 원본 코드보다 수십 배 이상 커지고, 정식 검증 언어를 다룰 수 있는 전문 인력이 극히 드물어 경제적 타당성을 확보하기 어려웠다.

[사실(Fact) 기반 비교 및 한계]

  • seL4 커널 사례: 마이크로커널 개발에는 **2인년(Person-years)**의 인력이 투입된 반면, 이를 정식 검증하는 데에는 10배에 달하는 20인년의 고숙련 전문가 공수가 소요되었다.
  • 적용 분야의 한계: 비용적 장벽으로 인해 정식 검증은 에어버스(Airbus)의 항공 전자 공학 소프트웨어와 같이 실패가 인명/재산상 치명적 결과를 초래하는 극히 일부 영역에만 제한적으로 적용되어 왔다.

클로드와 같은 프론티어 LLM은 수억 줄의 코드 맥락을 분석하고 명확한 목표 지향적 증명 코드를 연속적으로 작성할 수 있어 이러한 인적·비용적 한계를 극복하는 패러다임 전환을 이끌어냈다.

2.2. 퍼즈 테스트의 수학적 증명(Spec) 전환 및 검증 메커니즘

퍼즈 테스트(Fuzz Testing)는 프로그램의 엔트리 포인트에 무작위 또는 변형된 무작위 입력값을 주입하여 비정상 종료(Crash)를 유발하는 방식이다. 그러나 퍼즈 테스트는 입력 데이터의 무한한 가능성으로 인해 프로그램의 모든 실행 경로를 탐색할 수 없다는 근본적 한계를 지닌다.

연구팀은 구글의 OSS-퍼즈(OSS-Fuzz) 프로젝트에 수록된 C/C++ 라이브러리의 퍼즈 테스트 코드를 RISC-V 기계어 수준의 정식 명세(Specification)로 정밀하게 변환하였다. C/C++ 프로그램은 컴파일 시 주소 위생 처리기(AddressSanitizer, ASan)가 삽입되어 버퍼 오버플로우나 메모리 해제 후 재사용(Use-after-free) 등 메모리 오염 발생 시 즉시 크래시를 일으킨다. 연구팀은 이를 활용하여 "64MB 미만의 모든 입력값과 모델링된 리눅스 OS 응답 조건하에서, 본 프로그램은 메모리 오염이나 단증 실패(Assertion failure) 없이 항상 정상 종료한다"는 정밀 명세를 구축했다.

최종 산출물 크래시를 유발하는 개별 무작위 입력 샘플 발견 로크(Rocq) 커널로 기계적 검증이 가능한 수학적 증명 코드

클로드가 작성한 증명 코드는 로크 증명 검증기(Rocq Proof Checker)를 통해 엄격하게 검증된다. 따라서 개발자는 LLM이 생성한 수억 줄의 증명 코드를 수동 검토할 필요 없이, 정식 모델(RISC-V 및 리눅스 프로세스 의미론), 증명 정리 명제, 로크 검증기 자체만 신뢰하면 된다.

2.3. 버그 발견 및 자동 수정 (Finding and Fixing Bugs)

본 보고서의 제3장(Chapter 03) 내용에 따르면, 클로드가 증명 작성을 시도하는 과정에서 기존의 수조 회 퍼즈 테스트로도 발견하지 못했던 심각한 고난도 버그들이 다수 드러났다. 연구팀은 버그 탐지 시 사람의 개입 없이 클로드가 소스 코드를 자율적으로 수정(Patch)하고, 수정된 코드로부터 명세를 재생성한 뒤 증명을 다시 완성하는 완전 자동화 워크플로우를 구현하였다.

클로드가 정식 증명 과정에서 실제 발견하고 수정한 대표적인 버그 사례는 다음과 같다.

  1. 희귀 레이아웃 기반 카운터 언더플로우: 압축 해제기 모듈에서 일반적인 퍼저가 탐색하기 어려운 약 20MB 크기의 특정 레이아웃 입력값에서 발생하는 카운터 언더플로우(Counter Underflow) 및 경계 외 쓰기(Out-of-bounds Write) 발견.
  2. 대용량 입력 조건의 경계 외 읽기: 이미지 디코더 라이브러리에서 64MB 크기의 입력값과 2GB 이상의 메모리 할당이 동시 요구될 때 발생하는 경계 외 읽기(Out-of-bounds Read) 발견.
  3. 복수 핸들 호출 시퀀스 버그: 동일한 파일에 대한 두 개의 핸들 사이에서 특정 순서로 함수가 호출될 때 유발되는 경계 외 읽기 버그 발견.
  4. CVE-2026-56132 재발견: libexpat 라이브러리에서 매우 깊게 중첩된(Deeply nested) 입력 조건에서 발생하는 기존 알려진 취약점 재발견.
  5. 비충돌 보안 논리 버그 (Logic Bugs): 크래시를 일으키지 않아 퍼즈 테스트로 탐지가 불가능한 버그 탐지. 애플리케이션의 파일 로딩 제한 보안 기능이 특정 조건에서 무력화되는 문제 정식 검증 중 발견.
  6. 고상위 속성 검증 (LZO 압축 알고리즘): 단순 메모리 안전성을 넘어 LZO 압축 알고리즘의 압축 후 해제 시 원본과 동일함(Encode-decode roundtripping)을 검증하는 동등성 성질 증명.
  7. 기계어 수준 심층 기하 증명 (cpp-httplib): cpp-httplib 라이브러리의 스택 오버플로우 방지를 증명하기 위해, libc++ 내 std::set 소멸자 호출 시 재귀 깊이가 제한됨을 machine-code 수준에서 분석하여 표준 라이브러리의 레드-블랙 트리(Red-Black Tree) 재평형 알고리즘이 트리의 깊이를 로그 수치 범위 내로 유지함을 정식 증명.

자동 수정 프로세스 중 발생할 수 있는 보상 해킹(Reward Hacking—LLM이 증명 과제를 쉽게 통과하기 위해 원본 프로그램을 아무 일도 하지 않고 즉시 종료되는 더미 프로그램으로 바꾸는 편법)을 방지하기 위해, 패치 적용 시 점수를 감점하고 변경되는 입력 변환 영역을 최소화하도록 유도하는 감점 체계와 패치 감사(Patch Auditing) 시스템을 적용했다.

2.4. 토큰 효율성 및 증명 재사용성 (Token Efficiency & Proof Reuse)

대규모 정식 검증의 경제성을 확보하기 위해 토큰 소모를 줄이는 모델 성능 개선 및 증명 코드 재사용 기법이 적극적으로 도입되었다.

  1. 차세대 모델을 통한 토큰 절감 효과: 실제 OSS-Fuzz 코드에서 추출한 36개 소형 검증 과제에 대해 과제당 3회의 독립적 시도와 500만 토큰(5M tokens) 예산을 부여해 평가한 결과, 오퍼스 5.5(Opus 5.5)는 오퍼스 5(Opus 5) 대비 약 40% 적은 토큰 소모량만으로 동일 과제의 절반을 증명해 냈다.
  2. 공용 작업 공간(Shared Workspace)을 통한 효율 향상: 에이전트들이 작성된 증명 코드를 공유하고 복사할 수 있는 환경을 제공한 결과, 단독 작업 대비 평균 17%의 토큰을 절감했다. 완수된 34개 과제 중 30개 과제에서 공용 작업 공간을 활용한 에이전트의 토큰 비용이 단독 에이전트의 평균 비용보다 낮았으며, 단독 작업 시 실패했던 2개 과제를 추가 완수했다.
  3. 공통 기반 코드 증명의 재사용 메커니즘: 모든 바이너리가 공통으로 포함하는 C 런타임 초기화(crt0) 및 주소 위생 처리기(ASan) 런타임 설정 코드는 공통 증명 블록으로 작동한다. 에이전트 팀이 이 공통 블록을 복사 및 경미한 수정으로 재구조화함으로써, 마치 수학 정리 라이브러리(Lean의 Mathlib)처럼 레이어화된 추상화를 구축해 전체 증명 비용을 크게 낮추었다.
2.5. 기타 정식 검증 사례 연구 (Case Studies)

연구팀은 퍼즈 테스트 기반 명세 검증 외에도 다각도의 정식 검증 응용 연구를 수행했다.

  • 리눅스 커널 zlib 규격 및 ISA 의미론 자율 생성: RFC 1950 zlib 포맷 명세를 작성하고 리눅스 커널 내 zlib 구현체가 이를 준수함을 x86 바이너리 수준에서 증명했다. 특히 클로드는 x86 및 RISC-V ISA 정식 의미론을 자율 생성하는 성과를 올렸는데, 이 의미론을 통해 단일 스텝 명령어를 실행하여 리눅스 커널 상에서 우분투(Ubuntu) 사용자 공간을 정상 부팅시키는 데 성공했다. 또한 이 의미론 생성 과정에서 공식 참조 문서 내 수백 개의 오류와 하드웨어 자체의 버그를 찾아내는 독보적 성과를 거두었다.
  • Rust 기반 파이썬 해석기의 CPython 동작 동일성 검증: Verus 도구를 활용하여 Rust로 구현된 파이썬 해석기가 CPython의 학술적 명세와 일치함을 증명했다. 170만 개 이상의 무작위 파이썬 프로그램을 실행한 실증 테스트에서 99.95%의 테스트가 CPython과 완전히 동일하게 동작함을 입증했다.
  • PDF 리더 및 방치된 상주 버그 발견: 널리 쓰이는 PDF 리더의 정식 검증을 단 1주일간 시도한 끝에 일반적으로 1년 동안 보고되는 수에 맞먹는 보안 버그를 발견했으며, 10년 이상 방치되어 있던 시스템 로직 버그를 발굴했다.
  • Nix 생태계 검증 로드맵 확장: 의존성 파워 로(Power Law) 법칙에 따라 시어럼(Theorem)은 foundational 라이브러리인 glibc, OpenSSL, cURL 등을 포함한 전체 Nix 생태계 소프트웨어 스택으로 정식 검증 파이프라인을 확장하는 대규모 로드맵을 제시했다.

5. 한계와 불확실성 (Limitations & Uncertainties)

본 연구의 비약적 성과에도 불구하고, 소스 문서에서는 정식 검증 기술이 지닌 근본적인 한계와 불확실성을 다음과 같이 명시하고 있다.

  1. "정식 검증됨(Formally Verified)"과 "버그 없음(Bug-free)"의 차이:

    • 정식 검증은 프로그램이 명세(Spec)를 준수함을 증명할 뿐, 명세 자체가 현실 세계의 물리적 시스템과 완벽히 일치함을 보장하지 않는다.
    • 버그는 실제 배포 환경의 동작이 수학적으로 모델링된 명세 범위를 벗어날 때 언제든 발생할 수 있다.

  2. 실험 모델 환경과 실제 배포 환경 간의 격차 (Model vs. Reality Gap):

    • 실험 모델 환경: 본 연구의 정식 증명은 musl libc와 정적으로 링크(Static linking)된 단일 스레드(Single-threaded) RISC-V 바이너리 및 모델링된 리눅스 OS 환경을 전제로 수행되었다.
    • 실제 배포 환경: 대부분의 실제 소프트웨어는 x86 또는 ARM 아키텍처 기반에서 glibc와 동적 링크(Dynamic linking)되어 다중 스레드(Multi-threaded)로 동작하므로 실제 배포 환경과의 격차가 존재한다.

  3. 신뢰 기반 요소(Trusted Components)의 불확실성:

    • 증명의 정당성을 보장하기 위해 오류가 없다고 신뢰해야 하는 핵심 구성 요소를 "신뢰 기반 요소"라 한다.
    • 본 연구의 신뢰 기반 요소는 ① RISC-V 및 리눅스 프로세스 정식 의미론 모델, ② 작성된 증명 정리 명제 문구, ③ 로크(Rocq) 증명 검증기 자체이다.
    • 나아가 로크 검증기가 실행되는 하드웨어(CPU), OS, OCaml 컴파일러 등의 신뢰성에도 의존하므로 이들 하위 레이어의 잠재적 오류 불확실성이 존재한다.

  4. 명세 미미 영역 및 외부 호출자 메모리 오염:

    • ASan 탐지 한계: 주소 위생 처리기(ASan)가 모든 유형의 메모리 오염이나 논리적 오류를 탐지할 수 있는 것은 아니다.
    • 미검증 코드 영역: OSS-Fuzz의 특정 엔트리 포인트만 증명되었으므로, 라이브러리 내부의 미실행 코드(Dead code)나 미검증 엔트리 포인트의 안전성은 담보되지 않는다.
    • 호출자 코드(Caller Code)의 메모리 오염: 라이브러리 자체의 무결성이 증명되었더라도, 해당 라이브러리를 호출하는 외부 애플리케이션이 API 사전 조건(Preconditions)을 위배하여 잘못 사용할 경우 호출자 영역에서 메모리 오염이 유발될 수 있다.
