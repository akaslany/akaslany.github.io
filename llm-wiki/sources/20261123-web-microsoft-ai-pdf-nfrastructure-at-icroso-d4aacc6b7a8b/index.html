1. 개요 (Overview)

마이크로소프트 AI(Microsoft AI, 이하 MAI)는 '인간 중심 슈퍼인공지능(Humanist Superintelligence)' 달성을 핵심 비전으로 설정하고, 외부 모델로부터 지식을 전달받는 교사-학생 구조의 증류(Distillation) 절차를 배제한 채 베이스 모델에서 직접 강화학습(Reinforcement Learning, RL)을 수행하여 성능 역량을 확장하는 장기 학습 파이프라인 전략을 운용하고 있다. 이는 포스트 트레이닝(Post-training) 단말의 단기 RL 미세조정 방식과 달리, 수천 대의 GPU 환경에서 수주에서 수개월 동안 수만 번의 학습 스텝(Training steps)을 지속해서 밟아 나가는 대규모 분산 컴퓨팅 연산 체계이다.

이러한 초장기·대규모 RL 환경에서는 오프-정책 이탈(Off-policy drift), 커널 단위 정밀도 차이, 시스템 미세 결함에 따른 오버헤드가 누적되어 전체 학습 안정성을 훼손한다. 이를 해결하기 위해 MAI는 독자적인 강화학습 분산 프레임워크인 'Rocket'을 자체 개발하였다. 최근 공개된 3조 파라미터(3-trillion-parameter) 규모의 초거대 베이스 모델인 'MAI Base 2'는 Rocket 프레임워크를 기초 인프라로 채택하여 타사 모델의 증류 없이 베이스 단계에서부터 직렬 강화학습을 진행하고 있다. (단, 본 프레임워크 기반 작업은 MAI Code 2 모델 라인업 개발 체계와는 명확히 분리된 별개 프로젝트이다.)

학습 효율성을 최적화하기 위해 MAI는 학습 프레임워크(Learner), RL 인프라(Rocket), 그리고 MAI가 직접 유지 관리하는 SGLang 포크(MAI-maintained fork of SGLang) 기반 추론 엔진이라는 3대 요소를 밀접하게 결합한 시스템 공학 설계(Co-design) 방식을 적용하였다.

본 분석 보고서는 소스 문헌(Source Context)에 근거하여 Rocket 프레임워크의 시스템 아키텍처, 수치 정밀도 최적화, 정책 지연(Staleness) 통제, 내결함성(Fault Tolerance) 및 컴퓨팅 자원 신축성(Elasticity) 메커니즘을 객관적으로 분석한다. 기술적 검증을 거친 사실(Fact) 정보와 함께 소스 측 연구진이 제시한 성능 향상 추세 및 향후 지표 전망에 관한 주장(Claim)을 철저히 구분하여 기술한다.

2. 주요 논점 (Key Points)
2.1. 장기 대규모 RL 학습의 3대 핵심 과제 및 설계 배경

3조 파라미터 규모의 MAI Base 2 모델을 수천 대의 GPU 인프라에서 수주~수개월 동안 자립적으로 학습시킬 때 직면하는 3대 핵심 기술 과제는 다음과 같다.

  1. 정책 지연 (Staleness): 에이전트(Agentic) 작업의 Rollout(실행 트레이스) 생성에는 최대 수 시간이 소요되는 반면, 학습기(Learner)는 정책(Policy) 가중치를 실시간으로 갱신한다. Rocket의 기초 알고리즘인 GRPO(Group Relative Policy Optimization)는 동일 문제에 대한 Rollout 간 상대적 리워드를 비교하여 이점(Advantage)을 계산하므로, 개별 Rollout의 지연이나 실패가 그룹 전체의 수집 완료를 막아 심각한 오프-정책 이탈을 야기한다.
  2. 수치적 일관성 (Numerical consistency): 초거대 모델과 장문 컨텍스트를 추론 샘플러(Sampler) VRAM에 할당하기 위해서는 저정밀도 양자화 저장이 불가피하다. 그러나 샘플러와 학습기 간의 계산 정밀도, 실행 커널, 병렬화(Parallelism) 방식 차이로 발생하는 미세 수치 불일치는 학습 스텝이 누적됨에 따라 오차를 증폭시켜 학습 속도 저하 및 발산 현상을 초래한다.
  3. 결함 허용성 및 신축성 (Fault tolerance and elasticity): 수천 대의 GPU 노드에서 수주 이상 지속되는 단일 작업 특성상 하드웨어 결함 발생은 필연적이며, 모델 성능 향상 및 태스크 변화에 따른 최적 런타임 설정값과 데이터 혼합 비율(Data mixture) 역시 동적으로 변한다. 노드 장애나 구성 변경 시 전체 작업을 재시작하는 것은 막대한 컴퓨팅 자원을 손실시키므로, 런타임 상태를 유지한 채 단위 구성 요소를 즉시 복구하고 재설정하는 기술이 필수적이다.

오픈소스 프레임워크의 한계 및 설계 제약 조건: verl, slime 등 기존 오픈소스 RL 프레임워크는 분산 실행과 비동기 샘플링 기본 프레임을 제공하지만, 교사 모델에서 증류된 정제 모델 학습 환경에 맞춰진 경향이 있다. 증류 기반 모델은 이미 성능 상한선 부근에서 포스트 트레이닝이 시작되므로 RL 구간이 짧아 수치 불일치나 하드웨어 장애 영향이 치명적이지 않다.

반면, 베이스 모델에서 직접 성능을 끌어올리는 MAI의 장기 RL 클라이밍(Climbing) 레시피에서는 하드웨어 결함 발생 가능성이 100%에 수렴하며, 미세 수치 불일치 오차가 수만 스텝에 걸쳐 복리로 누적된다. 따라서 Rocket 프레임워크는 오픈소스 툴셋의 단순 적용을 넘어 분산 커널 단위의 비트 일치성(Bitwise parity)과 초단위 무정지 복구 기능을 시스템 설계 조건으로 설정하였다.

2.2. Rocket 아키텍처 및 비동기 GRPO 학습 루프

그림 1 (Figure 1)에 제시된 Rocket의 비동기 강화학습 아키텍처는 제어, 컴퓨팅, 저장 및 실행 환경이 상호 분리된 6개의 핵심 구성 요소로 이루어져 있다.

[Rocket 비동기 강화학습 아키텍처 레이아웃 및 데이터 흐름]

Controller (CPU) <=====================> Problem Workers (CPU pool) <=====================> Rollout Workers (CPU pool)
      ║                                          ║                                                 ║
      ║ (Segment Refs + Advantages)             ║ (Payloads)                                      ║ (Context + Settings)
      ▼                                          ▼                                                 ▼
Learner (GPU pool) <── (Direct Retrieval) ── Rollout Store <── (Store Payloads) ─── Sampler (MAI SGLang GPU)
      │                                    (Tokens / Logprobs)                                     │
      └────────────────────────── (Updated Model Weights) ─────────────────────────────────────────┘
                                                                                                   │ (Actions / Checks)
                                                                                                   ▼
                                                                                           Environments (SEE)
  1. Controller (CPU): 커리큘럼에서 문제를 선택 및 배치하고, 승인된 작업 패킹, 학습기 세그먼트 생성, 주기적 가중치 전송 트리거, 체크포인트 저장을 총괄 제어한다.
  2. Problem Workers (CPU pool): 컨트롤러로부터 전달받은 문제 요청을 처리하며, 동일 문제에 할당된 Rollout 결과를 종합하여 그룹 평가(Group grading)를 수행하고 GRPO 이점(Advantage)을 계산한다.
  3. Rollout Workers (CPU pool): 에이전트 루프 및 도구 디스패처를 제어하며, 샘플러 추론과 환경 관측(Observation)을 교대 실행한다. 완료 후 개별 평가(Per-rollout grading)를 거쳐 트레이스 페이로드를 Rollout Store에 저장한다.
  4. Sampler (Router on CPU / MAI-maintained SGLang on GPU): 추론 엔진으로, 에이전트 루프 요청에 맞춰 Prefill 및 Decode 연산을 수행하고, 학습기로부터 갱신된 모델 가중치를 동기화한다.
  5. Environments / SEE (Sandbox Execution Environments): 샌드박스 연산 실행 환경, 웹 검색, MCP(Model Context Protocol) 도구 등 에이전트의 액션을 수행하고 실행 결과를 반환한다.
  6. Learner (GPU pool) & Rollout Store: Rollout Store는 토큰 ID, 샘플링 시점의 로그 확률(Logprobs) 및 모델 턴 페이로드를 보관하며, Learner GPU 풀은 해당 데이터를 조회하여 정책 가중치를 업데이트한다.

GRPO 기반 이점(Advantage) 산출 및 학습 루프 순차 절차:

  1. 문제 선택 및 요청 분배: Controller가 커리큘럼 데이터 혼합(Problem mixture) 규격에 맞춰 특정 문제(Problem)를 선택하고 Problem Worker로 전송하면, Problem Worker는 필요한 수의 Rollout 요청을 생성하여 Rollout Worker 풀로 동시 디스패치한다.
  2. 에이전트 상호작용 및 트레이스 생성: Rollout Worker 내부의 에이전트 루프가 Sampler(MAI 포크 SGLang) 추론 연산과 Environments(SEE 샌드박스, 도구) 실행 결과를 지속해서 주고받으며 다중 턴(Multi-turn) 문제 해결 트레이스를 형성한다.
  3. 개별 평가 및 페이로드 저장: 개별 평가기(Per-rollout grader)가 완료된 트레이스와 최종 환경 상태를 기반으로 리워드 점수를 산출한다. Rollout Worker는 토큰 및 로그 확률 페이로드를 Rollout Store에 저장하고, 획득 점수와 참조 ID(Rollout ref)를 Problem Worker로 반환한다.
  4. 그룹 평가 (Group Grading): Problem Worker는 단일 문제에 할당된 모든 Rollout 결과가 수집될 때까지 대기한 후, 그룹 평가기를 구동하여 동일 문제 그룹 전체의 상대적 리워드 분포를 구성한다.
  5. 이점(Advantage) 산출: GRPO 알고리즘을 적용하여 그룹 내 상대적 점수 편차를 기반으로 개별 Rollout의 최종 이점(Advantage)을 계산한다.
  6. 세그먼트 전달 및 데이터 직접 조회(Retrieval) 학습: Controller는 계산된 이점과 문제 세그먼트 참조 정보(Segment refs)만을 패킹하여 Learner 배치를 구성한다. 이때 Learner는 토큰 데이터 전체를 Controller로부터 직접 수신하지 않고, 전달받은 참조 정보를 통해 Rollout Store에서 실제 토큰 ID 및 생성 시점의 로그 확률(Logprobs)을 직접 효율적으로 조회(Retrieval)하여 정책 가중치를 업데이트한다.
2.3. 정책 지연(Staleness) 제어 메커니즘

그림 2 (Figure 2)에 나타난 바와 같이 태스크 유형별 Rollout 실행 시간은 단순 명령 이행(Instruction Following, 중앙값 2분, 1턴)부터 소프트웨어 공학 작업(Software Engineering, 중앙값 93분, 249턴)까지 극심한 시간 격차를 보인다. 학습기가 정책을 업데이트하는 동안 추론이 진행되는 비동기 시스템 구조 특성상, 생성 시점 정책과 학습 시점 정책 간의 격차가 벌어지는 정책 지연 문제가 발생한다.

로그 확률 차이 증폭 원인: 그림 3 (Figure 3)에 명시된 실험 데이터에 따르면 지연 수준(Staleness)이 증가함에 따라 샘플러와 학습기 간의 평균 절대 로그 확률 차이(Mean |log-prob difference|)가 선형적으로 증폭된다 ($R^2 = 0.76$). 지연 수준이 0일 때는 수치적 일치가 유지되나, 지연이 커지면 오프-정책(Off-policy) 이탈이 누적되어 활성화값(Activation) 변동성이 증폭되고 학습 불안정성 위험이 급격히 증가한다.

그림 4 (Figure 4)는 단일 GRPO 그룹 내 3개 Rollout 간 지연 편차 현상을 보여준다. 가장 빠르게 완료된 Rollout은 가장 느린 Rollout(784 턴 소요)이 끝날 때까지 7.6시간 동안 대기해야 했다.

정책 지연 수치 산출 공식: 학습 스텝 간 소요 시간이 일정하다고 가정한 상태에서 개별 토큰의 지연 수준은 다음과 같이 정의된다.

$$\text{지연 수준 (Staleness)} = \text{샘플러 지연(Sampler lag)} + \frac{\text{토큰 학습 시점} - \text{토큰 생성 시점}}{\text{학습 스텝 간 소요 시간}}$$

첫 번째 항인 샘플러 지연(Sampler lag)은 토큰이 생성될 때 샘플러 정책 버전이 학습기 대비 뒤처진 스텝 수를 측정한다. 두 번째 항은 토큰 생성 완료 후 GRPO 그룹 대기 및 학습 대기열 체류 과정에서 누적되는 지연을 나타낸다.

[정책 지연(Staleness) 발생 및 통제 제어책 구조]

  [샘플러 2단계 가중치 전송] ──► Sampler Lag (0~3 스텝 제한)
  [기존 Rollout 우선순위 부여] ──► 생성 진행 중 체류 대기 최소화 (VM 자원 점유 고려)
  [실패 Rollout 즉시 폐기]   ──► 그룹 대기 시간 (7.6시간 -> 0시간 단축)
  [학습기 GPU 과다 할당]     ──► 학습 대기열 체류 시간 (12초 단축)

Rocket의 4가지 지연 제어책:

  1. 샘플러 2단계 가중치 갱신 (Keeping the sampler current): 학습기의 가중치 변경분을 대규모 샘플러 노드 전체로 개별 전송하면 Learner 통신 오버헤드가 추론 플릿 크기에 비례하여 폭증한다. Rocket은 일부 대표 샘플러 엔진이 Learner로부터 파라미터 청크를 먼저 수신(Pull)한 후, 이를 각 샘플러 복제본(Replica) 내 랭크로 분산시키는 2단계 계층 전송 구조를 구축했다. 이를 통해 가중치 동기화 시간을 15초로 단축하여 Sampler lag을 0~3 스텝 범위로 통제한다.
  2. 기존 Rollout 우선순위 부여 및 자동 스케일링 (Prioritizing existing rollouts): 토큰 생성이 이미 시작된 Rollout의 체류 시간을 줄이기 위해, 생성 시작 시점이 빠른 기존 Rollout에 높은 우선순위를 부여하여 추론 자원을 우선 할당한다. 아울러 대기열 적체를 막기 위해 진행 중인 Rollout 수를 추론 용량에 맞춰 자동 조절(Scaling)한다. 단, 롤아웃 시작 전 대기 시간이 길어질 수 있으며(그림 4 기준 최초 추론 시작까지 24분 대기), 이 대기 시간 동안 해당 Rollout이 VM 및 컴퓨팅 자원을 미리 점유(Hold)하고 있는 운용상의 비효율이 발생하므로 타임아웃 설정 시 이 자원 점유 대기 시간을 반드시 반영해야 한다.
  3. 실패한 Rollout 즉시 폐기 (Dropping failed rollouts): GRPO 그룹 내 일부 Rollout 결함 발생 시 재시도(Retry)를 수행하면 정상 완료된 데이터의 대기 시간이 급증한다. Rocket은 실패한 Rollout을 즉시 폐기하여 완료된 그룹 트레이스가 대기 없이 곧바로 학습 스텝으로 전환되도록 처리한다.
  4. 학습기 GPU 과다 할당을 통한 Inference-bound 유지 (Keeping jobs inference-bound): Learner GPU 풀의 용량을 의도적으로 과다 할당하여 RL 병목을 학습 연산이 아닌 추론(Inference) 단계에 고정시킨다. 이에 따라 그림 4와 같이 완료된 그룹 데이터가 Controller 대기열에서 체류하는 시간을 단 12초 수준으로 단축한다.

한계 및 분석적 트레이드오프: 실패한 Rollout을 즉시 폐기하는 방식은 지연 시간을 극적으로 단축하지만, 특정 실패 패턴이나 복잡도를 공유하는 샘플이 학습 대상에서 배제되므로 GRPO 이점 산출 베이스라인에 편향(Bias)이나 노이즈를 유발할 수 있다. 또한, 배치 크기를 고정한 상태에서 추론 인프라만 추가 증설할 경우, 학습 스텝 간 소요 시간(분모)이 감소하여 연산 공식상 역설적으로 계산된 지연 수치 값이 올라가는 시스템적 상충 관계가 존재한다.

그림 5 (Figure 5)는 Sampler와 Learner 사이의 메모리 저장 정밀도 및 연산 정밀도 분리 아키텍처를 보여준다.

정밀도 분리 전략 및 BF16 유지 사유: MAI Base 2 구조에서 MoE 전문가 가중치는 전체 파라미터의 95% 이상을 점유한다. MoE 가중치를 MXFP8로 저장하면 메모리 점유량이 절반으로 감소하여 전문가 병렬화(EP) 차수 및 샘플러 복제본당 필요 GPU 수를 감축시킬 수 있다. 연산 시에는 이를 BF16으로 역양자화하여 계산함으로써 정밀도 손실에 의한 학습 발산을 방지한다. Learner 역시 동일한 수치적 궤적을 흉내 내기 위해 가짜 양자화(Fake quantization)를 적용한다.

KV 캐시의 경우, MAI Base 2는 로컬 어텐션과 글로벌 어텐션 레이어가 5:1 비율로 배치되어 있다. 실험 분석 결과 로컬 어텐션 KV 캐시까지 양자화할 경우 Sampler-Learner 간 로그 확률 오차가 심화됨이 확인되었다. 이에 따라 로컬 어텐션 전체와 최종 수치 예방을 위한 상위 3개 글로벌 어텐션 레이어에는 BF16 정밀도를 유지했다. 이로써 글로벌 컨텍스트 토큰 수용량을 기존 BF16 대비 약 67% 확장하는 성과를 거두었다.

비트 단위 일치(Bitwise Parity)의 하드웨어 레벨 구현 및 성능 검증: 그림 6 (Figure 6)은 동일 체크포인트에서 출발한 L42 모델(7B active, 180B total 파라미터)의 실험 결과를 보여준다. Sampler와 Learner 간 비트 단위 일치를 달성한 파이프라인(Blue)이 기존 베이스라인(Yellow) 대비 수학 추론 벤치마크(avg pass@1)에서 우월한 상승 곡선을 기록하였다.

[비트 단위 일치(Bitwise Parity) 3대 연산 최적화]

1. Attention Output Projection:
   [Sampler TP 환경] Attention Heads ──► All-Gather ──► Single GPU Projection (FP32 Accumulation)
   [Learner Non-TP]   Attention Heads ───────────────► Single GPU Projection (동일 순서 연산)

2. MoE Expert Combination:
   [EP Distribution] Experts ──► All-to-All 통신 ──► Source GPU 분배 ──► FP32 Local Weighted Sum

3. Attention Kernels:
   FlashAttention4 공통 적용 + K-Block 타일 정렬 + 고정 KV Tokens per Split 정렬

그림 6의 비트 단위 일치를 달성하기 위해 적용된 3가지 분산 연산 기법:

  1. 어텐션 출력 프로젝션 가중치 복제 (Attention output projections): 텐서 병렬화(TP) 환경의 Row-parallel projection 연산 시 발생하는 텐서 리덕션(All-reduce) 과정의 수치적 축적 순서 오차를 완전히 제거하기 위해, 샘플러 내 어텐션 출력 프로젝션 가중치를 복제(Replication)하였다. 프로젝션 연산 전 어텐션 헤드 출력을 All-gather로 수집한 후 단일 GPU 내부에서 프로젝션을 계산함으로써, 텐서 병렬화를 사용하지 않는 Learner와 연산 수적 축적 순서를 비트 단위로 완벽히 일치시켰다.
  2. MoE 전문가 결합 FP32 로컬 연산 (MoE expert combination): 전문가 병렬화(EP) 수행 후, 선택된 전문가들의 연산 결과를 All-to-all 통신을 통해 토큰의 원래 소스 디바이스로 수집한다. 이후 가중 합산 연산을 수행할 때 FP32 정밀도로 로컬에서 축적 계산을 진행하여 디바이스 간 리덕션 오차 및 누적 순서 오차를 방지하였다.
  3. 공통 FlashAttention4 및 타일/분할 경계 정렬 (Attention kernels): Learner forward, Sampler prefill, Sampler decode 전반에 걸쳐 공유 FlashAttention4(FA4) 커널을 적용했다. 슬라이딩 윈도우 어텐션의 K-블록 경계를 Learner의 타일 위치와 엄격히 정렬하고 Split당 KV 토큰 수 및 분할 경계를 동일하게 고정함으로써 온라인 Softmax 및 어텐션 리덕션 연산 구조를 동기화했다.
2.5. 내결함성(Fault Tolerance) 및 컴퓨팅 자원 신축성(Elasticity)

수준별 내결함성 복구 메커니즘:

  • Learner 복구: Learner 노드 장애 발생 시 Rocket은 각 랭크의 NCCL 타임아웃 종료를 무작정 기다리지 않고 즉시 Learner 랭크 프로세스를 강제 종료(Terminate)시킨다. 이후 Learner 체계만 즉시 재구축하여 최신 체크포인트를 복구(약 5분 소요)하고 기존 Controller와 재연결한다. 이 복구 구간 동안 추론 인프라는 정지 없이 지속 구동되어 자원 손실을 방지한다.
  • 추론 복구 (Inference recovery): 결함이 발생한 추론 복제본만 개별 교체하며, 정상 인스턴스 비율이 설정 임계치 밑으로 떨어질 때만 클러스터 단위 재시작을 수행한다.
  • 인옵 복구 (In-Job recovery): 모듈 단위 복구가 불가능할 경우 기존 Ray 작업 내부에서 환경을 재구성하여 컨테이너 재시작 오버헤드를 회피한다.
  • 제어 평면 분리 (Control-plane isolation): Ray Head 및 Rocket CPU 아키텍처를 안정성이 높은 CPU 전용 노드에 배치하여 GPU 하드웨어 장애가 시스템 제어 평면으로 전이되는 것을 차단했다.

예비 노드 풀(Spare Node Pool) 및 2계층 스케줄링 신축성: 그림 7 (Figure 7)과 같이 클러스터 스케줄러(Kubernetes/Slurm)가 노드를 할당하면, Rocket의 Scheduling Actor가 토폴로지(Topology)를 인식하여 자원을 배치한다.

  • 예비 노드 풀 (Spare Node Pool) 전략: Rocket은 Learner 1개 슬라이스(Slice)를 즉시 대체할 수 있는 규모의 예비 노드 풀(Spare group of nodes)을 항상 유지한다. Learner 슬라이스 장애 발생 시 이 예비 노드를 즉시 투입하여 복구 시간을 최소화하며, 백그라운드 오토스케일링이 클러스터에서 새 노드를 할당받아 예비 노드 풀을 다시 채워 넣는 구조로 자원 신축성을 확보한다.
  • 컴퓨팅 자원 신축성 (Compute resource elasticity): 병목 위치에 따라 Learner, Inference, Controller의 크기를 개별 조정한다. 추론 서버는 동적 동기화되며, Learner는 연산 낭비를 막기 위해 체크포인트 저장 시점에 동적으로 크기를 변경한다.
  • 런타임 신축성 (Runtime elasticity): 재시작 없이 동시성, 지연 제한, 배치 패킹, 문제 혼합 비율 등의 런타임 설정값을 동적으로 동기화 적용한다.

2.6. 평가 벤치마크 성과 및 향후 전망

5. 한계와 불확실성 (Limitations & Uncertainties)

본 보고서는 제공된 소스 콘텍스트에 엄격히 근거하여 작성되었으며, 소스에서 기술 세부사항이 생략되었거나 명확히 기재되지 않은 항목은 다음과 같다.

  1. MAI 유지 관리 SGLang 포크의 세부 개조 기술: SGLang 추론 엔진을 MAI의 장기 에이전트 워크로드에 맞게 개조한 구체적인 C++/CUDA 커널 수준 수정 내역은 포함되어 있지 않다 (향후 블로그 포스트로 공개될 예정임).
  2. MAI Code 2 프로젝트와의 연계 구조: MAI Code 2 모델 연구 체계와 본 Rocket 인프라 간의 기술 교류나 아키텍처 차이점은 구체적으로 명시되어 있지 않다 (단지 "별개 작업"으로만 기재됨).
  3. 토폴로지 인식 스케줄러 알고리즘: Rocket의 Scheduling Actor가 Blackwell 등 랙 스케일 클러스터 토폴로지를 계산하고 노드를 할당하는 세부 알고리즘 수식은 서술되어 있지 않다.
  4. 데이터 커리큘럼 세부 비율: 학습에 투입된 태스크 유형별 데이터 혼합 비율(Problem mixture)의 세부 수치는 본문에 제시되어 있지 않다.
