ChatGPT Work: 독립 제품 기능 및 보안 감사 보고서 (2026-08-31 기준)

1. 제품 정체성 및 분류 체계 (Product Taxonomy)

OpenAI가 2026-07-09 출시한 ChatGPT Work는 독립적인 구독 SKU가 아니라, ChatGPT 환경 내에서 제공되는 특정 업무 위임 표면(Surface) 혹은 "ChatGPT 내의 에이전트(an agent in ChatGPT)"로 정의됩니다. 감사관 관점에서 본 제품은 단순한 인터페이스의 확장이 아니라, 권한과 데이터 보존 경계가 서로 다른 개별 실행 환경의 집합으로 분석됩니다.

  • 공식 명칭 및 제품 표면 분리:
    • Chat: 답변, 설명, 초안 작성을 중심으로 하는 기본 텍스트 인터페이스.
    • Work: 파일, 도구, 브라우저를 사용하여 검토 가능한 결과물을 생성하는 실행 중심 인터페이스.
    • Codex: 전용 뷰와 별도 개발자 워크플로 기록을 유지하는 기술 중심 인터페이스.
    • 기타 표면: 데스크톱 앱, Business/Enterprise Workspace, Projects, Tasks, Apps/Connectors, API Platform은 각각 별도의 권한, 보존 정책 및 요금 경계를 가집니다. 이들은 기능이 겹쳐도 권한·보존·요금 경계를 구분해 설명해야 합니다.
  • 분석용 분류 (Simon Willison의 체계):
    • Work Cloud: OpenAI 관리 공유 인프라 기반의 VM 샌드박스 환경.
    • Work Local: 데스크톱 앱을 통해 승인된 로컬 파일 및 애플리케이션을 사용하는 환경.
    • 주의: 위 두 명칭은 공식 SKU가 아니며, 기능적 차이를 설명하기 위한 도구적 분류입니다.

2. 모델 라인업 및 요금제 구조

2.1 모델 계층 및 추론 엔진 (GPT-5.6 모델군)
  • Sol: 플래그십 모델로, 추론 레벨(Instant, Medium, High, Extra High)에 따라 성능이 차등화됩니다.
  • Terra: 성능과 속도의 균형을 맞춘 중급 계층 모델입니다.
  • Luna: 빠르고 저렴한 비용으로 제공되는 보급형 계층 모델입니다.
  • Ultra 모드: 단순한 최고 성능 추론 단계가 아닌, Subagents 병렬 오케스트레이션(Parallel Orchestration) 모드를 의미하며, 공식 문서는 Ultra를 subagents 병렬 orchestration으로 설명하며 위임 강도는 별도 관찰로 남습니다.

4. 기술적 보안 경계 및 통제 메커니즘 분석

  • Cloud Browser 격리 및 Takeover: 사용자의 로컬 환경과 분리된 원격 샌드박스에서 실행됩니다. 사용자는 필요한 로그인·인증 단계에서 **인간 개입(Takeover)**을 수행할 수 있지만 이것이 모든 비정상 행위 차단을 보장하지는 않습니다.
  • 'Sites' 데이터 구조: 관계형 데이터베이스(D1, 10GB 제한)와 오브젝트 스토리지(R2)를 활용하며 저장(Save)과 배포(Deploy) 단계가 분리되어 있습니다. Simon의 관찰에 따르면 Cloudflare Workers 기반 인프라로 보이나, OpenAI는 이를 공식적으로 명시하지 않았습니다.
  • 인증 정보 관리의 한계: 모델이 사용자의 비밀번호를 직접 보지 못하도록 설계되었으나, 브라우저 세션 쿠키, 네트워크 로그, 혹은 브라우저 확장 프로그램 상태를 통한 간접적 노출 가능성은 여전히 존재합니다. "모델이 보지 못한다"는 것이 "시스템 전체에서 안전하다"는 것을 보장하지 않습니다.
  • Auto-review 시스템의 불확실성: 샌드박스 내 위협 행위를 자동 감지하는 Auto-review 시스템은 **결정론적 보안 보장(Deterministic guarantee)**이 아닙니다. 샌드박스의 접근 권한(writable roots)과 네트워크 범위가 넓어질수록, 자동 리뷰는 결정론적 보안 보장이 아니므로 사람의 검토와 최소 권한을 대체할 수 없습니다.

5. 위협 모델링: The Lethal Trifecta 및 9대 위협

보안 전문가 Simon Willison은 (1) 개인 데이터 접근권, (2) 신뢰할 수 없는 외부 콘텐츠 노출, (3) 외부 데이터 유출 채널의 결합을 가장 치명적인 위협(Lethal Trifecta)으로 정의했습니다. 이는 Work 환경이 가질 수 있는 잠재적 공격 표면에 대한 분석입니다.

6. 안전 사용 가이드: 5단계 사다리 (Safe-Use Ladder)

다음은 데이터 민감도에 따른 review·avoid 조건을 정리한 safe-use ladder입니다.

  1. 공개 자료 조사: 외부 쓰기 기능을 비활성화하고 도구의 출력물을 철저히 검토합니다.
  2. 개인 문서 작업 (외부 액션 없음): 데이터 학습 제외 설정을 확인하고 휘발성 워크스페이스를 사용합니다.
  3. 인증된 브라우징 (Authenticated Browsing): 별도의 저권한 계정을 사용하며, Takeover 기능을 통해 제출 내용을 상시 모니터링합니다.
  4. 소스/종속성 실행: Lockfile 사용, 버전 고정, 네트워크 허용 리스트가 설정된 격리 환경에서만 수행합니다.
  5. 운영/금융/관리자 액션: 원칙적으로 지양해야 합니다. 불가피한 경우 **별도의 서비스 계정(Service Account)**을 사용하고, 실행 전 Preview/Diff 검토 및 롤백 대책을 반드시 수립해야 합니다.

4. 보존·가시성·concurrency

  • 채팅 삭제는 통상 30일 내 영구 삭제 예정이나 법적·보안 예외가 있다.
  • Enterprise의 Library 밖 임시 upload는 별도 설정이 없으면 48시간 후 만료 가능하나 Library 파일은 채팅 삭제와 연동되지 않을 수 있다.
  • browser cookie, Project 파일, memory, execution snapshot, Sites D1/R2와 logs는 각각 별도 삭제와 보존 경계를 가진다.
  • Business/Enterprise/Edu 데이터는 기본적으로 학습에 사용되지 않는다. 개인 Plus/Pro는 “Improve the model for everyone” 설정 영향을 받는다.
  • Compliance Logs가 prompt/response와 일부 app/file 사건을 제공해도 모든 shell/browser/file/tool/approval의 완전한 trace를 보장하지 않는다.
  • 여러 채팅의 동시 실행은 가능하지만 공개 문서는 Work 전체의 고정 concurrency 수를 제시하지 않는다. 같은 파일·연결 소스의 동시 write는 충돌 위험이 있다.

5. 보안 통제와 한계

  • sandbox와 최소 권한, domain allowlist, HTTP method 제한, network proxy, consequential-action confirmation, browser takeover, 별도 reviewer/auto-review가 문서화돼 있다.
  • Auto-review는 기존 sandbox·writable roots·network 범위를 넓히지 않으며 exfiltration·credential probing·파괴행위를 차단하도록 설계됐다. OpenAI도 이를 deterministic security guarantee로 부르지 않는다.
  • product docs는 의도된 통제와 현재 제품 동작의 근거이지, prompt injection의 완전 예방·침해 부재 증명이 아니다.
lethal trifecta

Simon Willison의 threat model은 (1) private-data access, (2) untrusted content 노출, (3) 외부 exfiltration channel의 결합이다. Work가 connector/file/browser로 private data를 읽고, 웹·repo·package의 공격자 통제 텍스트를 처리하며, network/site/write action을 수행할 수 있으면 세 조건이 동시에 성립할 수 있다. 이는 공격 표면 분석이며, 이 기사 실험에서 실제 exploit이나 유출이 발생했다는 뜻이 아니다.

6. safe-use ladder

  1. 공개 자료 조사: 사용 가능. 출처와 tool output을 검토하고 external write는 끈다.
  2. private documents, 외부 action 없음: 민감도·학습 설정·retention을 확인하고 disposable workspace와 최소 connector를 쓴다.
  3. authenticated browsing: 별도 저권한 계정, takeover, 목적지·제출 내용 검토. 생산 credential·광범위 session 사용은 피한다.
  4. source/dependency 실행: lockfile·pinning·secret scan·network allowlist·격리 환경 필수. 출처 불명 setup은 실행하지 않는다.
  5. production/financial/admin actions: 기본 회피. 불가피하면 external-action isolation, 별도 승인자, preview/diff, rollback, 최소권한 service account를 요구한다.

어느 단계도 제품 전체를 “안전” 또는 “불안전”으로 단정하지 않는다. 관찰된 attack surface, 문서화된 통제, 미해결 보장과 이를 뒤집을 수 있는 검증 자료를 함께 제시한다.
