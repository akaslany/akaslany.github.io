DFly2: Turbocharging Long-Context Speculative Decoding by Sharing the Target's Sparsity

원문

DFly2: 타겟의 희소성 공유를 통한 긴 문맥 추측 디코딩 가속화 해설 보고서

1. 개요 (Overview)

[사실] 대규모 언어 모델(LLM)이 에이전트(Agent) 및 다중 대화(Multi-turn chat) 워크로드로 확장됨에 따라 처리해야 할 문맥의 길이가 수만에서 수십만 토큰으로 늘어나고 있습니다 [Section 1]. 이러한 긴 문맥(Long-context) 환경에서는 모든 토큰 간의 연산을 수행하는 기존 밀집 주의 집중(Dense Attention) 방식이 문맥 길이의 2차 비례($O(N^2)$)로 증가하는 연산 및 메모리 병목 현상을 유발합니다 [Abstract, Section 1]. 이를 해결하기 위해 최근 등장한 타겟 모델들(DeepSeek-V4.1-Flash, GLM-5.3-Flash, Hy4 flash)은 특정 토큰 위치만을 선택적으로 참조하는 자생적 희소 주의 집중(Natively Sparse Attention) 구조를 채택하여 KV 캐시(Key-Value Cache) 용량과 토큰당 계산량을 비약적으로 절감하고 있습니다 [Abstract, Section 1, Section 2].

[사실] 추측 디코딩(Speculative Decoding)은 상대적으로 작은 드래프터(Drafter) 모델이 여러 토큰 후보(블록)를 먼저 생성하고 타겟 모델이 이를 한 번에 검증함으로써 디코딩 지연을 줄이는 무손실 가속 기법입니다 [Abstract, Section 2]. 디코딩 속도가 가장 느린 긴 문맥 환경일수록 추측 디코딩의 필요성이 더욱 크지만, 기존의 블록 병렬 드래프터(Block-parallel drafter; 예: DFlash, DSpark 등)들은 밀집 타겟 모델용으로 설계된 패러다임을 그대로 유지하고 있습니다 [Abstract, Section 1]. 이들은 프롬프트 전체 또는 슬라이딩 윈도우(Sliding window) 영역에 대해 드래프터 전용 KV 캐시를 독립적으로 생성하고 유지합니다 [Abstract, Section 1, Section 3.1].

[소스의 주장] 소스 문서에서는 기존 블록 병렬 드래프터 방식이 드래프터 전용 캐시를 유지함에 따라 프리필(Prefill) 지연 시간 증가, 접두사 캐싱(Prefix Caching) 히트율 및 길이 저하, 디코드 동시성(Decode Concurrency) 감소라는 명확한 한계를 지닌다고 지적합니다 [Abstract, Section 3.1]. 또한, 드래프터가 타겟의 쿼리(Query) 특성을 반영하지 않은 채 고정된 위치(전체 또는 윈도우)만을 참조하거나, 드래프터 내부에서 위치 선택을 위한 스코어링을 별도로 수행할 경우 문맥 길이에 비례하는 연산 비용이 다시 발생하게 됩니다 [Abstract, Section 3.1, Section 3.2].

[작성자의 해석] 소스에서 제안하는 DFly2는 이러한 한계를 극복하기 위해 타겟 모델이 이미 수행하여 지불한 희소성(Sparsity) 정보를 직접 공유하는 패러다임을 제안합니다 [Abstract, Section 4]. 즉, 타겟 모델이 구축한 콤팩트(compact)한 KV 캐시를 직접 읽어오는 KV 공유(KV Sharing)와, 타겟의 색인기(Indexer)가 각 쿼리별로 선별한 희소 위치 인덱스를 공유하는 인덱스 공유(Index Sharing)를 동시 구현합니다 [Abstract, Section 4]. 이를 통해 DFly2는 자체 KV 캐시를 전혀 유지하지 않고 별도의 위치 스코어링 단계도 거치지 않음으로써 메모리 및 연산 오버헤드를 근본적으로 제거하면서도, 긴 문맥 및 에이전트 워크로드(최대 128K 토큰)에서 기존 최선책 대비 수용 토큰 길이 및 처리량을 크게 향상시켰습니다 [Abstract, Section 5.2, Section 5.3].

2. 주요 논점 (Key Arguments & Technical Details)

2.1 기존 드래프터 방식의 한계와 타겟 희소성 공유의 당위성

소스 문서의 Section 3(Observations)에서는 기존 드래프터 구조가 독립적인 KV 캐시를 유지할 때 발생하는 4가지 메모리 및 비용적 한계와, 타겟의 인덱스 선택을 블록 전체에 재사용할 수 있는 당위성을 정량적 데이터로 증명합니다 [Section 3.1, Section 3.3].

(1) 프리필(Prefill) 비용
  • [사실] 프리필-디코드 분리(Prefill-decode disaggregation) 환경에서 드래프터가 자체 캐시를 가지려면 프리필 인스턴스에 드래프터 가중치를 로드하고 모든 프롬프트 위치에 대해 임베딩 프로젝션을 실행하여 캐시를 생성한 뒤 디코드 인스턴스로 전송해야 합니다 [Section 3.1].
  • [소스의 주장] KV 공유를 적용하면 드래프터가 읽는 잠재 상태(Latents)는 타겟이 이미 프리필 단계에서 작성한 것이므로, 프리필 인스턴스에 드래프터 전용 연산이나 전송 지연이 전혀 추가되지 않습니다 [Section 3.1].
(2) 접두사 캐싱(Prefix Caching) 손실
  • [사실] 드래프터의 자체 캐시는 타겟의 은닉 상태(Hidden states)로부터 프로젝션되는데, 일반적인 접두사 캐싱 기법은 이 은닉 상태를 저장하지 않습니다 [Section 3.1]. 따라서 드래프터 캐시를 접두사 캐시 메모리에 함께 유지하거나, 히트(Hit) 시 타겟을 재연산하여 복원해야 합니다 [Section 3.1].
  • [사실] DeepSeek-V4.1-Flash(DS-V4.1-Flash) 기준, 3개 레이어 드래프터의 자체 캐시(3.4 KiB/토큰)는 타겟 고유의 KV 캐시(4.4 KiB/토큰) 대비 캐시된 접두사 메모리의 2/5(40% 이상) 이상을 차지합니다 [Table 2, Section 3.1].
  • [소스의 주장] 드래프터 자체 캐시를 저장하면 캐시 풀에 담을 수 있는 접두사 수(대화 이력)가 줄어들고, 복원 방식을 쓰면 타겟 히트 길이가 단축됩니다 [Section 3.1]. KV 공유를 사용하면 드래프터 전용 캐시가 없으므로 타겟의 모든 접두사 캐시 히트를 100% 그대로 상속받습니다 [Table 3].
(3) 디코드 동시성(Decode Concurrency) 감소
  • [사실] 디코딩 단계에서 요청별 KV 캐시 메모리 사용량이 늘어나면 GPU 메모리 내 동시 처리 가능 요청 수(Concurrency)가 감소합니다 [Section 3.1].
  • [사실] 32K 문맥 길이 환경에서 타겟 전용 KV 캐시 대비 드래프터 캐시가 추가되면 메모리 증폭률이 DS-V4.1-Flash 1.76배, GLM-5.3-Flash 1.26배, Hy4 flash 1.20배에 달합니다 [Figure 2a, Table 2].
  • [소스의 주장] KV 공유를 통해 드래프터 캐시를 제거하면 DS-V4.1-Flash 32K 환경에서 동일한 메모리 풀로 최대 동시 요청 수를 1.73배 향상시킬 수 있습니다 [Figure 2a, Table 3].
(4) 문맥 길이에 따른 디코딩 시간 증가
  • [사실] 드래프터 디코딩 시간($T_{\text{draft}}$)은 문맥 독립적 연산($T_0$)과 문맥 위치 수($m$)에 비례하는 주의집중 연산($T_{\text{attn}}(m)$)의 합으로 구성됩니다 [Section 2, Eq. 2]: $$T_{\text{draft}} = T_0 + T_{\text{attn}}(m)$$
  • [사실] 프롬프트 전체에 대한 드래프터 캐시를 읽는 DFlash 방식의 경우, 디코딩 연산에서 드래프팅이 차지하는 시간 비중이 4K 토큰에서는 3.6%~5.6%에 불과하지만 128K 토큰에서는 14%~23%(부하 증가 시 최대 22.6%)까지 지속적으로 상승합니다 [Figure 2b].
  • [소스의 주장] 긴 문맥 환경에서는 읽는 위치 수($m$)를 고정된 예산으로 제한해야 디코딩 시간이 문맥 길이에 따라 폭증하는 것을 막을 수 있습니다 [Section 3.1].
(5) 블록 내 타겟 선택 유지력 (Block Coverage)
  • [사실] 블록 병렬 드래프트 시, 1개 블록은 $\gamma$개 토큰(실험 설정 $\gamma=5$)으로 구성됩니다. 블록 시작 시점에서는 앵커 토큰 바로 전 위치($A-1$ 행)에서 타겟 모델이 선택한 희소 인덱스 집합($S_{A-1}$)만 활용 가능합니다 [Section 2, Section 3.3].
  • [사실] DS-V4.1-Flash의 긴 문맥 평가 데이터(158,638개 블록)에서 $A-1$ 행의 상위 512개 인덱스 선택 집합($S_{A-1}$)이 블록 내 이후 위치($A+k-1$)들의 실제 상위 512개 선택과 얼마나 겹치는지(Top-$k$ Mass Coverage) 측정한 결과, 레이어 및 슬롯 평균 커버리지가 87.3% ~ 88.0% (90% 근접)에 달했습니다 [Figure 3a, Figure 3b]. 반면 동일 크기(512)의 최근 슬라이딩 윈도우 커버리지는 14.7% ~ 17.5% (20% 미만)에 그쳤습니다 [Figure 3a, Figure 3b].
  • [소스의 주장 및 작성자의 해석] 타겟 모델의 인덱서 쿼리는 저주파 RoPE 성분에 에너지가 집중되어 있어 몇 토큰 위치 이동에도 선택 위치가 급변하지 않고 문맥 내용을 따라 점진적으로 변화합니다 [Section 3.3]. 따라서 $A-1$ 단계에서 결정된 타겟의 인덱스를 블록 전체에 재사용하더라도 높은 커버리지가 유지되므로 인덱스 공유 방식은 이론적·실험적으로 완전히 정당화됩니다 [Section 3.3].
2.2 DFly2의 핵심 메커니즘: KV 공유와 인덱스 공유

DFly2는 타겟 모델의 희소성 구조를 완전히 공유하며, 3개의 드래프터 레이어가 각각 타겟 모델의 특정 희소 레이어와 페어링되는 방식으로 작동합니다 [Section 4, Figure 4].

(1) KV 공유 (KV Sharing)
  • [사실] 기존 DFlash/DSpark는 타겟 은닉 상태를 받아 드래프터 고유의 K, V를 모든 문맥 위치에 대해 새로 프로젝션하고 저장합니다 [Section 4, Eq. 3].
  • [사실] DFly2의 드래프터 레이어 $i$는 별도 캐시 생성 없이, 페어링된 타겟 레이어 $L_i$가 이미 메모리에 저장해 둔 잠재 상태(Latent) $c_s^{L_i}$를 직접 읽어옵니다 [Section 4, Eq. 6].
  • [사실] 드래프터 레이어 $i$가 문맥에 대해 형상화하는 Key 및 Value 잠재 행렬 $(X_i, Y_i)$는 다음과 같습니다 [Section 4, Eq. 6]: $$X_i = W_i^{UK} C_{R_i}^{L_i}, \quad Y_i = W_i^{UV} C_{R_i}^{L_i}, \quad C_{R_i}^{L_i} = { c_s^{L_i} }_{s \in R_i}$$
  • [사실] 블록 내부 갱신 시에는 축소 프로젝션 행렬 $W_i^D$ 및 확장 프로젝션 행렬 $(W_i^{UK}, W_i^{UV})$와의 인수분해 결합 구조를 통해 문맥과 블록 토큰의 은닉 상태 $H_{\text{blk}}$를 하나의 텐서 결합 주의집중 연산으로 동시 처리합니다 [Section 4, Eq. 7]: $$K_i = [ W_i^{UK} C_{R_i}^{L_i} ; ; ; W_i^{UK} W_i^D H_{\text{blk}} ], \quad V_i = [ W_i^{UV} C_{R_i}^{L_i} ; ; ; W_i^{UV} W_i^D H_{\text{blk}} ]$$
(2) 인덱스 공유 (Index Sharing)
  • [사실] 드래프터 레이어 $i$가 읽어오는 문맥 위치 집합 $R_i$는 타겟 레이어 $L_i$의 색인기가 $A-1$ 위치에서 선택한 top-$k$ 인덱스 집합($S_{A-1}^{(L_i)}$)과 타겟의 근접 윈도우($N$)의 합집합으로 정의되며, 전체 읽기 위치 수 $m$은 고정됩니다 [Section 4, Eq. 8]: $$R_i = S_{A-1}^{(L_i)} \cup N, \quad m = |R_i|$$
  • [사실] 타겟 모델의 색인기 연산은 검증 패스에서 이미 완료되었으므로, DFly2는 자체적인 색인기나 스코어링 패스를 전혀 실행하지 않습니다 [Section 4, Figure 5b]. 읽는 위치 수($m$)는 프롬프트 길이가 증가해도 고정되어 연산량이 유효하게 제한됩니다 [Section 4].
(3) 타겟 모델별 사양 비교표

[사실] 소스 문서에 명시된 3개 타겟 모델별 DFly2 적용 사양은 다음과 같습니다 [Table 4].

타겟 모델명 페어링 레이어 $L$ Top-$k$ 방식 근접 창 (Near Window) 스텝당 읽는 위치 수 ($m$)
DS-V4.1-Flash [28, 32, 36] 512개 단일 위치 128 토큰 646 (512 + 128 + 블록 6)
GLM-5.3-Flash [35, 39, 43] 512개 그룹 (4개 인접 토큰 풀링) – (top-$k$ 내 이미 포함) 2,054 (512×4 + 블록 6)

(4) 타겟 가중치 초기화 (Initialization from Target)
  • [사실] DFly2의 드래프터 레이어 가중치는 페어링된 타겟 레이어의 가중치로부터 직접 초기화됩니다 [Section 4, Eq. 9, Eq. 10]: $$O_i = W_i^O \text{Attn}(Q_i, K_i, V_i), \quad Q_i = W_i^{UQ} W_i^{DQ} \text{Norm}(W_i^D H_{\text{blk}}), \quad W_i^\star \mid_{\text{init}} = W_{L_i}^\star$$
  • [사실] 주의집중 파라미터 초기화 시 타겟의 쿼리 프로젝션 가중치($W_{L_i}^{DQ}$)를 복사함으로써, 드래프터의 쿼리 잠재 공간이 타겟 색인기의 top-$k$ 선택이 생성된 쿼리 공간과 동기화된 상태로 학습을 시작합니다 [Section 4, Eq. 9, Figure 5b].
  • [사실] FFN(Feed-Forward Network) 파라미터는 타겟의 MoE 라우팅 전문가(Routed experts) 중 일부분($E$)을 무작위 추출하여 초기화하고, 라우터 및 공유 전문가는 그대로 복사합니다 [Section 4, Eq. 10]: $$\theta_i^{\text{exp}} \mid_{\text{init}} = \theta_{L_i}^{\text{exp}}[E_i], \quad E_i \sim \text{Unif}{B \subseteq E{L_i} : |B|=E}$$
2.3 추가 구성 요소: 최종 레이어 은닉 상태 주입 및 블록 내 보정

DFly2는 KV 및 인덱스 공유 외에도 추측 성공률을 극대화하기 위한 2가지 보조 메커니즘을 포함합니다 [Section 4].

(1) 최종 레이어 은닉 주입 (Last-layer Hidden Injection)
  • [사실] 타겟 모델의 최종 레이어 은닉 상태($h^{(\text{last})}$)는 캐시에 저장되지 않지만, 타겟이 앵커 토큰을 생성한 최신 정보를 직접 담고 있습니다 [Section 4].
  • [사실] DFly2는 $A-1$ 위치의 $h^{(\text{last})}$를 앵커 토큰 임베딩과 게이트 융합(Gated Fusion)하여 블록 입력 시점에 주입합니다 [Section 4, Figure 4]. 게이트 값은 0에서 시작하여 학습됩니다 [Section 4].
(2) 블록 내 보정 (Intra-block Correction)
  • [사실] 블록 내부의 슬롯 $k$를 디코딩할 때, 이전 슬롯($k-1$)에서 생성된 드래프트 토큰 정보와 은닉 상태를 바탕으로 순차 보정을 수행합니다 [Section 4, Eq. 11, Figure 6].
  • [사실] 기존 TreeFlash의 SwiGLU 기반 은닉 보정(Hidden Correction)에 더해, 공유된 타겟 문맥 캐시를 재참조하는 문맥 주의집중(Context attn) 및 블록 내 이전 드래프트 토큰을 참조하는 게이트 접두사 주의집중(Gated prefix attn)을 결합하여 실행합니다 [Section 4, Eq. 11, Figure 6]: $$h_k \leftarrow h_k + \text{SwiGLU}(z_k) + W_c^O \text{Attn}(q_k, C_{R_i}) + g_k \odot \text{Attn}(q_k, h_{0:k})$$ 여기서 $z_k = [\text{Norm}(h_k) ; \text{Norm}(\text{Emb}(y_{k-1}))]$이며, 쿼리 $q_k$와 헤드별 게이트 $g_k$는 해당 쌍으로부터 프로젝션됩니다 [Section 4, Eq. 11]. 이 연산은 순차적으로 진행되지만, 이미 생성된 타겟 캐시를 이용하므로 연산 추가량이 매우 작습니다(디코딩 시간의 1% 미만) [Section 4, Section 5.4].

5. 한계와 불확실성 (Limitations & Uncertainties)

본 보고서는 작성 지침에 따라 소스 컨텍스트에 명시된 사실만을 기반으로 작성되었으며, 이에 따른 기술적·실험적 한계 및 불확실 요소를 다음과 같이 정리합니다.

  1. 소스 미기재 정보 (확인 불가 항목):

    • [확인 불가] 연구진 개별 저자의 구체적 역할 분담(예: 구현, 이론 설계 등)은 문서에 기재되어 있지 않아 확인 불가합니다 [Title Page].
    • [확인 불가] 본 연구의 정확한 논문 작성 시점 및 학회 제출 연도/날짜는 표기되어 있지 않아 확인 불가합니다 [Title Page].

  2. 타겟 모델 의존성 (Target Model Dependency):

    • [사실] 본 연구는 DeepSeek-V4.1-Flash, GLM-5.3-Flash, Hy4 flash와 같은 자생적 희소 주의집중(DSA 등)을 갖춘 타겟 모델만을 대상으로 검증되었습니다 [Abstract, Section 5.1].
    • [작성자의 해석] 희소 주의집중 인덱서가 아예 존재하지 않는 순수 밀집(Fully Dense) 타겟 모델에 DFly2의 인덱스 공유 메커니즘을 그대로 적용할 수 있는지 여부 및 이때의 성능 한계는 소스 문서에서 다루지 않으므로 불확실성이 존재합니다 [Section 1, Section 6].

  3. 하드웨어 아키텍처의 한계:

    • [사실] 소스 문서의 모든 가속도 및 처리량 실험 수치는 엔비디아(NVIDIA) H20 GPU (tp8) 환경에서 측정되었습니다 [Section 5.1].
    • [작성자의 해석] H20 이외의 타사 NPU 시스템이나 다른 엔비디아 GPU 아키텍처(예: H100, B200 등)에서의 연산 및 메모리 대역폭 차이에 따른 정량적 가속 성능은 문서 내 검증 데이터가 부재합니다 [Section 5.1].

  4. 학습 데이터 시퀀스 길이 한계와 일반화 경계:

    • [사실] DFly2의 학습 데이터셋(DFly-SFT)은 시퀀스 길이가 최대 32,768 (32K) 토큰으로 제한되어 있습니다 [Section 5.1, Table 5].
    • [작성자의 해석] 평가 과정에서 64K 및 128K까지의 수용 길이가 안정적으로 유지된 것은 타겟 모델 색인기의 길이 일반화 성능에 전적으로 귀속됩니다 [Section 5.2]. 만약 타겟 색인기 자체가 초장문에서 성능 저하를 일으킬 경우 드래프터 성능 역시 이에 종속되는 경계 한계가 존재합니다 [Section 5.2].
