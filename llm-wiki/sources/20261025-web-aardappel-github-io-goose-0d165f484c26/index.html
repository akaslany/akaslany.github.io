1. 개요 (Overview)

본 보고서는 구스(Goose) 프로그래밍 언어의 공식 문서 및 README.md 파일의 소개 단락을 바탕으로 작성되었습니다. 구스는 힙 할당자(Heap Allocator), 가비지 컬렉터(Garbage Collector, GC), 참조 카운팅(Reference Counting), 소멸자(Destructor), 그리고 수명 표기(Lifetime Annotations)가 존재하지 않는 메모리 안전 시스템 프로그래밍 언어입니다. C 언어 및 러스트(Rust)와 유사한 문법 체계를 제공하면서도, 메모리 관리 체계와 데이터 레이아웃을 근본적으로 재설계하여 높은 메모리 안전성과 성능을 동시에 달성합니다.

구스의 고유한 메모리 모델은 힙(Heap)의 전면 배제와 컴파일 타임 정적 추론을 핵심 원리로 삼습니다. 프로그램은 네이티브 호출 스택, 정적 데이터, 그리고 컴파일러가 정적으로 할당한 $N$개의 '데이터 스택(data stack)'만을 사용하여 메모리를 관리합니다. 데이터 스택은 범프 포인터(bump pointer)를 갖는 대용량 주소 공간 예약 영역으로 구성되며, 스택당 최대로 활성화될 수 있는 가변 크기 값은 상단에 위치한 1개로 제한됩니다. 따라서 가변 데이터의 크기가 증가하더라도 기존 데이터의 재배치(Move)가 발생하지 않으며, 해당 데이터가 속한 범주(scope)가 종료되면 범프 포인터의 스토어 명령(one store) 단 한 번으로 메모리가 해제됩니다.

성능 및 메모리 효율성 수치 지표 측면에서 구스는 16개의 벤치마크 테스트 결과, 관용적 C++(Idiomatic C++) 대비 3.3배, 손수 최적화된 C++(Hand-optimized C++) 대비 1.16배, 그리고 안전한 러스트(Safe Rust) 대비 1.12배 빠른 실행 속도를 기록하였습니다. 동시에 피크 메모리 사용량은 관용적 C++ 대비 1.9배~1.95배, 최적화된 C++ 대비 1.3배~1.32배, 러스트 대비 1.2배~1.25배 적은 메모리만을 사용하는 우수한 효율성을 입증하였습니다.

2. 주요 논점 (Key Points)

2.1. 단일 메모리 모델 및 수명 종료 시 메모리 해제
  • 주장 (Assertion): 구스는 힙 할당자 없이 정적으로 추론된 데이터 스택과 범프 포인터만을 사용하며, 스코프 종료 시 단 한 번의 포인터 복원 명령만으로 메모리를 즉시 해제합니다.
  • 근거 (Grounds): 모든 동적 가변 데이터는 데이터 스택의 상단(Top)에 위치하므로 용량 재할당 시 메모리 이동이 발생하지 않으며 용량 체크도 필요 없습니다. 컴파일러는 컴파일 타임에 스택 할당 구조를 검증하고, 런타임에는 오직 범프 포인터만 추적하므로 메모리 해제 비용이 가깝게 절감됩니다.
  • 사례 (Examples):
    for round in 3 {
    var scratch: u8[>..] = [];                        // 증가 전용(grow-only): 포인터 증가만으로 메모리 할당
    for i in 100000 { scratch.push((i % 256) as! u8); }
    print("round ", round, ": ", scratch.len, " bytes");
}                                                     // 메모리 해제: 스택 상단 포인터로 1회 스토어(store) 명령 수행
2.2. 참조 안정성과 가변 배열 확장
  • 주장 (Assertion): 가변 배열의 크기가 늘어나더라도 내부 요소의 메모리 주소는 이동하지 않으므로, 기존 요소에 대한 참조(reference)가 유효하게 유지됩니다.
  • 근거 (Grounds): C++의 std::vector나 러스트의 Vec은 배열 확장 시 새로운 메모리 공간을 재할당하고 기존 데이터를 이동(reallocate/move)시키기 때문에 기존 포인터나 참조가 무효화(dangling)됩니다. 반면 구스는 데이터 스택 구조상 재배치가 일어나지 않으므로 배열이 유지되는 한 내부 요소의 타입 참조가 안전하게 보호됩니다.
  • 사례 (Examples):
    struct Item { id: i32, weight: f32 }

var items: Item[>..] = [];
let first .= items.push(Item { 1, 0.5 });             // 0번 요소에 대한 참조 바인딩
for i: i32 in 2..1000001 { items.push(Item { i, 0.0 }); }
first.weight = 99.5;                                  // 100만 번의 push 수행 이후에도 참조가 유효함
2.3. 주석 없는 안전한 참조 및 수명 추론
  • 주장 (Assertion): 명시적인 수명 표기(lifetime annotations), 에일리어싱/독점 규칙, 또는 unsafe 블록 없이 컴파일 타임 추론만으로 참조의 안전성을 보장합니다.
  • 근거 (Grounds): 컴파일러는 모든 참조 및 슬라이스(slice)에 대해 대상의 수명을 제한하는 정적 '루트(root)' 변수를 추론합니다. 참조가 소유자보다 오래 살아남거나 호환되지 않는 타입으로 접근하려는 경우, 컴파일러는 명시적인 위반 에러를 발생시킵니다.
  • 사례 (Examples):
    fn longest(a: u8[:], b: u8[:]) -> u8[:] { if a.len >= b.len { a } else { b } }

var outer: u8[>..] = [];
var w = outer[..];
{
    var inner: u8[>..] = [];
    format(inner, "inner text");
    w = longest(outer, inner);     // 컴파일 에러: inner를 루트로 하는 참조가
}                                  // 목적지(outer의 범위)의 수명을 초과할 수 없음 (§9.2)
2.4. 중첩 데이터의 인라인 배치 및 직렬화 성능

  • 주장 (Assertion): 모든 배열과 구조체는 포인터 인디렉션(Indirection) 없이 연속된 메모리 블록에 인라인(Inline)으로 직접 배치되어 메모리 사용량과 캐시 미스(Cache Miss)를 획기적으로 줄입니다.

  • 근거 (Grounds): 포인터 기반의 힙 재할당 구조를 사용하는 C++(std::string, std::vector) 및 Rust(String, Vec)와 달리, 구스는 구조체 내부의 모든 멤버 데이터와 메타데이터(길이 정보)를 단일 연속 바이트 레이아웃으로 밀집시켜 포인터 역참조 오버헤드를 제거합니다. 가변 길이 정수(varint) 표현과 결합되어 간섭 없는 캐시 스트리밍을 가능하게 합니다.

    명기 방식 (Spelling) 배열 종류 및 특성
    T[k] 컴파일 타임에 크기가 고정된 고정 크기 배열
    T[], T[varint] 생성 시 크기가 결정된 후 동결되는 배열 (고정 또는 가변 폭 길이)
    T[..k], T[..] 인라인 용량(capacity)을 포함하며 내부 범위 내 증감하는 배열
    T[>..] 증가 전용(grow-only) 배열: 주력 배열 종류로 내부 요소 참조가 유효하게 유지됨
    T[>..<] 증감 가능(grow-shrink) 배열: 스택, 큐, 힙 등의 동적 데이터 구조에 사용

  • 사례 (Examples):

    struct Item  { sku: u8[varint], qty: varint, cents: varint }
struct Order { id: varint, customer: u8[varint], items: Item[varint] }

var book: Order[>..] = [];
book.push(Order { id: 1001, customer: "alice",
                  items: [Item { sku: "SKU-441", qty: 2, cents: 1999 },
                          Item { sku: "SKU-7", qty: 1, cents: 500 }] });
    • 메모리 절감 및 할당 비교: 상기 Order 구조체의 경우 구스에서는 29바이트 및 0회 할당이 발생하는 반면, C++(std::string + std::vector<Item>)에서는 160바이트 및 1회 할당, 러스트(String + Vec<Item>)에서는 153바이트 및 4회 할당이 필요합니다.
2.5. 두 가지 크기의 열거형(Enum) 및 상대 참조(Relative Links)
  • 주장 (Assertion): 대수적 데이터 타입(ADT)의 메모리 배치 모드를 고정/가변 모드로 선택할 수 있으며, 좁은 상대 참조(Relative Reference)를 활용하여 추가적인 직렬화/역직렬화 오버헤드 없이 제로 카피(Zero-Copy) 파일 입출력을 지원합니다.
  • 근거 (Grounds):
    • 고정 모드(Fixed mode, Shape): 태그와 가장 큰 페이로드(Payload) 크기를 확보하여 인덱싱 및 값의 덮어쓰기가 가능합니다.
    • 가변 모드(Variable mode, Shape..): 값마다 해당하는 배리언트(Variant)의 실제 크기만 할당하여 메모리 사용량을 최소화하며, 내부 페이로드의 제자리(In-Place) 수정을 지원합니다.
    • 상대 참조 메커니즘 및 위치 독립성(Position Independence): 절대 포인터(8바이트 주소) 대신 T&<u32>와 같이 자기 자신 필드의 위치로부터의 상대적 오프셋(Offset)을 저장합니다. 이로 인해 메모리 블록 전체가 위치 독립성을 갖게 되어, 포인터 재조정(Pointer fixup)이나 별도의 직렬화기(Serializer) 없이 파일 쓰기/읽기만으로 데이터 구조를 즉시 복원할 수 있습니다.
  • 사례 (Examples):
    // 1. Enum의 두 가지 모드 (Fixed vs Variable mode) 및 제자리 수정 사례
enum Shape { Circle { r: f64 }, Rect { w: f64, h: f64 }, Dot }

var packed: Shape..[>..] = [];                       // 17바이트 고정이 아닌 9, 17, 1바이트 각각 할당
packed.push(Shape.Circle { r: 1.0 });
packed.push(Shape.Rect { w: 2.0, h: 3.0 });
packed.push(Shape.Dot);

for s in packed {
    match s { Rect &r => { r.w += 1.0; }, _ => {} }  // 배열 내부 페이로드를 제자리(in-place)에서 직접 수정
}

// 2. 상대 참조 및 제로 카피 직렬화/역직렬화 메커니즘
struct Node { key: i32, left: Node&<u32>?, right: Node&<u32>? } // 링크 포함 12바이트 노드

var image: u8[>..] = tree.to_bytes();               // 전체 이진 탐색 트리 배열을 바이트 이미지로 직렬화
var loaded, ok = from_bytes<Node[>..]>(image);      // 무결성 검증 pass 실행 후 즉시 복원
image[image.len - 3] = 200;                         // 링크 데이터 손상 시도
var bad, bok = from_bytes<Node[>..]>(image);        // 검증 실패: false 반환 및 임의 참조 방지
2.6. 호출 체인을 통과하는 제자리 생성(In-Place Construction) 및 에러 반환
  • 주장 (Assertion): 생성되는 값은 중간 임시 객체의 복사 없이 항상 최종 목적지에 직접 작성되는 생성을 보장하며, 언와인더(Unwinder)나 Result 타입 없이 복수 호출 프레임을 뛰어넘는 에러 반환 구문을 제공합니다.
  • 근거 (Grounds):
    • 제자리 생성 보장(In-Place Construction Guarantee, 스펙 §4.3): 모든 리턴값과 데이터 생성 연산은 호출 체인을 상향식으로 관통하여 최종 소유 변수나 배열 슬롯 위치에 정적 지정 후 직접 생성됩니다.
    • 복수 프레임 에러 반환 (return err from f): return E from f 구문은 중간 함수들의 시그니처를 변경하거나 Result/Option 형태의 랩핑 타입을 사용하지 않고, 정적으로 검증된 상태에서 최상위 지정 함수 f의 호출 프레임 위치로 에러 데이터를 직접 리턴합니다.
  • 사례 (Examples):
    // 1. 제자리 생성(In-Place Construction) 코드 사례
words.push(str("word", i));                         // 신규 배열 요소 위치에 직접 포맷팅되어 작성됨
let evens = xs.filter() { it % 2 == 0 };            // 임시 객체 없이 evens 목적지에 직접 생성됨
book.push(Order { id: 1001, customer: "alice", 
                  items: parse_items("SKU-441:2:1999;SKU-7:1:500") });

// 2. 호출 체인을 뛰어넘는 에러 반환 코드 사례
struct User { name: u8[..16], age: i32 }

fn load(text: u8[:]) -> User[>..], u8[] {
    var users: User[>..] = [];
    each_split(text, '\n') { users.push(parse_user(it)); };
    return users, "";
}

fn parse_user(line: u8[:]) -> User {                // 리턴 타입에 Result/Error 선언 불필요
    let comma = find(line, ",");
    // Result 타입 없이 load 함수의 호출 위치로 에러 직접 반환
    guard comma >= 0 else { return [], str("expected name,age: ", line) from load; }
    let age, ok = parse_int(line[comma + 1..]);
    guard ok else { return [], str("bad age: ", line) from load; }
    let name = trim(line[..comma]);
    return User { name: name, age: age as i32 };
}
2.7. 공유 제로 스레드 모델(Share-Nothing Threads) 및 외부 C 연동
  • 주장 (Assertion): 스레드 간 가변 메모리 공유를 완전히 차단하여 데이터 레이스(Data Race) 및 락(Lock)을 방지하고, C 언어 소스 출력과 TinyCC 백엔드를 통해 이식성과 즉시 실행성을 제공합니다.
  • 근거 (Grounds): 각 작업 스레드(thread_fn)는 고유한 데이터 스택과 전역 변수 복사본을 지닌 별개의 독립 프로그램으로 컴파일됩니다. 스레드 간 통신은 참조가 없는 플랫 값(Flat Value) 단위로 큐를 통과할 때 memcpy로 전달됩니다. 또한 extern fn을 통해 C 함수를 직접 바인딩하며 단일 C 파일로 컴파일됩니다.
  • 사례 (Examples):
    // 1. 공유 제로 스레드 모델 코드 사례
thread_fn worker() {                                // 독립된 메모리와 스택을 지닌 스레드
    loop {
        let job = qget<Job>();                      // 타입화된 Job 큐에서 차단 대기
        guard job.n >= 0 else { break; };           // 음수 값 수신 시 종료
        qput(Result { n: job.n, digits: count_digits(job.n) });
    }
}

for i in n { ids.push(thread_spawn(worker)); }

// 2. 외부 C 라이브러리 연동 코드 사례
extern fn hypot(x: f64, y: f64) -> f64;             // C 표준 라이브러리(libm) 직접 호출
extern fn crc32_bytes(s: const u8[:]) -> u32;       // 슬라이스는 { data, len } C 구조체 형태로 전달
extern fn stats_of(xs: i32[:], out: Stats&);        // 포인터를 통한 C 구조체 수정

4. 수치 및 시점 (Metrics & Specifications)

  • 벤치마크 성능 지표 (16개 벤치마크 프로그램 대상 통합 평가):
    • 실행 속도 (Speed):
      • MSVC 백엔드 기준: 관용적 C++(Idiomatic C++) 대비 3.51배, 손수 최적화된 C++(Hand-optimized C++) 대비 1.24배, 안전한 러스트(Best Safe Rust) 대비 1.13배 빠른 속도 달성.
      • Clang 백엔드 기준: 관용적 C++ 대비 3.54배, 최적화된 C++ 대비 1.26배, 안전한 러스트 대비 1.19배 빠른 속도 달성.
      • 통합 기하평균 (Geometric Mean over 16 benchmarks): 관용적 C++ 대비 3.3배, 최적화된 C++ 대비 1.16배, 안전한 러스트 대비 1.12배 빠른 속도 기록.
    • 피크 메모리 사용량 (Peak Memory):
      • 관용적 C++ 대비 1.95배 절감 (1.9배~1.95배 수준).
      • 최적화된 C++ 대비 1.32배 절감 (1.3배~1.32배 수준).
      • 안전한 러스트 대비 1.25배 절감 (1.2배~1.25배 수준).
  • 개발 환경 및 실행 요구 사양:
    • 소프트웨어 및 빌드 도구: CMake 3.27 이상, C++20 지원 컴파일러(MSVC, Clang, GCC), Python 3 (테스트 수트 및 샘플 스크립트 실행용).
    • 운영체제 요구 규격: Linux (glibc 2.35 이상 - Ubuntu 22.04, Debian 12 이상), macOS (macOS 13.3 이상), Windows (Windows 10 버전 1903 이상에서 프로세스 코드 페이지로 UTF-8 설정).
  • 코드 규모 및 인프라 명격:
    • 컴파일러 코드 규모: 약 30,000줄(30k lines)의 C++ 코드로 작성됨.
    • 기본 데이터 스택 메모리 예약: 가변 크기 값당 기본 2GB의 주소 공간 예약 (--stack-reserve 16G 플래그로 변경 가능).
    • 소프트웨어 라이선스: Apache License, Version 2.0.

5. 한계와 불확실성 (Limitations & Uncertainties)

  • 언어적 제약 조건 (Deliberately Out of Scope):
    • 가변 크기 값의 이동(move) 미지원.
    • 구조체 당 가변 크기 멤버 1개 제한.
    • 라벨이 붙은 break (labeled break) 미지원.
    • 네임스페이스 은닉 및 접근 제어(namespace privacy) 미지원.
    • OS 및 C 표준 라이브러리 저수준 직접 접근 기능의 제한적 제공.
  • 사용자 부담 요소 및 개발 비용 (Cost & Trade-offs):
    • 데이터의 위치와 스코프 수명을 개발자가 명시적으로 고려해야 함.
    • 재귀 함수 제약: 재귀 함수 내 재귀 호출 간 가변 데이터(growable data)를 계속 유지할 수 없음 (스프래치가 호출 전에 종료되거나 전용 풀로 전달되어야 함).
    • 가변 요소 배열의 직접 인덱싱 불가: 가변 크기 요소를 가진 배열은 순회(iteration)는 가능하나, 별도의 포인터 참조 인덱스 배열을 두지 않는 한 임의 인덱싱(direct indexing)이 불가함.
    • ADT 사용 제약: 고정 모드 열거형 내부 페이로드로는 참조를 걸 수 없으며, 가변 모드 열거형은 배리언트를 덮어쓸 수 없음.
    • 동적 디스패치 제한: 탈출 클로저(escaping closures), 함수 포인터, ADT 태그 분기 이외의 동적 디스패치를 지원하지 않으며 전체 프로그램 컴파일(whole-program compilation)만 제공함.
    • 재사용 풀(reusable pool) 논리적 버그 가능성: 반환된 슬롯을 지칭하는 포인터를 유지할 경우, 메모리 손상(Memory Corruption)은 발생하지 않으나 다른 소유자가 할당받은 올바른 타입의 다른 값을 읽게 됨 (논리적 버그로 동작).
  • 불확실성 및 비어있는 정보:
    • 향후 구스(Goose) 언어 자체로 컴파일러를 재작성(Self-hosting)하는 일정이나 구체적 실행 시점은 소스에서 다루지 않음 / 확인 불가.
